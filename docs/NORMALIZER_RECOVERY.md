# Паспорт восстановления нормализатора UVM_Steel

Дата фиксации: 2026-10-16. Этап B1: документация и воспроизведение,
без исправления бизнес-логики и без изменения действующего бота.

## Цель

Интеллектуальная нормализация больших заявок на металлопрокат: извлечение
всех исходных потребностей, объединение совместимых позиций, точное
суммирование, сохранение исходных характеристик и естественные команды
редактирования. Сохранение количества строк само по себе не доказывает
сохранение потребности. Коммерческая группировка не означает нормативную
взаимозаменяемость. Неизвестные характеристики нельзя додумывать.

## Результаты аудита Astra и границы доказательств

| Наблюдение | Основание и ограничение |
| --- | --- |
| Резервный RecognitionService не поддерживает балки | `recognition.py`, `_SUPPORTED`: нет beam/i_beam. AI-схема эти категории поддерживает. |
| Неизвестная единица может приводить к удалению распознанного количества | `telegram_service.py`, `exact_source_attributes`: при отсутствии буквального количества с единицей присваивается quantity=None. Подтверждено экспериментом B1. |
| Строгая проверка может отклонить семантически правильное извлечение | `ai.py`, `_validate_source_fragments`, и `source_fidelity.py`, `validate_source_coverage`: требуют подтверждённых исходных фрагментов и покрытия. Пробелы/регистр/часть пунктуации нормализуются; это не семантическое сопоставление. Конкретный прошлый ответ GPT не исследован. |
| Отклонённое извлечение не всегда доступно recovery | Проверка фрагментов находится внутри AIService.parse_request; capture_extraction вызывается только после успешного возврата в _build_active. |
| «Нормализуй», «Все», «Какой общий тоннаж?» маршрутизируются недостаточно | `dialog_context.py`, route_dialog/specific_question/request_reference: короткие команды могут возвращать общий вопрос; вопрос о тоннаже может уйти помощнику без current. «Все» должно трактоваться только относительно ожидающей операции. |
| «тонны» не назначает общую единицу всем подходящим позициям | Уточнение привязано к одному item_id; parse_bulk_quantity не поддерживает отдельное общее назначение единицы. В B1 ответ вообще не изменил ни одну единицу и повторил вопрос. Точный перехват ответа требует следующей отдельной проверки. |
| Коммерческая подпись смешивается с технической маркой в выводе | Telegram запускается с commercial_view=True; commercial_family относит С255 с индексами к ст3, consolidate_items подписывает так даже одиночную позицию. Это не доказательство изменения исходной марки в БД. |

Сравнение `defeae61..a6509c3` показывает, что большинство перечисленных
ограничений существовало до PR №8. Перечисленные модули распознавания,
проверки источника и маршрутизации этим PR не менялись. PR №8 добавил
ограниченные версионируемые GradeRule, проверки консолидации, групповые
команды и подключения репозитория правил. Их влияние на конкретные прошлые
сбои не доказано. Рациональная база ремонта — `19c9657`, с сохранением
проверок источника, Decimal, исходных снимков и связей консолидации.

Сведения сверены с `docs/DOMAIN_RULES.md`, `docs/NORMALIZATION_STAGE_ONE.md`
и текущим кодом. DOMAIN_RULES требует сохранять технические марки;
commercial_view использует отдельные коммерческие подписи. Различие
технических данных и закупочного вывода необходимо явно согласовать,
не объявляя коммерческую подпись технической заменой.

## Эталоны и ограничения проверки

- Четыре балки: 10,700 + 186,698 + 127,097 + 56,669 = **381,164 т**
  после явного подтверждения единицы пользователем.
- Шесть уголков/швеллеров из `tests/fixtures/real_114_1_4_angles.txt`:
  **4,3618 т**; сохранить марки, редакции ГОСТ, длины и исходные массы.
- Групповые изменения: все целевые позиции, без затрагивания нецелевых
  марок; область категорий и производных обозначений должна быть явной.
- Большие перечни: уголки, швеллеры, профильные трубы, листы и двутавры.
  Сохранять исходные марки, ГОСТ, размеры, количества, единицы и происхождение.
- Существующий P0: 38 исходных → 28 коммерческих строк при двух явных
  решениях, 30 без них, **205,355 т**. Не включать решения автоматически.
- Уголок 50х50х5 группы Ст3: **3,128 т**, не 3,321 т.

Большие тесты подставляют готовое извлечение Mock и не подтверждают качество
живого GPT. В B1 они не запускались. Полные четыре отраслевых эталона не
проверялись; краткие примеры не являются их заменой. Нельзя автоматически
заменять С345/С355 на 09Г2С ради совпадения короткого вывода.

## Воспроизведение B1

Тест: `tests/test_normalizer_recovery_b1.py`.
Вход — четыре строки из задания B1, без единиц, с точными исходными
фрагментами. Контролируемый ответ содержит четыре beam, С355-5,
типоразмеры и Decimal-количества, unit=None. Префикс ГОСТ к сокращённым
номерам не придумывается; номера сохраняются в исходном тексте.

Подменяется только `_invoke`: настоящий AIService.parse_request выполняет
проверку фрагментов. TelegramService работает с reliable=True и
commercial_view=True; используются настоящий TelegramRepository и временная
SQLite. Наблюдающая обёртка exact_source_attributes вызывает оригинальную
функцию без изменения результата. Сеть, SDK-клиент и production .env не используются.

Результат Windows: **1 failed** — ожидаемый воспроизводимый отказ приёмки.
Первый запуск в ограниченной среде не дошёл до сценария из-за прав на
временный каталог pytest; успешный запуск тестового контура выполнен с
отдельным временным каталогом вне репозитория. Полный pytest не запускался.

| Профиль | До exact_source_attributes | После | После «тонны» |
| --- | --- | --- | --- |
| 20Ш2 | 10.700 | None | quantity=None, unit=None |
| 30Ш2 | 186.698 | None | quantity=None, unit=None |
| 40Ш2 | 127.097 | None | quantity=None, unit=None |
| 45Ш2 | 56.669 | None | quantity=None, unit=None |

Сервис сохраняет четыре позиции и их полные source_text, но первый вывод
содержит только профили и марку без количеств. Затем спрашивает единицу
первой исходной позиции. После «тонны» повторяет тот же вопрос. Вызов
контролируемого извлечения один; дополнительных AI-вызовов нет.
381,164 т конвейером не получено. Первая доказанная потеря — присваивание
quantity=None в exact_source_attributes, до normalize_request и validate_request.

Тест намеренно красный, без xfail/skip и без закрепления дефекта как нормы.
Он содержит требования ко всему диалогу, включая все четыре единицы и сумму;
последующие проверки станут достижимы после устранения первой потери.
Он не доказывает качество живого GPT и отдельно не проверяет распознавание
сокращённых нормативных обозначений.

## Порядок ремонта после отдельного согласования

1. Количество и единицы: сохранять явно извлечённое число при неизвестной
   единице; проверить маршрутизацию «тонны» и область общего уточнения.
2. Извлечение и fallback: сохранять непроверенный ответ для адресной проверки,
   поддержать балки в существующем распознавателе, завершать partial после
   проверки исправлений. Не отключать защиту от вымышленных характеристик.
3. Контекст: локальные команды нормализации/показа/общей массы, понятная
   обработка коротких ответов без потери активной заявки.
4. Групповые правки: естественный порядок слов и проверяемая область изменения;
   согласовать техническое обозначение и коммерческую подпись.
5. Полные закупочные эталоны: исходные характеристики, связи, арифметика,
   порядок и формат; затем отдельная разрешённая Telegram-приёмка.

B1 не исправляет перечисленные механизмы. Первый следующий шаг — минимальное
исправление потери количества с неизвестной единицей, после согласования.
