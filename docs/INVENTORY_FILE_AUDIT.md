**Безопасно после выбора поля J как баланса:** сохранить явные тонны как тонны в масштабе `quantity.py`; например, J11 = 251.582 т даёт 251 582 000 масштабных единиц. Дробные значения и видимые двоичные хвосты на расчётных листах требуют определённой политики десятичной точности и проверки предела `quantity.py`.

## 8. Качество данных

- **Пропуски:** D пусто в 13 строках, E — в 7, J — в 26. Примеры: `1.ОСТАТКИ!C28` = `Окалина`, D28/E28 пусты, J28 = 0.18; C220 = `Бронзовый пруток БрАЖ 9‑4 ф 140 МЗОЦМ`, D220/E220 пусты; C71 = `Арматура А240 25`, J71 пусто при I71/S71 = 1.5. Отсутствующих B или C нет.
- **Дубли и коллизии групп:** точных дублей по (B, C, D) в 1 284 строках нет. Но по (B, E) есть 258 дополнительных строк сверх уникальных пар. `Волгоград` + `Арматура А240 8 бухта` объединяет строки 33, 34, 49, 50, 51: среди исходных C есть и `Арматура А240 8 размот`, и `Катанка 8 ст3 бухта`. Простое суммирование по E потеряет товарную идентичность. Строки 30–31: одна C `Арматура А240 10 размот`, но D = `11,7м ГОСТ 34028` против `6м ГОСТ 34028`.
- **Разные справочные и исходные признаки:** C11 = `Арматура А500С 12`, E11 = `Арматура А500 12`; C385 = `Швеллер 18П С255 12`, E385 = `Швеллер ст.3 18П`; C414 = `Лист ГК 14 С255 1,5х6м`, E414 = `Лист ГК ст.3 14 1,5х6м`. Эквивалентность не доказана.
- **Мнимые остатки и корректировки:** I15 = -0.009 т при J15 = 142.714 т и S15 = 142.705 т; I100 = -0.002 т. Отрицательных физических остатков J нет. J71 пусто, однако S71 = 1.5 из I71; нельзя интерпретировать такую строку как 1.5 т на складе. Числовых нулей J и S нет.
- **Служебные данные:** `1.ОСТАТКИ!A1` — заголовок блока, `F2` = `Устар!`, `T3` = `!!!`, строка 4 — названия полей; `1!A814` = `Общий итог`. `1_Профицит` в конце содержит строки с `-` и `0.0`, а `инструкция` содержит текст, не товары.
- **Смешанные форматы характеристик:** D11 = `11,7м ГОСТ 34028`, D346 = `немер ГОСТ 8734`, D1288 = `моток`, C163 включает стандарт ASTM, размер и обработку в одной строке. На листе `0` AE216 = `20Б1`, AE724 = числовое 10.0, AE1567 = `50х25`: один столбец имеет разные типы и семантику.
- **Подозрительная география и дата:** 27 строк с N=`-`; `Тюмень РЛЦ (Западная Сибирь)` находится под N=`ЕКАТЕРИНБУРГ`; `2.ПУТЬ!E87` содержит дату позже даты в имени файла. Это вопросы к владельцу данных, а не доказанные ошибки.

## 9. Сопоставление с SQLite

Прочитаны `database.py`, `product_identity.py`, `quantity.py`, все модули `repositories/`, `ARCHITECTURE.md`, `DECISIONS.md`, `PLAN.md`; дополнительно проверены `rules.py` и `normalizer.py` для трактовки ключа и единиц. Модель не менялась.

| Модель | Что укладывается напрямую | Что остаётся вопросом |
|---|---|---|
| `product` | Название C, часть классификации F/O, размеры и ГОСТ/ТУ после достоверного извлечения | `product_group` требует сопоставления с допустимыми кодами `rules.py`; часть видов (например, сетка, проволока, отходы, цветной металл) в перечне `PRODUCT_GROUPS` отсутствует. |
| `product.identity_key` | Версионированный ключ из product_group и нормализованных признаков | Не включает исходное название C и номер строки. Пара (B,E) не определяет уникальный продукт. Нужно решить, входят ли ГОСТ, длина, форма/размот и точный класс `А500С` в идентичность. `build_identity_key` потребует обязательные поля для ряда групп. |
| `warehouse` | B как название; N может быть базой для города | `warehouse.city TEXT NOT NULL`; 27 строк имеют N=`-`. Справочник синонимов и правила для виртуальных/специальных складов не определены. `WarehouseRepository.create` не обеспечивает уникальности названия/города. |
| `inventory` | Пара (warehouse_id, product_id), J как кандидат баланса в тоннах | `quantity_scaled >= 0`, `unit NOT NULL`, `UNIQUE(warehouse_id, product_id)`; 26 пустых J и 258 дополнительных строк по (B,E) требуют решения, что суммировать. `set_balance` перезаписывает, а не суммирует. |

**Поля без места в текущих `product/warehouse/inventory`:** исходные номер листа/строки, исходное C/D/E и точная единица источника, A бизнес-регион, O категория, I отгружаемый объём, S общий показатель, статусы `ОТХ`/долголёжа, цены K:M и стоимости P:R, данные пути, заказов, поставщиков, дат и продаж. Часть исходного текста могла бы быть отображена в `product.product`, но его одного недостаточно для трассировки каждой строки. Это анализ зазора модели, не предложение немедленно менять схему.

`quantity.py` корректно масштабирует подтверждённые тонны и кг, но не разрешает смысл спорных колонок, не конвертирует массу в длину/штуки и не принимает отрицательные объёмы. `InventoryRepository.set_balance` допускает ноль через `allow_zero=True`, но значение `NULL` в J не следует заменять нулём автоматически.

## 10. Проблемы и неоднозначности

- **ФАКТ:** `1.ОСТАТКИ!J` и `S` различны для 276 строк с заполненными J и I; ещё в 26 строках J отсутствует и S получается из I. **НЕИЗВЕСТНО:** какой показатель бизнес считает доступным к продаже.
- **ФАКТ:** у `2.ПУТЬ` I = `кг`, а P — дробные числа 67.895, 69.195. **НЕИЗВЕСТНО:** физическая единица P в выгрузке; его нельзя конвертировать без подтверждения.
- **ФАКТ:** C и E иногда меняют класс/марку/форму. **НЕИЗВЕСТНО:** утверждённые правила соответствия `А500С`→`А500`, `С255`→`ст.3`, `Катанка`→`Арматура`.
- **ФАКТ:** N — смесь городов, филиалов и служебных меток (`КРЫМ`, `ОТХ НАХАБИНО`, `-`). **ПРЕДПОЛОЖЕНИЕ:** N можно использовать как ключ группировки филиала после проверки владельцем данных; это не достоверное поле города.
- **НЕИЗВЕСТНО:** точная дата среза детального листа, статус формульного пересчёта, интерпретация отрицательных I, допустимость специальных складов, правило обработки разных длин/ГОСТ внутри одной группы.

## 11. Предлагаемый pipeline импорта

Только концепция: **XLSB → потоковое чтение → выбор листа и строк 5–1288 → удаление заголовков/служебных строк → сохранение исходных C/D/E → нормализация товара → нормализация характеристик по типу проката → выбор показателя количества → нормализация единицы → сопоставление склада и города/филиала → построение product identity → валидация конфликтов → product → warehouse → inventory**. Различные группы строк пути, заказов и динамики остаются вне импорта текущего баланса до отдельного решения.

Пример промежуточного объекта для **реальной** строки `1.ОСТАТКИ!11`; `normalized_product: null` означает, что бизнес-правило о `А500С`/`А500` ещё не принято:

~~~json
{
  "source_sheet": "1.ОСТАТКИ",
  "source_row": 11,
  "product": "Арматура А500С 12",
  "source_group": "Арматура А500 12",
  "characteristic": "11,7м ГОСТ 34028",
  "normalized_product": null,
  "warehouse": "Уфа склад Зеленая роща",
  "city": "УФА",
  "quantity": 251.582,
  "unit": "т",
  "quantity_field": "В наличии т"
}
~~~

Технически сохранять координату/исходные значения до идентификации продукта и фиксировать отдельные причины отказа: пустое J, неразрешённая группа, неоднозначный склад, конфликт характеристик, несовместимая единица или ключ.
