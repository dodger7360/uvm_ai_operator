# Этап 1: нормализация и проверяемые знания

## Аудит и границы поставки

База: `4dba1730bbb64928e74248c8be83fa9a32c34508`, чистая main.
Исходный штатный набор: 484 passed, 4 deselected, 86 subtests passed.
Четыре legacy_23met по-прежнему исключены настройкой pytest.ini.
README и commercial.py в этом HEAD отсутствуют. Основные документы — PLAN.md,
ARCHITECTURE.md и docs/DOMAIN_RULES.md. Объявленные виды RequestOperation
не равнозначны готовым исполнителям всех операций.

До этапа уже работали: отдельное извлечение каждой исходной строки,
source_fidelity, производная консолидация с идентификаторами источников,
Decimal и точный кг→т, восстановление исходных значений, история Telegram,
консервативный ключ с защитой неизвестных требований, расчёт листа Ст3.

В этапе развиты эти механизмы; исходные items не заменяются итоговыми группами.
Новая проверка validate_consolidation контролирует покрытие, ссылки,
характеристики и суммы. Потеря строки и двойной учёт — ошибки; 40→15 — допустимо.
Тесты проверяют оба интерфейса, повторяющиеся строки в разных частях заявки,
40→40/20/15 и 100→15. Workbench восстанавливает буквальные количества, марки
и стандарты для всех категорий тем же механизмом, что Telegram.

Итоговый порядок сохраняет существующий приоритет вида и числовых размеров,
добавляя марку как критерий при равных размерах. Равные ключи сохраняют порядок
исходных строк. Номера итоговых групп могут меняться после правки; стабильны
item_id и source_position. Команда с номером многопозиционной группы требует
выбора исходной строки, чтобы не изменить произвольную часть потребности.

## Узкие правила

GradeRule — направленное бизнес-разрешение для конкретной категории, размера,
ГОСТ/ТУ, марки, исполнения, обработки и условий длины/толщины. None означает
отсутствующее значение, а не любое значение. Неизвестный остаток source_text
блокирует применение. Правило не доказывает нормативную эквивалентность стали.
Ни одного реального правила или справочного значения в поставке нет.

NormalizationPolicyRepository хранит неизменяемый payload каждой версии,
кандидат/approved/rejected/retired, администратора и ссылку на регрессию,
журнал решений. Утверждение использует существующий AccessRepository.is_admin.
Новая утверждённая версия отключает предыдущую; повторное утверждение той же
версии запрещено. Конфликтующие разрешения останавливают вычисление,
не выбирая одно произвольно. Применение одношаговое, без цепочек замен.
Ссылка на регрессию — аттестация администратора, не автоматический запуск CI.

Добавляются только две таблицы normalization_rule и normalization_rule_event.
Они создаются через существующий Database при старте приложения новой версии;
существующие таблицы и request JSON не переписываются. Рабочая БД в этой
разработке не открывается. SQL остаётся в repository; PostgreSQL потребует
отдельной реализации этого маленького интерфейса и миграции, а не изменений
алгоритма нормализации.

В Telegram wiring передаёт repository в сервис. Для Workbench его можно
передать вторым параметром NormalizationWorkbench; WorkbenchResult фиксирует
снимок правил на момент обработки для воспроизводимости. Чтобы получить
новое состояние после отзыва правила, заявку нужно обработать заново.
Производная группа содержит applied_rules с ID и версией.
Административного Telegram UI для реестра в этапе нет. Предложение/решение
доступны через Python repository API в доверенном административном контексте.
Пользовательские правки сами по себе никогда не создают глобальное правило.

Примеры пользовательских действий:

- «Объедини все одинаковые уголки» — существующая точная консолидация;
  одинаковые остальные характеристики с разными марками перечисляются
  отдельно как предложения для согласования. «Да» не утверждает новое правило.
- «Во всех уголках замени Ст3сп5 на Ст3» — явная разовая правка только уголков
  с этой текущей маркой; другие категории и марки не меняются.
- «Поменяй Ст3сп5 на Ст3 там, где это разрешено» — только позиции, попавшие
  в точную область уже утверждённого правила. Без него требуется уточнение.
- «Восстанови исходную марку исходной позиции 1» — существующее восстановление.

Утверждённые правила используются автоматически в производном представлении.
При восстановлении источника активное правило может снова изменить его
представление; исходная восстановленная марка остаётся в items/original.

## Масса

Кг→т и существующий геометрический расчёт обычного листа Ст3 сохраняются.
calculate_reference_mass в quantity.py принимает явные kg_per_unit,
reference_unit (м/шт), basis и expected_identity = consolidation_key(item).
Полный ключ привязывает значение к характеристикам конкретного товара.
Неполные характеристики, неизвестные требования, неверная единица/ключ,
неположительная масса, дробное число штук дают unavailable.
Все вычисления Decimal, округление не меняет исходную потребность.
Результат содержит исходное количество/единицу, метод, источник, ставку,
итог кг/т и reliability: verified_reference либо supplier_actual.

Это общий программный API для проверенного справочника/спецификации.
Значения не извлекаются автоматически из разговорного текста и не берутся
из AI. Автоматического подключения справочных ставок и команды их ввода
в Telegram пока нет; пересчёт метров без переданного источника не обещается.
Флаг supplier_actual обозначает происхождение ставки из спецификации;
он не является независимой проверкой поставщика и не заменяет заказанный
объём фактической массой. Расширение геометрии труб/профилей требует проверенных
формул, плотностей и условий применимости. Компактное «50505» без доказуемой
расшифровки не превращается автоматически в «50×50×5».

## Минимальная модель обучения (проект, не загрузчик истории)

Реализованный реестр правил — первая часть контура. Для следующего этапа:

- learning_example: UUID, обезличенный вход, согласованный итог, структурированная
  правка, источник, версия обезличивания, статус проверки. Только выборочные примеры.
- example_provenance: ссылка на Bitrix request ID и стабильный actor user ID,
  доступная ограниченному кругу; имя только атрибут отображения. Не Git.
- regression_run: rule ID/version, commit SHA, набор example IDs, результат,
  время и метрики; связать с уже существующим regression_evidence.

Путь: выборка действий эталонного сотрудника по ID → проверка авторства →
обезличивание → кандидат → проверка человеком и регрессия → администратор →
новая версия. Одобрение разовой правки не означает одобрения глобального правила.
Данные других сотрудников служат фактическим контекстом, не источником
автоматических глобальных правил. Весов GPT этот процесс не изменяет.

Полная история 80 тысяч заявок остаётся в Bitrix. Индекс должен хранить ссылки,
минимальные поисковые признаки и права; загрузка текста — выборочная и с проверкой
прав. Сроки хранения, требования обезличивания и доступ к примерам согласуются
перед сбором. Автоматический экспорт реальных сообщений в Git запрещён.

## Контракты будущих адаптеров

Контракты ниже — проект интерфейсов, сетевых реализаций сейчас нет.

BitrixRequests: get_request(request_id, actor), search(query, actor, cursor),
get_comments(request_id, actor, cursor), apply_patch(request_id, expected_revision,
patch, actor, idempotency_key), add_comment(...), change_status(...).
request_id равен видимому номеру заявки. Revision защищает от перезаписи чужой
правки; адаптер отображает меняющиеся поля модуля в общие модели ядра. Права
проверяются на чтение, поиск и запись, не только при входе в Telegram.

OutlookMail: draft(request_id, supplier_id, city, body, attachments),
send(draft, policy_decision, idempotency_key), read_replies(message_id, cursor).
Microsoft Graph — кандидат; доступность и требования не проверены в этапе.
Стандартный шаблон + утверждённый поставщик могут разрешать отправку автоматически;
остальные письма требуют подтверждения. До реальных отправок обязательны outbox,
уникальный ключ операции, журнал, reconciliation после сетевого таймаута
и связь Bitrix ID ↔ message ID. Таймаут не означает, что письмо не отправлено.

Suppliers: search(city, product, actor), get_supplier(id, actor).
Excel и «Карта поставщиков» — разные источники одной логической записи с
происхождением полей и датой актуальности; не две несвязанные копии контактов.

MarketOffers: search(query, city, warehouse, observed_after) → offer + источник,
время наблюдения, единица, валюта, условия, наличие. Исторические цены отдельно
от текущих. Металлоторг/Металлсервис подключаются после проверки доступов,
структуры и разрешённого способа получения данных.

Attachments: extract(document, limits) → текст/таблицы + ссылки на лист/страницу
и неопределённости; затем обычная проверка исходных позиций и нормализация.
Личный чат — отдельное хранилище/лимиты/права и ограниченная память, без
автоматического включения в корпоративные заявки и обучающие примеры.

## Безопасная приёмка

Все текущие новые тесты используют синтетические данные, mock AI и временную
SQLite. Они подтверждают Python-пайплайн, но не качество живой модели на 100
строках и не задержку Telegram. Windows и production polling не изменяются.

После отдельного решения о тестовом развёртывании: отдельный тестовый бот,
тестовый токен и SQLite, без второго polling для production-токена. Проверить
40 строк без дублей, 40 с 20/15 группами, смешанные кг/т, групповую замену марки,
восстановление и неоднозначный номер группы. Сверить исходные количества и
source_indices/source_positions каждой группы. Затем проверить узкое правило
и отзыв на синтетической заявке. Не вводить реальные правила до проверки
области применения, источника и регрессий администратором.

Для Bitrix потребуются: адрес/тип установки, схема модуля «Заявка на снабжение»
и полей позиций, механизм комментариев и статусов, тестовый доступ с правами,
пагинация/лимиты/изменения, постоянный user ID эталонного сотрудника, разрешение
на выборку и обезличивание. Для Outlook — tenant/mailbox, модель авторизации,
политики отправки, шаблоны и тестовые получатели. Секреты передаются вне Git.

При сохранении нового ответа Telegram сохраняет снимок normalization_rules
в JSON заявки. Отображение исторического снимка воспроизводит его версии;
новая обработка берёт действующий реестр, включая отзыв. Старые JSON без
этого поля читаются как заявки без применённых правил. WorkbenchResult также
содержит снимок. Это не добавляет копию исходной заявки Bitrix в новый реестр.
