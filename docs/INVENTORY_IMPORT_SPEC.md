# Спецификация импорта остатков из XLSB

## 1. Статус и границы

Документ продолжает [аудит исходной книги](INVENTORY_FILE_AUDIT.md). Источник: `9. Дефицит профицит_25сентября'2026.xlsb`, SHA-256 `f1c7ded3128a72cfe7317aff1499d2434695bc639b8e30fe39f44f2f959b704d` по аудиту. Здесь описан **кандидат** на импорт текущего физического остатка: лист `1.ОСТАТКИ`, строки 5–1288, поле `J` (`В наличии т`). Дата среза и актуальность кэша формул не подтверждены. Имя файла не служит датой среза.

Статусы правил: **факт** следует из файла или текущего кода; **предлагается** означает безопасное правило для будущей реализации; **решить** означает, что строка не может быть записана без решения владельца данных. Этот документ не разрешает запуск production-импорта. В рамках dry-run не открывались SQLite и OpenAI API, не изменялись XLSB, схема и production-код.

Сводные и расчётные листы (`1`, `2`, `3`, `4`, `ИСХОДНЫЕ ДАННЫЕ`, `для динамики` и остальные) не входят в баланс. `2.ПУТЬ` — ожидаемое поступление, `3. Неотгруж объем` — объём заказов, `I` — отгружаемый объём. Их нельзя складывать с `J`.

## 2. Контракт одной строки

| Назначение | Источник | Правило |
|---|---|---|
| Трассировка | имя/хеш книги, `1.ОСТАТКИ`, номер строки | Сохранить в журнале dry-run и будущем журнале импорта. В текущем `inventory` этих полей нет. |
| Склад | `B` | Точное исходное имя физического/специального склада; не заменять значением `N`. |
| Филиал | `N` (`Склад2`) | Отдельная метка группировки, не гарантированное название города. |
| Бизнес-регион | `A` | Контроль и диагностика; не использовать для автоматического города. |
| Исходный товар | `C` | Основной текст для разбора идентичности; сохранить без потери. |
| Характеристика | `D` | Разбирать длину, ГОСТ/ТУ и форму только по проверенным правилам конкретного вида товара. Пустое значение не заполнять догадкой. |
| Исходная группа | `E` | Справочная группировка для сверки с `C`, не identity товара и не источник замены марки/класса. |
| Вид и категория | `F`, `O` | `F` — кандидат для `product_group`; `O` — отдельная категория, не поле identity. |
| Физический остаток | `J` | Число тонн из заголовка `J4`; пустое значение означает отсутствие данных, а не 0. |
| Отгружается / итог | `I`, `S` | Оставить диагностическими полями; `S=J+I` при пустом слагаемом как 0, но это не правило физического баланса. |

Промежуточная запись должна нести `source_row`, исходные `A/B/C/D/E/F/I/J/N/O/S`, выбранное количество и единицу, результат сопоставления склада, нормализованные признаки товара, кандидат `identity_key` и список причин блокировки. Неуспешную строку нельзя молча пропустить из отчёта. Будущая запись `inventory` допустима только после разрешения всех обязательных решений.

## 4. Соответствие текущей модели product identity

`build_identity_key` в [product_identity.py](../product_identity.py) строит версионированный `v1:` ключ из `product_group` и 13 нормализованных признаков: `size_designation`, `grade`, размеров, `form`, `gost_tu`, `processing`. Исходное название `C`, склад, `E` и номер строки в ключ **не входят**. Для группы нужны обязательные поля из [rules.py](../rules.py); иначе ключ отклоняется. `product.identity_key` уникален в [database.py](../database.py). Поэтому совпадение `(B,E)` и даже `(B,C)` не доказывает совпадение product identity.

Для dry-run применена лишь **предварительная** классификация `F`: арматура → `rebar`; листы → `sheet`; уголок → `angle`; швеллер → `channel`; балки → `beam`; профильные трубы → `profile_pipe`; круглые трубы → `round_pipe`; круг → `round_bar`; полоса → `flat_bar`; лист ПВ → `expanded_metal`. Так классифицированы 1 155 строк, 129 остались без допустимого кода. Среди последних: `Профиль` 74, все виды проволоки 34, `Квадрат` 5, `Шестигранник` 4, отходы 3, сетка 3, металлоизделия 3, шпунт, цветной металл и канат. Само совпадение названия вида с группой ещё не доказывает корректный разбор размеров или марки.

В диагностике 477 строк арматуры дали кандидат ключа при локальном разборе явных `А…` и диаметра из `C`, длины/ГОСТ из `D`, формы из `C/D`. Из них 466 имеют число в `J`. Для остальных 55 строк арматуры диагностический разбор не доказал полный ключ: 34 содержат дополнительный текст, 21 не совпала с узким шаблоном названия (в частности, катанка). Кандидат ключа **не подтверждает** бизнес-эквивалентность: шаблон пока не трактует все свойства `D` и не решает `немер`, стандарты, АI/А240 и особые изделия. У 623 классифицированных строк других видов парсер признаков в этом dry-run не применялся. Это честная граница расчёта, а не число невалидных товаров.

Разные источники признаков требуют ручной сверки: `C11=Арматура А500С 12`, `E11=Арматура А500 12`; `C385=Швеллер 18П С255 12`, `E385=Швеллер ст.3 18П`; `C414=Лист ГК 14 С255 1,5х6м`, `E414=Лист ГК ст.3 14 1,5х6м`. По [DOMAIN_RULES.md](DOMAIN_RULES.md) нельзя подменять сталь, класс, раскрой или длину без подтверждённого правила. Строки 30–31 имеют одно `C`, но длины `11,7м` и `6м`; их нельзя объединять по `C`.

## 5. Склады

На детальном листе 37 точных имён `B`, 24 метки `N` и 22 бизнес-региона `A`. Полный перечень `B/N/A` дан в [аудите](INVENTORY_FILE_AUDIT.md#7-склады-и-города). Ключ будущего склада должен быть основан на утверждённом соответствии точного `B` существующему или новому складу; имя `N` годится лишь для контроля филиала. `warehouse.city TEXT NOT NULL`, а `WarehouseRepository.create` не обеспечивает уникальность имени и города. Следовательно, нельзя автоматически создавать склад из `(B,N)` или использовать `N` как `city`.

Обязательные исключения в справочнике:

| Источник | Строк | Решение до импорта |
|---|---:|---|
| `B` начинается с `Долголежи` | 13 | Отдельный статус, не сливать с обычным складом того же города. |
| `B` начинается с `ОТХ` | 228 | Отдельный статус; из них `ОТХ Уральская Сталь (Нахабино)` — 206 строк с `N=ОТХ НАХАБИНО`. |
| `Склад приемки Пермь НН` | 1 | Не считать автоматически обычным складом `Пермь`. |
| `N=-` | 27 | Город/филиал не определён из `N`; требуется явная запись в справочнике. |
| `Тюмень РЛЦ (Западная Сибирь)` | 5 | `N=ЕКАТЕРИНБУРГ` противоречит названию `B`; проверить до сопоставления. |
| `Москва (Нахабино)`, `Псекупс (Краснодар)`, `КРЫМ` | несколько | Уточнить физический город и роль филиала; топоним в скобках и `N` не являются утверждённым `city`. |

Нельзя полагаться на единственность `N`: `УФА`, `МОСКВА`, `ВЛАДИВОСТОК`, `КАЗАНЬ` объединяют несколько разных `B`. В сухом прогоне утверждённый справочник городов отсутствовал, поэтому число строк, готовых к записи в `warehouse/inventory`, равно **0**. Это блокировка правила, а не ошибка данных всех 1 284 строк.

## 6. Количество и единицы

Источник баланса: `J` в тоннах. В [quantity.py](../quantity.py) `to_scaled_quantity(value, "т")` умножает на 1 000 000 без округления; превышение точности или диапазона SQLite отклоняется. Не пропускать округлением результат, который функция не принимает. Пустой `J` остаётся `NULL` на этапе анализа и не передаётся в `to_scaled_quantity`. Явный ноль, если появится в другой книге, требует отдельной политики; `set_balance` технически допускает его через `allow_zero=True`. Отрицательный физический баланс отклонять.

`I` и `S` не входят в расчёт `inventory`: `I` имеет 28 отрицательных значений и может обозначать корректировки; `S` иногда положителен при пустом `J` (строка 71). Размер `11,7м` в `D` — длина изделия, не единица остатка. `2.ПУТЬ!I=кг` не доказывает единицу `P=Поступит`; путь исключён до отдельной спецификации. Метры и штуки не выводятся из тонн без проверенной массы единицы.

## 9. Условия будущей реализации

1. Владелец данных утверждает срез, точный смысл `J/I/S`, набор складских статусов и полный справочник `B → warehouse/city/branch`.
2. Владелец товара утверждает `C/D/E` и правила эквивалентности. Для каждого поддержанного вида реализуется локальный, проверяемый парсер атрибутов с явным отказом при недостающих обязательных полях и противоречиях.
3. Перед любой записью формируется полный отчёт: число принятых/отклонённых строк, причины по координатам, суммы `J` до и после фильтров, группы коллизий `warehouse + identity_key + unit` и решение по каждой группе.
4. Агрегация выполняется до `InventoryRepository.set_balance`, потому что метод заменяет существующий баланс. Повторный импорт требует согласованной политики срезов и сохранения происхождения строк вне текущей таблицы `inventory`.
5. Отдельно проектируется импорт пути, заказов, продаж и исторической динамики, если он нужен. Текущая SQLite-схема не хранит эти типы данных и координаты источника.
