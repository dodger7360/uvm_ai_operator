# Чтение MetalReference для RecognitionService — этап 3

## Аудит и границы

Существующая схема `metal_reference/schema.py` содержит source, family,
category, item, variant, standard, dimension, property и alias. Импортёры
`ingest_armatura_price.py` и `ingest_armatura_a3.py` заполняют эти таблицы,
но отдельного репозитория чтения справочника в проекте нет. Предыдущие
тесты модели используют прямые SQL-запросы к временным данным.

Новый `metal_reference/reader.py` — независимый адаптер чтения существующих
таблиц. Ни схемы, ни импортёры, ни данные не изменены. Индексы поиска в памяти
создаются на время одного пакета из прочитанных строк. Это не новый справочник,
не постоянное хранилище и не система идентификации товаров.

## Интерфейс

Контракты и протокол `ReferenceReader` находятся в `reference_lookup.py`:

```python
reader.find_candidates(specs, context=None) -> list[ReferenceCandidates]
```

Каждый результат содержит `record_id`, статус, список кандидатов, предупреждения
и признак ограничения числа результатов. `ReferenceLookupContext` задаёт
явный ID источника MetalReference, фильтр кодов категории, ссылку на рабочий
контекст нормализации и максимальное число кандидатов (по умолчанию 100).

```python
from recognition import RecognitionService
from metal_reference.reader import SQLiteMetalReferenceReader
from reference_lookup import ReferenceLookupContext

reader = SQLiteMetalReferenceReader('explicit-reference.sqlite3', reference_id='catalog-v1')
service = RecognitionService(reader, ReferenceLookupContext(reference_source_id=1))
batch = service.recognize_records(records)
spec = batch.results[0].spec
hypotheses = batch.results[0].reference
```

Reader требует явного пути. Он не использует `Database()` с production-путём,
не читает `.env` и не вызывает initialize/импорт. Открытие — URI `mode=ro`,
дополнительно `query_only=ON`, затем одна согласованная read-транзакция на пакет.
Читаются только девять таблиц `reference_*`; заявки и пользователи не читаются.
Подключение закрывается после снимка. При отсутствии файла он не создаётся.

Reader необязателен: обычный RecognitionService не импортирует sqlite3 и
работает как на этапе 2. Допустим тестовый или другой адаптер протокола.
Reader не вызывается для пустого пакета и пустых описаний без spec.
Адаптер обязан вернуть ровно один результат для каждого переданного record_id;
порядок возвращённых результатов может отличаться, соответствие проверяется.

## Поиск и кандидаты

Поиск использует полное исходное описание и известные исходные/нормализованные
обозначения профиля, названия категории и явно распознанный диаметр. Проверяются
`designation`, существующий `normalized_key`, имена категорий, raw/normalized
значения aliases и идентификаторы источников. Нормализуются лишь написание,
пробелы, регистр и уже поддержанные разделители размеров. Это поисковые метки,
а не технические или коммерческие ключи идентичности. Fuzzy-поиска и замены
материалов нет.

Семейство, категория и явно заданный category_codes ограничивают поиск.
Для профильной трубы категория должна указывать профильное/прямоугольное/
квадратное исполнение; общая «Труба» не доказывает этот тип. Явное семейство
pipe учитывается раньше неточного определения по подстроке «угол» внутри
«прямоугольная». Старый нормализатор не изменён.

Alias категории возвращает широкий набор гипотез с объяснением «только
категория». При указанном профиле такой набор ограничивается совпадением
написания типоразмера. Alias конкретного изделия разворачивается во все
его существующие варианты. Alias варианта ограничивает результат этим
вариантом. Несколько причин попадания объединяются в evidence, а не выбирается
первое совпадение. Сортировка по существующим ID стабильна и не означает рейтинг.
При достижении лимита `truncated=True`; единственный оставшийся в ограниченном
списке кандидат не объявляется выбранным или технически совпадающим.

Каждый кандидат содержит исходные строки item/category/family, необязательные
variant/standard, dimensions/properties, связанные источники и объяснение
поиска. `ReferenceEntry` хранит существующие ID/поля таблицы и provenance с
ID каталога, таблицы/записи и source_locator. ID записи локален каталогу:
при использовании нескольких каталогов следует задавать различный reference_id.

Поле REAL сериализуется как строка его сохранённого значения. Исходный raw_value,
unit и context сохраняются отдельно. Это не восстановление утраченной точности
Decimal и не подтверждение нормативности массы или геометрии. Никаких расчётов
по reference_property не выполняется.

## Aliases и область действия

Существующее свободное поле alias_type адаптируется без миграции:

| alias_type | Роль и ограничение |
| --- | --- |
| alternative_spelling / spelling | Альтернативное написание; только гипотеза поиска |
| abbreviation | Сокращение; только гипотеза поиска |
| supplier_designation | Только при совпадении явного reference_source_id |
| source_identifier | Только при совпадении явного reference_source_id |
| commercial_label | Только при совпадении явного reference_source_id; не технический alias |
| другие, включая legacy request_phrase | unclassified; при указанном source_id требуется тот же контекст |

Ссылка source_id у общих написаний означает происхождение, а не автоматически
ограниченную область действия. Для scoped-ролей отсутствие source_id делает
alias неприменимым. `external_id` изделия используется только в своём источнике.
Имя поставщика и SourceRef входной строки не преобразуются автоматически в
числовой ID MetalReference: такую связь должен явно передать адаптер источника.

Схема не хранит отдельный supplier_id, условия применимости, срок действия,
подтверждение пользователя и версии alias. Поэтому эти сведения нельзя угадывать
из metadata. Неизвестный alias_type сохраняется в evidence с предупреждением;
полноценная политика потребует отдельного согласования, без миграции на этом этапе.

## Технические факты, гипотезы и будущая память

`RecognitionResult.spec` и `RecognitionResult.reference` независимы.
Всем кандидатам присвоено `technical_assessment='not_assessed'`. Совпадение alias
не означает техническую взаимозаменяемость. Противоречащие марки или ГОСТ могут
остаться среди гипотез; сравнение этих требований — следующий этап.

Например, для «Швеллер 20У» найденный variant С345-6/ГОСТ 8240-97 не добавляет
ни марку, ни стандарт, ни высоту, ни количество в spec. Reader получает глубокие
копии технических моделей; даже изменение вложенных словарей тестовым адаптером
не изменяет результат распознавания. Специальный alias не превращается в правило
для новых заявок.

`ReferenceLookupContext.normalization` сохраняет связь с контекстом №101.
DI-протокол позволяет позднее добавить контекстные способы формирования
поискового запроса. Сами подтверждения, причины исправлений и scope должны
оставаться в CorrectionRecord/ConfirmedExperience и отдельном слое опыта.
`knowledge_layer='metal_reference'` намеренно не позволяет выдавать пользовательское
исправление за нормативную запись. Поиск, обучение, применение опыта и Telegram-
диалог сейчас не реализованы; существующие справочные таблицы не используются
как новое хранилище памяти.

## Пустые/неполные данные и тесты

Пустой item даёт empty_reference, отсутствие совпадений — no_candidates.
Недоступная БД или отсутствие основных таблиц — unavailable. Отсутствующие
необязательные таблицы дают предупреждения и частичный набор кандидатов.
Неизвестные grade_class, standard, свойства остаются отсутствующими.
Чтение с ошибкой не меняет распознанный spec и не запускает исправление схемы.

Новые тесты используют только синтетическую временную SQLite или тестовый
адаптер. Они проверяют неоднозначность, контекст поставщика, происхождение,
противоречия, лимит, отсутствие записи в БД и неизменность spec. Значения массы
в тестах не являются реальными нормативными источниками.
Прежние эталоны №101/102, Telegram 38 → 28, исходные данные и масса 205,355 т
сохраняются. Production, платные API и обучение не запускаются.
