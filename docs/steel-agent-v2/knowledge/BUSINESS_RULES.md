## Запись и изменение правила

Глобальные ID BR-001–011 заданы владельцем. Для будущих предметных правил
сохраняется предложенный формат `BR-<GROUP>-<NNN>`; ID не переиспользовать.
Каждое правило получает номер редакции.
Поля: статус, формулировка, область (товар/условия/единицы/операция), действие,
исключения и случаи неприменимости, основания/CASE, связанные технические факты,
точное отдельное подтверждение владельца и дата, проверенные/пограничные случаи.
Формат ID — организационное предложение №26, не отраслевое правило.

| Статус | Значение |
|---|---|
| proposed | Кандидат на общее правило; явно показать владельцу, не применять как постоянное утверждённое знание |
| approved | Владелец отдельно подтвердил формулировку и область; применять только внутри них |
| superseded | Прежняя редакция заменена, ссылка на новую обязательна; сохранить прежнее содержание и основание замены |

Пересмотр: добавить новую редакцию со своим основанием; прежнюю пометить superseded,
не удалять её историю. Новая proposed-редакция не отменяет действующую approved до
явного решения владельца. Конфликт с техническим фактом или утверждённой политикой
не закрывать догадкой: обозначить ограничение и запросить решение.

Утверждение итогового текста одного кейса **не** утверждает обобщение. Разовая
поправка действует в текущем кейсе и подходящих его позициях; новую постоянную
формулировку согласовать отдельно. Запись «владелец обычно предпочитает» без
подтверждения недопустима. При approved фиксировать свидетельство в публикации,
а не ссылаться на недоступную память чата. Кейсы не доказывают всеобщую норму.

## Правила

BR-001–009: **approved, rev 1, подтверждение владельца 19.10.2026, этап 1**.
Область — нормализация и обычные Telegram-ответы, с указанными исключениями.
Сохранять исходные позиции, характеристики, полные марки, ГОСТы, единицы и
количества. Не добавлять неподтверждённые характеристики/стандарты. Группировка
не разрешает потерю различий, консолидацию товаров или техническую замену.

### BR-001. Без итогов по умолчанию

Не выводить суммарный тоннаж, суммы стоимости и другие итоги без явного запроса.
Количество каждой позиции сохранять обязательно. Внутренние расчёты разрешены;
при запрошенном итоге обозначать неполноту. Просьба объяснить группировку сама
по себе не является просьбой показать суммы.

### BR-002. Без нумерации

Не нумеровать строки нормализованной заявки. Устойчивые внутренние ID сохраняются.
Ссылка «позиция 3» должна относиться к актуальному отображению, а не скрытому
старому порядку, даже если печатные номера отсутствуют.

### BR-003. Группировка по видам металлопроката

В смешанной заявке распределять все позиции по видам: лист, уголок, швеллер,
труба, балка, арматура и другие. Перечень не закрывает ассортимент и не задаёт
порядок видов. Неизвестный вид не придумывать; исходный фрагмент не выбрасывать.

### BR-004. Группировка по маркам стали

Внутри каждого вида группировать по маркам стали. **Только для утверждённого
примера с листами:** Ст3 перед 09Г2С-15. Не распространять этот частный порядок
на все марки или иные случаи без отдельного правила. Составные марки сохранять
полностью. Полный исходник примера в задании не дан: эталонный CASE не создаётся
и не объявляется проверенным.

### BR-005. Размеры по возрастанию

Внутри вида и марки сортировать по основным размерным параметрам; для листа
в первую очередь по толщине. Различающиеся позиции не объединять.
Неизвестные размеры не домысливать. Вторичные ключи, равные и неопределённые
размеры требуют предметных примеров; новый порядок для них здесь не установлен.

### BR-006. Нативное оформление Telegram

Не допускать видимых звёздочек Markdown, Markdown-ссылок, обратных слешей
экранирования и других артефактов разметки. Это не разрешает удалять значимые
буквальные символы исходных товарных данных. Проверить безопасное применение
Telegram HTML parse_mode с экранированием пользовательских данных; реализацию
в этом этапе не менять. Диагностика — [TELEGRAM_PRESENTATION](../TELEGRAM_PRESENTATION.md).

### BR-007. Компактные источники

В обычном ответе максимум 1–2 релевантных источника: короткие кликабельные названия
сайтов, без дублирования ссылок. Полный список — по отдельному запросу.
Все проверенные источники остаются доступны для внутренней проверки: ограничение
видимого списка не означает усечение доказательств. При отсутствии подтверждённого
URL не выдумывать сайт или ссылку.

### BR-008. Компактная заявка без заголовков групп

Каждая позиция — самостоятельная строка с наименованием, характеристиками и
количеством. Отдельные заголовки «Лист», «Труба» и т. п. не выводить.
Между группами допустима пустая строка. Наименование внутри товарной строки
не является заголовком. Существенные неизвестные и unresolved не скрываются.

### BR-009. Свободный порядок товарных групп

Порядок самих видов не регламентируется. Не вводить дополнительную сортировку
видов и не требовать сохранения порядка их первого появления.
Это не отменяет BR-004/005 внутри вида и марки.

### BR-010. Адресация по отображаемому порядку

**Approved, rev 1; владелец, этап 2, 19.10.2026.** «Позиция 3» — третья товарная
строка последней показанной нормализованной заявки, не исходника и не скрытого
items. Печатных номеров нет, внутренние ID устойчивы. Связь порядка с ID
сохраняется при создании, изменении, undo и повторном выводе.
Подготовить механизм к BR-003–005, не внедряя их сортировку в этапе 2.

### BR-011. Семантический выбор и редактирование

**Approved, rev 1; владелец, этап 2, 19.10.2026.** Выбирать позиции по виду,
характеристикам, марке, размерам и контексту. GPT понимает смысл, Python разрешает
выбранный набор ID, проверяет и применяет операции атомарно.
«Лист сделай Ст3» — всем листам; «лист 8» — толщина 8 мм, не номер 8;
«на всё поставь Ст3» — всем подходящим позициям. Очевидная групповая команда
не требует слова «все». Отличающиеся товары не сливаются.
Если требуется один из нескольких различающихся кандидатов, а выбора недостаточно,
задать короткий вопрос без мутации.

«Арматуру добавь 7 т» увеличивает существующее количество на 7 т, не заменяет
его и не добавляет новый товар. «Лист в итоге нужен 50 т» задаёт **каждому**
выбранному листу 50 т, не общий тоннаж заявки. «Труба профильная длиной 6 м»
задаёт 6000 мм только выбранным профильным трубам, не круглым электросварным.
«Позицию 3 сделай 10 т» адресует третью отображённую товарную строку по BR-010.
Не менять иные поля или марки догадкой. Групповая ошибка не оставляет частичного результата.

## Кандидат этапа 2 — реализация BR-010/011

Обычный normalized/forward теперь без нумерации (BR-002); порядок групп не изменён.
presentation.display_order — одно определение порядка ID для вывода и метаданных
Reply.display в существующей истории/outbox, без новой SQLite-таблицы.
Repository.last_display проверяет пользователя, request/revision, полный состав ID
и состояние доставки durable события. Недоставленный/unknown/denied ответ не
становится последним показанным. Для старой истории без метаданных сначала нужен
новый show_request; подставлять исходный порядок небезопасно.

Operation.selection выбирает display/where/all. Where — пересечение точных условий
по label/существующим характеристикам; для составного размера GPT может указать
буквальный разделитель и номер компонента. Python не назначает компонентам смысл
толщины/стенки сам. One с несколькими совпадениями и пустой набор дают уточнение.
All применяет операцию ко всему совпавшему набору. Скрытой консолидации нет.
Отдельные set_quantity/add_quantity/set_length поручают Python точную арифметику
и стандартный перевод длины в мм. Прибавление сохраняет единицу текущей позиции;
несовместимое или неизвестное исходное количество не пересчитывается догадкой.
PendingClarification сохраняет неразрешённую операцию вместе со значением и единицей.

Устойчивые ID, originals/provenance, версии и undo сохраняются. После известного
структурного сбоя ремонт семантического плана не может сменить набор ID, вид
операции или поле, кроме прежнего узкого ремонта set.quantity/unit в convert_mass
по тем же ID. Прежние прямые ID остаются совместимым внутренним интерфейсом
и используются для подтверждения сохранённых уточнений; новый GPT-путь инструктирован
использовать selection для предметного/числового выбора.

Проверки и ограничения — [отчёт этапа 2](../reports/stage-2-semantic-editing.md).
Структурные гарантии не доказывают безошибочность понимания живой GPT.
Кандидат ещё не развёрнут. BR-003–005/006/007 в этом этапе не реализуются.

## Точки следующей функциональной работы

1. transport.INSTRUCTIONS и существующий контекст SteelAgent.handle: правила
   обычного ответа, вид/марка/размер по доказанным фактам. Проверить достаточность
   label/Characteristic до предложения расширения данных; жёсткая сортаментная
   схема этим аудитом не утверждена.
2. presentation.render/_item_text: компактность и упорядоченный показ устойчивых ID.
   Один порядок для formatter и display_numbers; не сортировать только готовые
   строки, оставляя GPT старые номера. Перестановка текста не должна переписывать
   originals, версию, provenance или коммерческие группы.
3. agent web_search + Reply.sources/Repository.history: отделить краткий список
   от полного сохранённого, сделать полный список доступным без нового поиска.
   Сейчас history передаёт текст, отдельного чтения последнего полного списка нет.
4. queue.finish_hook/deliver + safe_chunks + TelegramAPI.call: проверить безопасный
   native payload, сохранив прежнюю атомарность outbox и политику unknown.
   Код и очередная схема в этом этапе не меняются.

Будущие проверки: create/edit/undo/show/forward и обходы через custom/поиск;
смешанные виды, марки и составные марки, толщины 2/10, неизвестные размеры,
разные ГОСТы, повторы без консолидации, длинные строки, адресная правка после
перестановки, HTML-символы и источники. Не требовать единственного порядка видов.
RequestEngine.validate сохраняет coverage/evidence/уникальность/partition;
его sorted(members) проверяет состав, а не товарный порядок.
