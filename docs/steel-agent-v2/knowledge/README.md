# Экспертное обучение Steel Agent

Редакция №26, 18.10.2026, для review владельца. GitHub — постоянный источник;
переписка сама по себе не означает сохранение или утверждение знания.
Процесс задан владельцем в №26; детали шаблонов ещё допускают исправление.

## Три разных уровня

- [METAL_BASICS](METAL_BASICS.md): проверяемые технические факты с источником и
  применимостью. Предпочтение владельца не превращает его в нормативный факт.
- [BUSINESS_RULES](BUSINESS_RULES.md): отдельно утверждённые способы обработки;
  proposed / approved / superseded, область, исключения, история пересмотра.
- [Эталоны](cases/TEMPLATE.md): история конкретной заявки от исходника до
  утверждённого результата. Корректировка кейса не становится общим правилом.

[Программа](CURRICULUM.md) задаёт последовательность, [SESSION_STATE](SESSION_STATE.md)
хранит контрольную точку. Неполный справочник не запрещает обработку понятного товара.

## Работа с одной заявкой

1. Владелец присылает исходную заявку в первоначальном виде. Не просить его
   сначала составить правильную нормализацию. Для публикации использовать только
   материал, явно предоставленный владельцем именно для этого процесса.
2. ChatGPT читает актуальные источники ниже, самостоятельно нормализует **всю**
   заявку, сохраняет позиции, характеристики, количества и неизвестные параметры.
   Не придумывает ГОСТы, исполнение, массу или взаимозаменяемость.
3. Владелец комментирует ошибки. ChatGPT применяет поправки ко всем подходящим
   позициям/группам текущей заявки, сохраняя различия, и выдаёт **весь** результат
   заново. При неясной области поправки уточняет её, не расширяет молча.
4. Повторять до явного утверждения итогового кейса владельцем. Сохранять первую
   нормализацию и ход исправлений. Утверждение частичной правки не равно утверждению
   всего результата. Кандидаты в общие правила показывать отдельно для одобрения.
5. После явного утверждения сразу выполнить запись через подключённый GitHub.
   Отдельная сессия Codex для каждого кейса не нужна.

## Прямая запись через GitHub-коннектор ChatGPT

Репозиторий `dodger7360/uvm_ai_operator` публичный. Не извлекать материалы из
production SQLite, Telegram-истории или логов. Убрать неразрешённые персональные
сведения; при сомнении о публикации остановить запись и уточнить разрешение.

Для утверждённого knowledge-only кейса целевая ветка — `main`. Review содержания
проводит владелец в диалоге; разрешение на кейс не разрешает изменение кода,
deployment или новых общих правил. Сам фундамент №26 публикуется через feature/PR.

1. Прочитать Git ref `refs/heads/main` и сохранить **commit H** через GitHub
   `fetch` URL `https://api.github.com/repos/dodger7360/uvm_ai_operator/git/ref/heads/main`.
   Прочитать Git commit H тем же инструментом по `/git/commits/H`, взять tree SHA.
   `fetch_file(..., ref=H)` читает текущие правила, checkpoint и нужные кейсы.
   SHA файла из Contents — **blob SHA**, его нельзя использовать вместо H.
2. Выбрать свободный `CASE-YYYYMMDD-NNN.md` в `knowledge/cases/`; заполнить
   [шаблон](cases/TEMPLATE.md). Проверить исходные позиции/точность/согласования.
   Обновить SESSION_STATE: ID, группа, итог, связанные правила и следующий шаг.
   BUSINESS_RULES менять только для отдельно подтверждённых правил/редакций.
3. Создать одно Git tree через `create_tree`: `base_tree_sha` из H, элементы
   только изменённых knowledge-файлов (mode `100644`, type `blob`, content).
   Не строить дерево с нуля: остальные файлы должны сохраниться.
4. `create_commit(parent_sha=H, tree_sha=..., message=...)`, без других родителей.
   Затем `update_ref(branch_name="main", sha=новый_commit, expected_sha=H,
   force=false)`. Все части кейса и checkpoint публикуются **одним коммитом**.
5. Повторно прочитать ref и файлы по опубликованному SHA; сверить содержимое.
   Только после проверки сообщить ссылку `https://github.com/dodger7360/uvm_ai_operator/commit/<SHA>`,
   ID кейса, изменённые файлы и какие правила действительно утверждены.

Если HEAD успел измениться — перечитать новые файлы и согласовать изменения,
не перетирать чужую контрольную точку. Force запрещён. При неоднозначной ошибке
записи сначала проверить ref: не создавать дубликат уже сохранённого кейса.
Созданные blob/tree/commit без обновлённого ref ещё не означают сохранение в main.
Если прав/инструментов нет или защита ветки отказала — явно сообщить, что запись
**не выполнена**; не обходить защиту. Допустима отдельная ветка и PR с тем же
комплектом, но до merge это не актуальный checkpoint main. Указать владельцу
точное место сохранения и ожидающее действие. Локальный текст в чате — не backup.

В №26 проверены чтение ref, Git commit/tree и файлов через коннектор и права
репозитория. Запись реального CASE не выполнялась: утверждённого кейса ещё нет.
Права могут измениться; фактический успех каждой записи проверяется отдельно.

## Начало нового чата

Прочитай из актуального GitHub main карту документации, PRODUCT, DECISIONS,
PROJECT_STATE и NORMALIZATION. Зафиксируй commit H. По тому же H прочитай
knowledge/README, SESSION_STATE, BUSINESS_RULES, METAL_BASICS и эталоны текущей
группы, перечисленные в checkpoint. Учитывай только approved правила в их области;
proposed и superseded не применять как действующие. Назови прочитанные файлы и H.
Затем попроси исходную заявку либо продолжи следующий шаг checkpoint; самостоятельно
выдай полную первую нормализацию. Не требуй всю старую переписку и не заявляй
о восстановлении знаний без фактического чтения. При недоступном GitHub явно
обозначь, что актуальная версия знаний не прочитана.
