## Вывод и границы изменения

В найденном эпизоде на 100,602 с два последовательных SDK/API-вызова занимают
99,835 с. Повтор начат после EngineError, а не из-за таймера 180 или SDK retry.
Первый вызов сам занял 53,861 с: даже устранение второго не доказывает ответ до
30 секунд. Обычная корректная заявка уже проходит за один вызов; второго вызова
ради оформления нет. Конкретное условие первичного живого отказа не сохранено
в достаточно подробном безопасном коде, поэтому обоснованно удалить этот repair
или исправить именно причину отказа по имеющимся данным нельзя.

**Production-код не изменён.** Изменены только два тестовых файла и этот отчёт:
существующий sdk_transport получил необязательный callback для чтения HTTP request;
в существующий диагностический модуль добавлены два случая valid/repair. Нет новых
систем телеметрии, порогов времени/размера, production hooks или инфраструктуры.
Сохранены strict schema, evidence, Decimal, доступ, атомарность, очередь и SQLite.
Модель/reasoning, timeout, BR-007 и approved knowledge не менялись.

## Фактическое измерение сохранённого эпизода

Источник — существующий локальный telegram.log, только чтение. Из него извлечены
allowlisted поля steel_v2_model_call, steel_v2_validation, operation_complete и
queue-state. Пользовательские тексты, ответы модели и токены доступа не
извлекались/не переносились в отчёт; базы и новый реальный API не использовались.
Взята последняя операция с двумя вызовами и длительностью 90–110 с, затем следующая
операция с двумя вызовами. Без исходных payload нельзя независимо доказать точную
идентичность заявки инциденту; это сохранённый временной эпизод, соответствующий
ранее найденной последовательности create/partial → неуспешное подтверждение.

| Показатель | Длинная операция create/partial | Следующая операция edit/failed |
|---|---:|---:|
| От начала Executor после claim до operation_complete | 100,602316 с | 31,272939 с |
| SDK/API-вызов 1 | 53,861 с | 16,907 с |
| SDK/API-вызов 2 | 45,974 с | 13,767 с |
| Сумма SDK/API | 99,835 с (99,24%) | 30,674 с (98,08%) |
| Остаток: context/schema, plan validation, Engine, SQL, presentation, доставка и журналирование вместе | 0,767316 с | 0,598939 с |
| Input tokens 1 → 2 | 9156 → 17195 | 10793 → 16024 |
| Output tokens 1 / 2 | 5811 / 4533 | 1399 / 1262 |
| Reasoning tokens 1 / 2 | 3497 / 3034 | 1211 / 791 |
| HTTP attempts / SDK retries | 2 / 0 | 2 / 0 |
| Последнее состояние очереди | delivered | delivered (доставлен отказ) |

Длительность steel_v2_model_call — замер вокруг client.responses.create:
SDK-сериализация/HTTP/API/разбор ответа, а не чистое серверное inference.
WireCoordinatorPlan.model_validate и Engine выполняются после этого замера.
reason=null у обоих вызовов означает получение ответа; последующий отказ Engine
не превращается в HTTP/network error в этой метрике.

У первой операции от события завершения первого вызова до validation прошло
примерно 17 мс; от завершения второго до delivered — 634 мс. Это интервалы между
логами, включающие несколько действий, а не отдельные таймеры Engine/SQL/send.
Разложить остаток 0,767 с на Python, SQLite и Telegram по этим событиям нельзя.
Каждый из них лежит внутри общего остатка; приписывать все 100 с Python неверно.
Нельзя и назвать сам HTTP round-trip чистым временем модели.

### Пробелы текущих метрик

- **Ожидание в очереди не измерено.** operation() начинается в Executor после claim;
  у inbox нет timestamp admission/claim. served — билет справедливости, не время.
  Предшествующее ожидание/FIFO не входит в 100,602 с. Переполнение, занятые worker
  и unresolved unknown предыдущего события могут увеличивать пользовательское
  ожидание, но не объясняют измеренный интервал уже выполняющегося события.
- stage_ms.steel_v2_coordinate не является чистым API-временем: phase выставляется
  перед вызовом и не закрывается после него; туда попадают последующие wire/Engine,
  SQLite и delivery. routing в первой операции — 86,547 мс, но это также общий этап.
  Для суммы API надо использовать отдельные steel_v2_model_call.duration_ms.
- Нет раздельных duration для wire validation, Engine, commit и sendMessage.
  Нет сохранённого размера фактического HTTP body этого живого эпизода и нет
  метрики input_tokens_details.cached_tokens. Реальную пользу prompt caching,
  серверную очередь и вклад reasoning по этим данным выделить нельзя.
- В первой попытке create известны EngineError/request_validation и 5 извлечённых
  items. Код замаскирован общим request_validation; конкретную ошибку evidence,
  размерности или другого инварианта не называть доказанной.

## Количество вызовов и смысл repair

Кодовые основания: [SteelAgent.handle](../../../steel_agent_v2/agent.py:126),
[OpenAITransport](../../../steel_agent_v2/transport.py:652),
[построение запроса](../../../steel_agent_v2/transport.py:521),
[AttemptTransport](../../../steel_agent_v2/queue_runtime.py:30).

| Исход | Вызовы координатора | Причина / необходимость |
|---|---:|---|
| Корректный create, включая готовую интерпретацию «т т» | 1 | break после валидации/применения; форматирование локальное |
| Исправимый известный невалидный ответ | до 2 | Один repair с diagnostics/previous proposal; новый тест исправляет duplicate_characteristic и сохраняет одну версию |
| Два невалидных ответа | 2 | Без третьего вызова; отказ или проверенный partial fallback, атомарность сохраняется |
| SelectionError с предметным уточнением | 1 | Вопрос формируется локально, повторная генерация не нужна |
| HTTP 400/401/403/404/429/500, incomplete/refusal, неизвестный transport outcome | 1 | SDK max_retries=0; эти исходы не входят в цикл обычного structural repair |
| Доставленный replay одного update | 0 новых | durable dedup, без повторной отправки |

Структурный ремонт действительно может вернуть применимую заявку после известного
ответа: это доказано контролируемым bad → good. Это не оценка его успешности на
настоящей модели. Синтаксис JSON, локальные Pydantic ограничения и Engine-инварианты
различаются; strict JSON Schema не гарантирует evidence, соответствие исходнику,
полноту и Decimal-смысл. Нельзя заменить их одним доверием к strict.

Повтор того же HTTP-запроса не исправит ключ доступа, неподдерживаемую API schema,
неизвестный исход сети или отсутствующий пользовательский факт. Для первых трёх
слепого retry уже нет. Если typed binding отсутствует, repair не может создать
согласие пользователя из «да»; нужен безопасный предметный вопрос/поддержка связи,
а не выдуманный evidence. Но один EngineError сам по себе не доказывает, что
модель не сможет исправить неверный target/revision/структуру по текущему context.
Без кода конкретного отказа нельзя отключать весь класс repair.

Исследование массы по явному запросу использует дополнительные plan/search вызовы;
оно не является обычным create или форматированием. В измеренной операции
stage_calls содержит только coordinate: 2, web_search отсутствует.

## Настройки и потенциальные задержки

- timeout=180 передаётся в OpenAI.with_options, max_retries=0. В реально
  сериализованных offline request.extensions видны connect/read/write/pool=180.
  Это сетевые фазовые timeout, не sleep на 180 с, не SLA и не единый лимит операции.
  Две попытки могут суммировать длительности. Нельзя автоматически обрывать на
  30 с и считать неизвестный результат несуществующим.
- Runtime выбирает gpt-6-luna/high. Журнал подтверждает модель и reasoning-token
  usage, но эффекта смены effort не измеряет. Настройка high не менялась.
- Scheduler работает независимо от getUpdates(timeout=25), tick с коротким
  ожиданием 0,02 с; long polling не добавляет обязательные 25 с к уже принятой заявке.
  FIFO одного пользователя и ограничение worker сохраняются.
- queue.write использует busy_timeout=1000 мс; остальные Database.connection
  оставляют timeout sqlite3 по умолчанию. Конкуренция за writer потенциально
  задерживает этапы, но их сумма в выбранном исполнении меньше секунды.
- TelegramAPI.sendMessage использует timeout=45 с на сетевой вызов; многочастный
  ответ может требовать несколько отправок. В этом эпизоде доставка вместе со всей
  работой после последнего ответа укладывается в 634 мс. Это верхняя граница смеси
  этапов, не измеренная длительность sendMessage.
- TypingIndicator выполняет сетевые pulse в отдельном потоке, join ограничен
  0,05 с. Причины 100 с в этом механизме не найдено.

## Измерение фактически отправленного JSON

В двух новых офлайн-случаях callback HTTP MockTransport читает **len(request.content)**
после настоящего SDK serializer. Ни ограничения на bytes, ни assertions на
скорость не введены. Источник — пять синтетических труб из блока 4.1; active/history
перед create пусты. Repair получает дубликат уже существующей характеристики,
затем корректный план. Исходник, Decimal, один snapshot/version и receipt защищены.

| UTF-8 bytes | Первичный запрос | Repair |
|---|---:|---:|
| Полный фактически отправленный HTTP body | 36 906 | 78 891 |
| JSON-кодированное значение instructions | 9436 | 47 500 |
| JSON schema (без внешнего text.format envelope) | 13 129 | 13 129 |
| JSON-кодированное значение input (строка с вложенным JSON) | 14 156 | 18 077 |
| context как отдельное compact JSON-значение внутри input | 13 401 | 13 489 |
| previous_proposal как отдельное compact JSON-значение | 4 (null) | 2951 |
| diagnostics как отдельное compact JSON-значение | 2 ([]) | 31 |

Вложенные размеры нельзя повторно складывать с input: это его части, с другим
уровнем escaping/пробелов. Полный body — прямое измерение байтов, не len(str).
За две попытки передано **115 797 bytes**. Repair вырос на **41 985 bytes**;
38 064 bytes прироста приходится на instructions: plan_request при diagnostics
переключает компактную CREATE_INSTRUCTIONS на полную INSTRUCTIONS. Это основной
источник прироста в данном синтетическом случае. Повторяются schema и полный
context, включающий message/source_lines/knowledge; добавлены предыдущий ответ и
validation_repair. Это stateless новый POST, не передача только исправления.

Повторная передача действительно происходит при repair; её частоту в реальной
работе по одному эпизоду не оценить. Сами bytes не доказывают линейную задержку:
в живом эпизоде второй input крупнее по tokens, но ответ пришёл быстрее первого.
Пустая история синтетического create не репрезентативна для длинного диалога.
В живом repair input tokens выросли на 8039, но точный byte body не сохранён.

Локальный mock: valid operation=69,566 мс, один coordinate=2 мс; repair
operation=88,590 мс, coordinate=2+2 мс. Это только один измеренный локальный запуск,
без сетевой/серверной задержки, без warm-up/статистики. Он доказывает состав
запросов/число вызовов, но не скорость живого OpenAI и не верхнюю границу CPU/SQL.

## Почему production-оптимизация сейчас преждевременна

Нет доказанного лишнего вызова на корректном плане: он уже один. Удаление repair
потеряет рабочий путь восстановления; снижение timeout не ускорит завершённый
ответ; смена reasoning запрещена без измерений. Большая полная repair-инструкция —
измеренный кандидат на сокращение, но эквивалентность короткой инструкции по
качеству исправления не проверена. Офлайн bad → good не измеряет такой эффект:
good заранее задан. Сужать её и объявлять ускорение без оценки нельзя.

Минимальный следующий шаг — не переписывание агента, а сбор недостающих полей
через **существующие** emit/Trace/steel_v2_model_call/steel_v2_validation:

1. Коррелировать timestamp admission и claimed существующего queue-события, без
   новой SQLite schema; отдельно показывать ожидание пользователя и исполнение.
2. Измерить границы context/schema, wire validation, Engine, Repository.finish и
   delivery в существующем Trace; не использовать coordinate stage_ms как API SLA.
3. Дополнить существующий безопасный request hook агрегатным числом bytes и
   метрику usage — cached input tokens, если они возвращены. Не писать payload.
4. Разобрать allowlisted код первичного EngineError и исходы repair на обычном
   согласованном корпусе. Пока этого кода в инциденте нет, фиксировать пробел.
5. После отдельного согласования реальных измерений сравнить долю успешного
   первого ответа, p50/p95 длительности каждого вызова, успешность repair и tokens.
   Затем точечно исправлять подтверждённую причину отказа/сокращать repair scope,
   сохраняя те же инварианты. Новые платные испытания этим PR не разрешаются.

create/partial → typed clarification и pending → append остаются отложенными
production-задачами. Пожелания PR #32 о target-specific evidence, consent и
revision/user scope сохраняются; здесь ни один из этих переходов не реализован.
