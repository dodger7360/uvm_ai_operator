## 1. Как завтра начнётся первая заявка

Владелец присылает первоначальный текст, явно предоставленный для этого процесса.
ChatGPT читает актуальный main, требования, знания и checkpoint; самостоятельно
нормализует всю заявку. Владелец указывает ошибки; поправки применяются ко всем
подходящим позициям/группам текущей заявки, после чего выдаётся весь результат.
Владелец не готовит правильную заявку заранее. Никаких реальных исходников в №26
не поступило: approved-кейсов и новых approved экспертных правил **0**.
[README](../knowledge/README.md) и [шаблон](../knowledge/cases/TEMPLATE.md) готовы для review.

## 2. Как эталон сохраняется в GitHub

После явного утверждения всего кейса ChatGPT напрямую через GitHub-коннектор читает
ref main = H и tree H, текущие файлы по H. Создаёт CASE, меняет SESSION_STATE и,
только при отдельном утверждении, BUSINESS_RULES. Одно дерево на основе H, один
commit с parent H, обновление ref без force с expected_sha=H, повторное чтение.
Вернуть ссылку на проверенный коммит; обсуждение в чате не означает сохранение.

Обычная цель для утверждённой knowledge-only записи — main; это не разрешает
изменение кода или deployment. Если защита/права запрещают запись, сообщить об
ошибке; возможный PR явно обозначить ожидающим merge, не считать main обновлённым.
При гонке или неоднозначной ошибке сначала перечитать ref, не перетирать изменения
и не создавать дубликаты. Отдельный Codex на каждую заявку не требуется.

В №26 выполнено реальное чтение через коннектор: репозиторий, файл PROJECT_STATE,
Git ref main, Git commit/tree; доступны операции create_tree/create_commit/update_ref,
API репозитория сообщает права записи. Это **не** тест записи утверждённого CASE:
такого материала ещё нет. Возможность конкретной записи проверяется по её результату,
а не по старому флагу прав. Файловый blob SHA не подменяет commit H.

## 3. Как продолжит новый чат

[SESSION_STATE](../knowledge/SESSION_STATE.md) хранит группу, CASE, редакции правил,
ограничения и следующий шаг. Новый чат читает GitHub по одному актуальному H:
основные документы → README/checkpoint → approved релевантные правила и кейсы
группы, предметные основания. Называет действительно прочитанные файлы и SHA;
вся прежняя переписка не нужна. Без чтения не заявляет о восстановленной памяти.
Сейчас checkpoint честно фиксирует отсутствие первого кейса.

## 4. Что уже есть в Metal Reference

metal_reference/schema.py, ingest_armatura_price.py, ingest_armatura_a3.py,

## 5. Фактические препятствия первой интеграции в Telegram

- Ещё нет минимального проверенного набора первой группы: ни нового утверждённого
  CASE, ни отдельно согласованного общего экспертного правила.
- Нет runtime-загрузчика нового каталога, отбора approved/релевантности и фиксации
  версии знаний. Документационный файл сам по себе не меняет работающий бот.
- Сохраняются структурные отказы, включая диагностированный duplicate_characteristic,
  неполные характеристики и многословный вывод. №26 их не исправляет и не объявляет
  покрытыми новыми эталонами. Исходные инварианты не ослабляются.
- Нельзя без проверки считать legacy Reference независимым источником или включать
  его старые нормализующие зависимости. Полный справочник не является prerequisite.

## 6. Конкретное следующее функциональное задание

После первого минимального approved-набора группы подключить локальный пакет к тому
же Steel Agent v2/GPT-6 Luna High: выбор только утверждённых и применимых редакций,
воспроизводимая версия Git SHA пакета, загрузка из релиза без GitHub на каждую заявку.
Проверить утверждённые и пограничные примеры, отсутствие выдуманных характеристик,
полноту source references, Decimal, версии/undo, права, FIFO и идемпотентность.
Мешающие структурные сбои исправить в той же ближайшей функциональной работе,
не заменять это одним добавлением знаний в промпт. Не возвращать старый нормализатор,
не создавать второй AI, RAG, embeddings, новую БД или инфраструктуру.

[CURRICULUM](../knowledge/CURRICULUM.md) начинает с отдельных групп, после нескольких
переходит к смешанным. Не ждать всего сортамента. Цель функциональной нормализации
за максимум 14 дней от T0 и трёхмесячный план [ROADMAP](../ROADMAP.md) сохранены;
№26 не назначает новый T0 и не начинает реализацию автоматически.
