## A. Последовательность и граница безопасного изменения

Подтверждено кодом и Event-тестом настоящего `run_bot`: синхронный dispatch
ожидает GPT и доставку, затем сдвигается offset. Пока fake GPT пользователя A
заблокирован событием, B не начинает работу, offset остаётся прежним. После
освобождения A выполняется B. Параллельность операций этого цикла сейчас — одна.

Существующие begin/finish обеспечивают durable inflight на пользователя,
дедупликацию завершённого события и атомарность заявки/версии/истории. Но inflight
не содержит стадии внешнего вызова и результата; ожидающей очереди нет. Отправка
Telegram выполняется после commit, без отдельного журнала доставки частей.
Общий offset находится в legacy SQLite, состояние операции — в v2 SQLite.

Подтверждено двумя дополнительными тестами:

- После повторного открытия незавершённый claim сохраняется, GPT повторно не
  вызывается; пользователь получает busy, автоматического восстановления нет.
- При ошибке sendMessage успешная мутация остаётся единственной; повтор update
  использует сохранённый ответ без GPT. Но достоверного receipt доставки в БД нет.

Требуются добавочная схема хранения, транзакционная запись outbox, новые стадии
восстановления и gate отката. Это существенное изменение безопасности/хранения,
а не локальная замена dispatch на thread pool. Применено прямое условие №15:
«сначала подготовить технический проект и остановиться для согласования».

Проект: [CONCURRENT_QUEUE_DESIGN.md](../CONCURRENT_QUEUE_DESIGN.md).
Предложены один poller, три конфигурируемых execution worker, FIFO по пользователю,
ограниченный inbox и backpressure. Inbox и receive watermark фиксируются в v2
до повышения legacy offset; внешние эффекты имеют отдельные устойчивые стадии.
Unknown GPT/delivery не повторяются автоматически. Никаких гарантий exactly-once
внешних API не заявлено. Новая параллельность, drain и recovery пока не достигнуты.

Database уже создаёт независимые короткие SQLite connections. Запросы GPT не идут
внутри write transaction. Метрики транспорта используют lock, диагностика —
ContextVar. Для будущих worker предложены отдельные SDK-клиенты; безопасность
совместного клиента не объявляется доказанной. Гонки access/revoke между двумя
SQLite требуют отдельного протокола и тестов. Supervisor/stop сейчас кооперативны,
не убивают операции; существующий timeout по умолчанию 180 секунд.

## B. Четыре балки

Буквальный исходник сохранён в `tests/fixtures/steel_v2_015_beams.txt` без замены
строк подготовленными RequestItem. Проверка идёт через настоящий Telegram adapter,
SteelAgent, RequestEngine, formatter и временную SQLite, с контролируемым plan
transport. Сетевой SDK payload в этих новых воспроизведениях не моделируется;
существующие wire/HTTP-тесты проверены отдельно в общей целевой регрессии.

Корректный GPT-план проходит **без исправления приложения**:

| Профиль | Количество, т | Марка | Стандарт |
|---|---:|---|---|
| 20Ш2 | 10,700 | С355-5 | 35087-2024 |
| 30Ш2 | 186,698 | С355-5 | 35087-2024 |
| 40Ш2 | 127,097 | С355-5 | Р 57837-2017 |
| 45Ш2 | 56,669 | С355-5 | Р 57837-2017 |

Четыре исходные/актуальные позиции, четыре отдельные группы, точный Decimal итог
**381,164 т**. Исходный текст, профили, марки и стандарты сохранены.

`RequestEngine.validate` выдаёт empty_source_range:s2, если диапазон s2 внутри
оригинала после strip пуст. Модель может создать лишний служебный record на
переносе строки; это воспроизведено. Также неверные смещения могут указывать
на whitespace вместо товарного текста: отдельный отрицательный тест проверяет
такой product record. Поэтому отсутствие сохранённого реального отклонённого
плана не позволяет доказать, какой из механизмов вызвал живой отказ.

Существующий однократный repair получает диагностический код и прежний план.
Если второй план корректен, четыре балки сохраняются с точным итогом. Если он
повторяет ошибку, старая заявка неизменна, полный исходник балок сохранён в turn,
claim освобождён. Пропуск строки, двойная позиция и плохой product range остаются
отказами; защитные проверки не ослаблялись. Служебный код сейчас попадает в текст
ответа — подтверждённый пользовательский дефект.

Проект предлагает строго ограниченную обработку только нессылаемых служебных
whitespace records с последующей полной валидацией. Это предложение, не патч.
Живое качество генерации source ranges и исправление конкретного случая не доказаны.

## C. «А балки?» → «Добавь»

Воспроизведена цепочка: исходная заявка → два отклонённых beam-плана → корректный
read-only ответ про балки → invalid edit_request без допустимых операций дважды.
AgentPlan.only_intended_mutation выдаёт `schema::value_error`. Старые данные и
ревизия сохраняются, а отклонённый исходник доступен в bounded history следующего
вызова. После reopen SQLite заявка также неизменна; второй пользователь её не видит.

Точная структура живого плана, породившего value_error, неизвестна. Такой код может
обозначать разные нарушения validator; нельзя утверждать, что тест восстановил
реальный ответ GPT. Достоверно: операция append/add отсутствует — разрешены только
set/regroup/undo; edit с extraction запрещён. Текущая инструкция явно не объясняет
поведение при неподдерживаемом добавлении после отказа. Сырые коды validator
добавляются к пользовательскому сообщению в agent.py.

Показан работающий безопасный путь существующего clarify: сообщить об ограничении
добавления без изменения заявки. Нужны минимальное уточнение GPT-инструкции,
явное различение отклонённого текста и активных позиций и удаление технических
кодов из пользовательского вывода. Ни keyword router, ни create вместо append
не предлагаются. Новый append RequestEngine требует отдельного согласования.
Код этого поведения в данном проходе не изменён.

- 10 новых диагностических тестовых случаев, все проходят. Это characterization
  текущих дефектов, **не** приёмка их исправления.
- Целевой запуск v2, prelaunch, Windows, wire schema, API diagnostics, UX/search,
  search runtime, supervisor, access, reasoning high и новых воспроизведений:
  **263 passed**, 14,44 s.

- Всего в этих двух запусках **319 passed**. Это другой перечень модулей, чем
  прежние 283; сравнение количества напрямую не является регрессией.
  Отдельного счётчика subtests эти запуски не вывели.
- Первое выполнение нового синхронного теста выявило дефект тестового access stub
  (отсутствовал repository); исправлена только фикстура, повтор прошёл.
- В этих проверках нет нагрузочного доказательства новой очереди/FIFO/drain,
  поскольку реализация остановлена до согласования. Полный legacy pytest и платные
  API не запускались. Mock-планы не подтверждают живое понимание GPT.
