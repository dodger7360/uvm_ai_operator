19.10.2026. Кандидат для review, без merge/deployment и без живых API-вызовов.
Ветка: `feature/steel-agent-v2-display-sorting`. Полный HEAD и ссылка на PR

## Основа и подтверждённая причина прежнего порядка

Перед началом GitHub API подтвердил merged=true для PR №17, его head точно
`e06828943365f6800639d85d79afcba890978703`, merge/main:
`205c1f47dc83db0e3da43b45f320cd737729f671`. Создан отдельный Windows worktree
от этого коммита. Main не изменяется. Production в этом этапе не инспектировался;
его последний подтверждённый SHA по владельцу/№32 — 818b18fc, не новое наблюдение.

Прежний display_order просто разворачивал commercial groups/item_ids. Render
использовал такой же обход; устойчивой классификации по виду и размерных ролей
в свободных Characteristic не было. Коммерческие группы не доказывают вид,
полную марку или взаимозаменяемость. Прежняя карта BR-010 сохранялась правильно,
но не содержала нового товарного порядка BR-003–005.

## Изменения

1. `contracts.py`: DisplayLayout содержит DisplayItem (вид, ссылка на поле полной
   марки, размерные ссылки), DisplayDimension (роль, имя поля, единица и при
   необходимости буквальный разделитель/номер компонента), scoped DisplayGradeOrder.
   AgentPlan.display_layout приходит **тем же** GPT-вызовом; Reply.display.layout
   сохраняет ссылки рядом с уже существующим порядком ID. Отсутствующие поля
   совместимы со старой историей; layout=None не меняет сериализацию старого receipt.
2. `transport.py`: текущий единственный координатор инструктирован возвращать
   семантические роли без выдумывания значений и без изменения коммерческих groups.
   Частный Ст3 перед 09Г2С-15 относится к разрешённому примеру. Иного рейтинга
   сталей и фиксированного порядка видов нет. Дополнительного model call нет.
3. `presentation.py`: display_order группирует вид → **полная текущая** марка,
   затем сравнивает числовые размерные ключи Decimal. Для sheet Python закрепляет
   первичность роли thickness, даже если модель прислала width первой. Без
   однозначной ссылки на толщину ширина не подменяет её. Вторичные сравнимые
   роли допустимы; одинаковые ключи стабильны, товарные строки не объединяются.
   Размер читается из текущего значения/компонента целиком, не из первой найденной
   цифры. Индекс 20Ш2 не становится размером 20. Стандартные длины сравниваются
   точным десятичным масштабированием, исходные значения не изменяются.
4. `agent.py`: normalized/forward и сохранённая карта вычисляются из одной
   display_order. После edit/undo ссылки читают новые значения; show старой
   заявки может получить layout тем же запросом, без новой версии товара.
   Прежний Repository.last_display проверяет user/request/revision/полный состав
   ID и delivered для durable события. Его код не менялся.
5. У нормализованного ответа нет нумерации, заголовков групп и итогов; все строки
   самостоятельные. Custom/original/totals не заменяют карту последнего полного
   normalized/forward. Коммерческий explanation остаётся отдельным подробным видом;
   этот этап не исправляет все прежние расхождения BR-001/006/007 в иных ответах.

Неполные/ошибочные ссылки классификации не удаляют товар. Дубли hint для одного
ID не выбираются произвольно; чужой ID игнорируется. Неизвестные марки/размеры
не заполняются из памяти. Без layout сохраняется прежний безопасный порядок,
а не выдуманная классификация. Неподдерживаемые числовые записи/несравнимые роли
остаются несортируемыми, при этом полные товарные строки сохраняются.
Стабильность равных/неизвестных ключей — техническое поведение, не новое
предметное правило порядка видов или неизвестных размеров.

## Обнаруженное ограничение общей единицы в эталоне

Владелец прямо разрешил публикацию исходника семи листов в
[фикстуре](../../../tests/fixtures/steel_v2_stage3_approved_sheets.txt).
Единица задана только общей шапкой «Всё в тоннах». Прежний RequestEngine требовал
unit_text в товарной строке и unit==unit_text. Подставлять единицы в оригинал или
считать букву «т» внутри «ст.» доказательством единицы недопустимо.

Минимальное совместимое дополнение: Item.unit_source_id указывает **явно** на
предшествующий header, unit_text буквально и целым словом присутствует в нём,
стандартное обозначение массы проверяется по существующим каноническим единицам
г/кг/т. Добавлена форма «тоннах». Несовпадение, отсутствующий/поздний header,
неподтверждённый текст, отсутствие самой единицы — отказ. Число не пересчитывается.
У старого пути без unit_source_id проверки остались прежними. recovery.py сохраняет
этот header при независимой проверке частичного плана. originals и source ranges
сохраняются; новые таблицы, миграция SQLite, парсер сортамента не нужны.

Python проверяет ссылки и буквальные доказательства, но не доказывает семантически
любую область действия шапки: это остаётся ответственностью того же GPT и предметной
приёмки. Новых отраслевых правил ГОСТов, стали или расчётной массы не добавлено.

## Эталон, адресация и сохранность

Для исходных i1…i7 получен порядок **i4, i5, i3, i1, i6, i7, i2**:
Ст3 — толщины 10, 16; 09Г2С-15 — 8, 10, 12, 16, 20. У каждой позиции 40 т.
Все семь ID, исходник, записи источников, original values и коммерческая группа
сохранены; ГОСТы не добавлены. Текст совпадает с утверждёнными строками, без
необязательной пустой строки между марками. Общий тоннаж не выводится.

После команды по третьей показанной строке размер i3 меняется с 8 на 22 мм,
товар переходит в конец своей марки. Теперь третья строка — i1, и следующая
команда «позицию 3» меняет **i1**, не прежнюю i3. Проверены отдельные версии,
undo, повторный показ, reopening Repository, одинаковые item_id у разных
пользователей, групповая правка марки и атомарный отказ ошибочной группы.

Сортировка/readonly show не создают товарных изменений. Реальная правка проходит
старый RequestEngine с evidence и expected revision, создаёт одну версию.
История сохраняет прежние версии/originals; undo восстанавливает факты новой
версией. Layout и item_ids — в Reply истории, текст — в прежнем outbox, одной
транзакцией Repository.finish. Повтор event_id возвращает сохранённые text/map,
не вызывает GPT и не пересортировывает старый receipt по новым данным.
Delivery_unknown не считается последним показом и не повторяется автоматически.

## Файлы и границы публикации

Исполняемые модули: contracts.py, presentation.py, agent.py, transport.py,
engine.py, recovery.py внутри steel_agent_v2. Добавлены тест и разрешённая фикстура.
Актуализированы BUSINESS_RULES/SESSION_STATE, NORMALIZATION, DECISIONS,
PROJECT_STATE, TELEGRAM_PRESENTATION, TESTING и этот отчёт.

GPT-модель, зависимости, supervisor, Task Scheduler, .env, старое ИИ-ядро.
Ни merge, ни deployment, ни платные вызовы, ни Telegram-сообщения не выполнялись.
HTML, компактные источники, справочные массы, append не входят в этот этап.
Живая классификация/сортировка GPT и Telegram ещё не приняты владельцем.

Кандидат предназначен для review. Следующее действие возможно только по отдельному
указанию; main и production самостоятельно не обновляются.
