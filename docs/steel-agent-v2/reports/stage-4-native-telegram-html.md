# Этап 4 — нативное оформление Telegram, BR-006

19.10.2026. Feature-ветка `feature/steel-agent-v2-native-html`, кандидат для review.
Merge, deployment и живые OpenAI/Telegram-вызовы не выполнялись. Полный SHA и PR
сообщаются после публикации; версия отчёта — содержащий его Git-коммит.

## Основа и прежняя проблема

GitHub API подтвердил merged=true для PR №16–18. Отдельный Windows worktree создан
от origin/main `0c77382b25eb8d736effb27127182e18dc265448` со слитым PR №18.
Прежний finish_hook записывал chat_id/text после plain safe_chunks. Deliver
пересылал payload без parse_mode: Markdown/HTML модели оставались видимым текстом.
TelegramAPI не умеет определять происхождение произвольной строки, поэтому
глобальное включение HTML было бы небезопасно.

Проверена официальная документация: [sendMessage](https://core.telegram.org/bots/api#sendmessage)
поддерживает HTML parse_mode и 1–4096 символов после разбора entities;
[HTML style](https://core.telegram.org/bots/api#html-style) требует поддержанных
тегов и экранирования `<`, `>` и `&`. Реальный sendMessage не выполнялся.

## Минимальная стратегия

Новый telegram_format.py — адаптер представления внутри существующего пути,
не новая система отправки. Reply.presentation хранит типизированные текстовые
фрагменты с allowlisted marks и optional URL. Это поле приложения, не контракт
нового GPT-вызова и не сырой HTML. Reply.text сохраняется для истории без изменений.
Если presentation отсутствует, новый payload экранирует прежний текст буквально.
При чтении старых Reply поле None не сериализуется — byte-совместимость проверена.

Перед разбором prose буквальные исходные строки, актуальные товарные строки,
значения/raw характеристик и сообщения пользователя временно защищаются непрозрачными
маркерами. Они восстанавливаются как текст до записи Reply. Оригинальный вид
целиком буквальный. Сортировка, IDs, оригиналы, количества, ГОСТы, provenance и
версии не меняются. Значимые `*`, `<`, `>`, `&`, кавычки и обратные слеши в данных
не удаляются; замена всех звёздочек/скобок регулярным выражением не применяется.

Поддержанный Markdown: **bold**, заголовки #…######, inline/fenced code и
именованные ссылки. Из HTML распознаются сбалансированные b/strong, i/em,
code/pre, h1…h6 и a. Все теги строятся заново приложением как b/i/code/pre/a;
входные атрибуты, кроме отдельно проверенного href, не переносятся.
HTML entities декодируются один раз как данные и не становятся вторым входом
Markdown/HTML. Соседние одинаковые фрагменты объединяются без повторного разбора.
На выходе текст/атрибуты экранируются; буквально написанное `&amp;` остаётся
видимым `&amp;`, а не ошибочно превращается в амперсанд.

Для URL повторно используется safe_source с дополнительным отказом при control/DEL,
обратных слешах, кавычках и угловых скобках. javascript/data/file/tg, credentials
и секретоподобные query не становятся кликабельными; остаётся название без target.
Это синтаксическая проверка http(s), не доказательство безопасности или достоверности
сайта. При поиске все прежние Reply.sources сохраняются; в доставке они становятся
кликабельными названиями (title, уже равный URL, не переименовывается автоматически).
Отбор 1–2, полная дедупликация inline/приложенных ссылок,
новый поиск и пользовательская выдача полного списка BR-007 здесь не реализуются.

## Durable outbox и длинный текст

Путь сохраняется: SteelAgent.handle → Repository.finish → DurableQueue.finish_hook
→ DurableQueue.deliver → TelegramAPI.call. Единственное изменение finish_hook —
запись готовых JSON payload с chat_id/text/parse_mode=HTML вместо plain text-частей.
Это та же транзакция заявки, версии, истории, claim и всех частей ответа.
SQLite DDL/schema, миграции, права и механизмы recovery не менялись.
Deliver не форматирует и не пересоздаёт payload. Старый outbox без parse_mode
доставляется ровно в прежнем виде; автоматической миграции или повторной отправки нет.

Разбиение работает по видимому тексту до экранирования. Бюджет по умолчанию —
консервативные 3200 UTF-16 единиц, максимальный параметр — 4096. Предпочитаются
целые строки; слишком длинная строка сохраняется во всех частях без потерь.
Кодовые точки не разрезаются; обычные combining/ZWJ/flag emoji сохраняются вместе.
После разбиения каждая часть самостоятельно закрывает/открывает marks и ссылку;
теги и entities никогда не разрезаются. Длинная подпись ссылки может продолжаться
следующим самостоятельным `<a>` с тем же проверенным target.
Plain safe_chunks для старых путей не менялся; HTML не включён глобально в API.

Execution_unknown/delivery_unknown не очищаются, автоматически не повторяются.
При неизвестной второй отправке первая receipt сохранена, вторая quarantined,
третья остаётся pending и не отправляется после restart. Все существующие проверки
доступа между частями и пользовательская изоляция сохранены. Повтор update_id
не вызывает новый GPT и не создаёт повторных outbox-отправок в production queue.
Изолированный прямой адаптер v2 использует тот же formatter, не становится новым
production polling-путём. Административные plain text-уведомления не переводятся
на глобальный HTML-режим.

## Границы и файлы

Заключительные проверки: 14 изменённых/новых файлов, 69 локальных Markdown-ссылок,
Python AST и git diff --check проходят. Паттернов реальных API-ключей/Telegram-токенов
в изменениях не найдено; production-данные не читались и не копировались.
AST действующих функций queue (кроме finish_hook) и presentation (кроме нового
literal_fragments) совпадает с базой: deliver/recovery/scheduling и порядок товаров
не переписаны. Защищённые предметные/Windows/dependency-файлы не изменены.
Remote main при заключительной проверке остаётся 0c77382b.

Неизвестная/повреждённая/неоднозначная разметка сохраняется безопасным буквальным
текстом. Поэтому неподдержанные символы могут остаться видимыми: удалять их как
«мусор» без доказательств нельзя. Markdown-экранирование снимается только внутри
распознанной конструкции; пути и неоднозначные backslash-последовательности
не очищаются глобально. Вне защищённых данных поддержанная конструкция считается
оформлением; смысл любого произвольного символа по одному тексту не доказуем.
Чрезмерная combining-последовательность длиннее одного сообщения делится по
кодовым точкам без потери текста. Это не универсальный Unicode grapheme engine.
Старые уже сохранённые plain payload не преобразуются в HTML при recovery.
Живое отображение в Telegram и реальное поведение GPT этим этапом не подтверждены.
