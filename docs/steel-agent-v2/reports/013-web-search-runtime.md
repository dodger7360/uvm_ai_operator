# Отчёт Codex №13 — Web Search runtime и контекст отказа

Статус: **NEEDS LIVE DIAGNOSTICS**. Подготовлены проверенные офлайн исправления
запроса/контекста и диагностика; Web Search работающим не объявляется.

## Источники и исходное состояние

База/проверенный production SHA: `3e7be5fe9ec2efe6251e6f30a31f94eb2580c81b`.
Отдельная ветка: `feature/steel-agent-v2-search-runtime`. Windows, Python 3.13.15,
OpenAI SDK 3.19.2, Pydantic 2.13.5. Прочитаны существующий локальный отчёт №12,
безопасные поля соответствующего диагностического события, код и установленный SDK.
Production Git чистый, остановок/перезапусков/изменений данных не выполнялось.

Официальные источники:

- [Web Search: output и citations](https://developers.openai.com/api/docs/guides/tools-web-search)
- [Responses: max_tool_calls](https://developers.openai.com/api/reference/cli/resources/responses/methods/create)

Первый описывает отдельные tool actions и итоговое message, источники и annotations.
Второй определяет предел общей суммы built-in вызовов в Response: дальнейшие
попытки сверх предела игнорируются. Это же явно документировано в установленном
SDK responses.py. В ResponseFunctionWebSearch.status перечислены required
completed/in_progress/searching/failed/incomplete. Missing не является ещё одним
успешным состоянием; мягкое SDK-десериализование не доказывает допустимость ответа.

## Что известно о живом отказе

Сохранены tool_calls=2, source_count=13, provider_count=0, reason=tool_incomplete,
request ID `req_8f63f7777a2043249a6add5504926810`. Вызов API прошёл до локальной
проверки. Из текущего _call следует status Response=completed: иначе управление
не достигло бы этой ветки. Сам response_status отдельно в старом событии не записан.

Не сохранены статусы отдельных вызовов, их action.type, наличие/статус финального
message и наличие output_text. Их нельзя восстановить или выдумать. Из условия
all(status == completed) известно только, что хотя бы один вызов не соответствовал
completed: он мог быть незавершённым, отсутствующим или иным. 13 безопасных ссылок
не доказывают завершение поиска и корректность финального ответа.

## Дефекты и исправления

1. Запрос ограничивался max_tool_calls=1, хотя задача требует многошагового поиска.
   Этот предел удалён. Он документированно ограничивает обработку дальнейших
   действий и мог помешать второй операции, но причинная связь с конкретным старым
   ответом не доказана. Серверные defaults не выдумываются. Клиентских циклов и
   повторов не добавлено: один search SDK вызов, max_retries=0 и timeout=180 прежние.
2. Проверялся агрегат output_text без самостоятельного доказательства завершённого
   итогового message. Теперь текст и annotations берутся только из завершённых
   assistant messages после последнего tool call. Отсутствие такого message,
   пустой текст и неизвестные статусы имеют разные безопасные причины отказа.
3. Прежняя диагностика сворачивала все статусы в один bool. Теперь сохраняются
   allowlisted response_status, первые 32 пары status/action с флагом усечения,
   message_statuses, message_present, has_output_text, final_message, source/feed
   counts, request ID, search_performed/tools_completed/usable. Числовой HTTP status
   сохраняется при API-ошибке; успешный HTTP код не придумывается. Нет запросов,
   ответов, URL, query, tool IDs и произвольных исключений в новых полях.
4. last_search не выделял непосредственный контекст предыдущего хода. Добавлен
   previous_operation intent/status из существующих turn rows и готовое безопасное
   last_search_explanation. Системная инструкция трактует короткое «Почему?» после
   failed web_search как answer_question/view=search_status, без повторного поиска.
   После другой операции GPT должен объяснять её. Regex-маршрутизации нет.

### Что намеренно не ослаблено

Успешный многошаговый ответ с несколькими completed actions проходит. Смешанные
completed+failed/incomplete/searching/in_progress и missing-status ответы пока
отклоняются: документация не даёт оснований автоматически объявлять их полностью
подтверждёнными. Требование all-completed было консервативной политикой, а не
доказанным нарушением SDK. Его ослабление без статусов реального ответа было бы
спекуляцией. Новые логи позволят пересмотреть конкретный случай по фактам.

## Тесты

До патча: **19 failed, 3 passed** в новых случаях — предел запроса, отсутствующая
диагностика/контекст и отсутствие проверки финального message воспроизведены.
Некоторые исходные status-matrix случаи уже корректно отклонялись; тесты падали
на недостающей диагностике, а не на необходимости разрешить незавершённый поиск.

Добавлены 24 случая с настоящим SDK/mock HTTP и временной SQLite: одиночный и
многошаговый completed поиск; все документированные промежуточные/ошибочные
статусы, missing status; неполный Response; отсутствующий/незавершённый/ранний
message; пустой текст; annotations/action.sources/weather feed; unsafe URL;
sanitized metadata; «Почему?» после отказа и другого разговора после reopen;
повтор объяснения без поиска; только явно запрошенный новый поиск. Допустимые
tool call структуры дополнительно валидируются установленной SDK-моделью.
Контролируемые планы проверяют исполнение и контекст, а не живую классификацию GPT.

Полная целевая регрессия: **283 passed, 20 subtests passed** (результат проверен
перед коммитом). Включены v2, Telegram, wire schema, API errors HTTP 400–500,
SQLite/history/access, Windows runtime и high-регрессии. Старый короткий mock
message дополнен обязательными полями SDK; проверки небезопасных ссылок сохранены.
Никаких платных вызовов или production SQLite в тестах. git diff --check пройден.
