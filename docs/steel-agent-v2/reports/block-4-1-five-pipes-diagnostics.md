## Границы доказательства

Новый [модуль](../../../tests/test_steel_agent_v2_five_pipes_diagnostics.py)
использует существующие `sample`, `rig`, `admit`, `Executor`, `sdk_transport` и
проверки Telegram HTML/outbox. Новая инфраструктура не добавлена; новый модуль
включён в current через существующий test_suite_inventory.py.

Путь: Telegram update → production admission/claim → Executor/AttemptTransport →
OpenAI SDK HTTP serializer → HTTP mock → WireCoordinatorPlan/AgentPlan →
SteelAgent/Engine → настоящая временная SQLite → outbox → fake sendMessage receipt.
Алгоритмы, queue, Engine, Repository и commit/delivery hooks не подменяются.
Reopen означает новые Database/Repository/DurableQueue с recover над тем же файлом;
история/уточнение из памяти не копируются. Остановка ОС/процесса здесь не имитируется.

Все пять строк, числа, вопросы и ответы модели синтетические. Существующие
031_clarification_mass проверяют типизированное уточнение и SDK отдельно;
queue/telegram_html — доставку и receipts. Точного воспроизведения перехода
create/partial с вопросом о повторённой единице через весь путь в v2 не найдено.
Legacy fixtures с реальными заявками не переносились в новый тест или отчёт.
Точный исходный ответ модели инцидента в исследованных v2 fixtures отсутствует;
совпадение конкретного нарушенного условия живого инцидента не установлено.

Mock заранее выбирает намерение, позиции и значения. Он не доказывает понимание
«т т»/«да», истинность отраслевых фактов или достижение 30 секунд. Проверка strict
схемы использует существующий локальный supported-profile helper, не API сервера.

## Разделение причин

1. **Неверный план модели.** В синтетическом воспроизведении «да» первый edit
   с evidence «т» не имеет ссылки на сохранённое уточнение. Это реальный отказ
   [Engine.edit](../../../steel_agent_v2/engine.py:404):
   `edit_evidence_not_in_message`. Диагностическое событие: EngineError,
   request_validation. Ответ получен; это не сетевой timeout.
2. **Wire/Python контракт.** Второй ответ содержит пустые operations. Установленный
   SDK получает completed HTTP response; затем WireActionPlan наследует
   [AgentPlan.only_intended_mutation](../../../steel_agent_v2/contracts.py:234)
   и отклоняет edit. Событие: ValidationError, structured_response. Это локальная
   семантическая валидация wire-ответа, не доказательство ошибки SDK-сериализатора
   или отказа OpenAI принять JSON Schema. Тест проверяет две известные попытки.
3. **Представление уточнения.** В корректном create/partial вопросы — строки
   RequestSnapshot.questions. [SteelAgent](../../../steel_agent_v2/agent.py:327)
   создаёт PendingClarification только для отдельного clarify. После reopen
   текст вопроса есть в истории/active, но typed binding отсутствует. Контекст
   не потерян целиком; отсутствует адресная связь для подтверждения.
4. **Недостающая возможность контракта.**
   [WireCreatePlan](../../../steel_agent_v2/wire.py:43) не имеет clarification;
   внутренний AgentPlan тоже разрешает proposal только для clarify. Красный тест
   передаёт proposal явно, чтобы не требовать от Python понимания текста вопроса.
   Его ответ намеренно не соответствует сегодняшней схеме. Это тест отсутствующей
   возможности для 4.2, не утверждение, что данный ответ допустим сейчас или был
   получен в инциденте. Fallback восстанавливает товары, но связь теряется.
5. **Очередь/SQLite/доставка.** В проверенных цепочках дефект не воспроизведён:
   committed/delivered и message_id сохранены, pending-source не подменяет active,
   replay не повторяет API или sendMessage, typed clarification переживает reopen.
   Это не исчерпывающая аттестация отказов питания/внешних API.

Повторённое «т т» Python сам по себе не требует подтверждать. Лишний вопрос при уже
известной единице зависит от выбора модели; такой выбор здесь задаётся mock.
Нужно отдельное model evaluation, а не новый парсер русского языка.

## Что исправлять в 4.2

- Согласовать и реализовать способ передавать типизированный вопрос вместе с
  частичным созданием: target IDs, предлагаемое значение/evidence, событие и
  request/revision. Проверять область и сохранять в существующем атомарном пути.
  Не восстанавливать binding догадками из строкового вопроса в Python.
- Обеспечить подтверждение такого вопроса после restart без фиктивного второго
  пользовательского вопроса, с точным изменением/снятием только своих вопросов.
  Не разрешать произвольные пустые edit-планы ради обхода валидации.
- Уточнить инструкции/оценку модели для повторённой одинаковой единицы и короткого
  ответа; отдельно оценивать выбор плана и количество вызовов. Тесты с готовыми
  планами не заменяют эту оценку.
- Сохранить безопасную локализацию отказов: не журналировать payload/текст ошибки
  целиком, но различать неверный plan, отказ контракта и отсутствие saved binding.
- Pending → append из блока 3.1 остаётся отдельной отложенной production-задачей;
  здесь она не исправлялась. Оснований менять queue/delivery по этим тестам нет.
