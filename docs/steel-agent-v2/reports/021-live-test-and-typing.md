### Чего журнал не доказывает

В текущих inbox/attempt/outbox нет timestamp колонок. Нет отдельных исторических
событий admission, start_api, commit, send-start, receipt. Поэтому нельзя точно
назвать время прихода в inbox, момент claim commit, сохранения заявки или каждой
Telegram отправки. Delivered event — окончательное состояние, а не точный момент
сети. Текущие технические состояния всех соответствующих jobs — delivered,
committed=1, uncertain=0; attempts=result_received, outbox=delivered с receipt.
Delivered не означает успешную нормализацию: failed reply тоже доставлен.

Общая сериализация через SQLite/permission gate/scheduler/poller опровергнута
перекрытием API-вызовов. Код отпускает BEGIN IMMEDIATE до сети; реальные event
тесты независимо доказывают доступность обеих SQLite во время заблокированного
fake GPT. FIFO внутри одного пользователя сохранён. На отдельных коротких
локальных фазах locks существуют, их wait-time в живом тесте не измерялся.

## 2. Почему пропал typing и что исправлено

Прямой v2 Telegram adapter оборачивает обработку TypingIndicator; queue Executor,
который стал рабочим маршрутом №20, эту обёртку не использовал. Это локальная
регрессия интеграции, а не отсутствие поддержки Telegram API.

Executor после claim/permission проверок запускает существующий TypingIndicator
вокруг активной обработки агентом. Периодическая отправка независима для каждого
пользователя. Общий индикатор дополнен cooperative stopping callback: maintenance
прекращает новые pulses, пока начатый GPT может штатно завершаться. При выходе и
ошибке устанавливается stop Event. Ошибка sendChatAction скрывает только индикатор,
не влияет на результат, inbox/outbox или идемпотентность. Сеть typing вне write
transaction и не является durable Telegram доставкой. Старый handler не возвращён.

Один уже начатый sendChatAction может завершаться до сетевого timeout=3;
он не отменяется принудительно и не задерживает основной ответ на весь timeout.
После обработки новых pulses нет. После смерти процесса фоновый daemon thread
не сохраняется; queue recovery не создаёт typing без новой активной обработки.

## 3. Отказ новой заявки

update 9346240: два coordinate вызова. Первый вернул ValidationError при
структурированном ответе; точные loc/type, initial intent и извлечённое количество
в исторической диагностике не сохранены. Сырые GPT ответы не сохранялись, их
нельзя восстановить или воспроизводить как фактический ответ API. HTTP status и
request ID для этого ValidationError не записаны.

После известного завершения первого вызова сделан один разрешённый ремонт.
Второй ответ прошёл контракт и дошёл до RequestEngine, где отклонён по точному
коду **duplicate_characteristic:i1**: повторено имя характеристики в первой позиции.
Код проверяет уникальность c.name; совпадали ли сами значения и сколько items было
в ответе — не установлено. Это подтверждённый дефект извлечения модели, не основание
ослаблять валидацию или механически удалять характеристики. До проверки групп этот
план мог не дойти. Ремонтный intent=create_request следует из данного пути engine;
исходный intent первого ответа неизвестен.

Активная заявка не изменена этим отказом: после исключения updated=None,
Repository.finish сохранил failed turn/ответ в одной транзакции без новой версии.
Сохранённый failed reply указывает прежнюю revision. Никаких ручных исправлений,
очистки unknown, offset или повторных GPT запросов не было.

### Воспроизведение только на синтетических данных

Владелец запретил перенос оригинальных товарных строк. Фикстура
`tests/fixtures/steel_v2_021_synthetic_angles_channels.txt` составлена вручную,
без копирования production текста или GPT payload. В ней три уголка и три швеллера,
разные вымышленные сочетания размеров/марок, вымышленные номера ГОСТ и количества.
Номера ГОСТ служат тестовыми строками, а не реальными нормативными ссылками.

Положительный тест через настоящий queue/agent/engine/repository route с fake GPT
сохраняет 6 позиций, исходник, отдельные size/grade/standard с буквальными evidence,
Decimal количества и итог 0,240726 т (240,726 кг). Консолидация/эквивалентность и
валидация характеристик не изменялись.

Отрицательный тест контролируемо добавляет в модельный ответ вторую характеристику
с именем grade у i1. Реальный RequestEngine возвращает точный
**duplicate_characteristic:i1**. Проверены два сценария: два дефектных плана и
синтетический ValidationError → дефектный ремонтный план. В обоих случаях исходник
сохраняется, некорректная заявка не становится активной, текст отказа не упоминает
append. Тип первой синтетической schema-ошибки выбран для проверки пути ремонта;
он не объявляется точной причиной первоначального live ответа.

Таким образом, воспроизведён и покрыт механизм отклонения повторяющегося имени
характеристики. Не воспроизведено самостоятельное появление этого повтора у живой
GPT: платных вызовов не было, исходный ответ не сохранён. Тест не доказывает, что
модель перестала создавать такие ошибки. Первоначальный live schema-дефект остаётся
неизвестным. Проверки не ослаблялись, автоматическое удаление дублей не добавлено.

Для следующей диагностики validation event теперь содержит operation_id,
порядковый номер попытки, доступный intent/first known intent, extracted_count,
validation_stage и allowlisted diagnostic_codes. Если SDK отклонил ответ до
возврата typed plan, intent/count остаются null. В логе нет exception text,
характеристик, model IDs, сообщений и тела GPT; неизвестный код заменяется общим.
Это минимальное дополнение существующего emit, не новая система диагностики.

## 4. Универсальный отказ и append

Универсальный отказ после двух невалидных планов безусловно говорил о
неподдерживаемом добавлении — даже при create_request. Эта фраза удалена.

Явный append остаётся делом GPT intent=clarify: typed пояснение может сообщить
об ограничении. Regex по «Добавь», append операция и замена заявки не добавлены.
Пользователь не получает schema/source коды. Новый тест отличает эти два случая.

## 5. Почему группировка повторяет заявку

update 9346238: answer_question, сохранённый ответ длиной 1021 символ побайтно
совпал с render(сохранённая revision=1, view='explanation'), содержащим 4 позиции
и 2 группы. Это проверено сравнением в памяти, без вывода текста ответа/заявки.
Agent при explanation вызывает formatter и не использует краткий plan.answer;
presentation.render перечисляет все группы/items, затем причины/различия.
Схема заявок/групп здесь не повреждена. Диагностический тест воспроизводит ровно
это поведение без мутации. Formatter и контракт не изменены по границам задания.

## 6. Отдельные следующие задачи (в №21 не реализованы)

1. Краткое объяснение группировки: answer_question должен отвечать по причинам и
   отличиям запрошенных групп, без повторного списка всей заявки. Полный explanation
   оставить только явному подробному показу. Сохранить readonly и один model call;
   проверить короткий вопрос после create/edit/undo и несколько групп.
2. Компактная нормализованная выдача: по одной строке на позицию с существенными
   характеристиками и Decimal количеством; общий стандарт/объяснение не повторять
   без запроса, технические различия не скрывать. Отдельная приёмка на больших списках.
3. Полноценный append: сначала согласовать атомарный контракт source/evidence,
   принадлежность новых фрагментов, количества, версии/undo/idempotency; создание
   новой заявки не считать добавлением. В этом патче его нет.
4. При необходимости точных фаз очереди — отдельные безопасные stage timestamps
   в существующих событиях admission/commit/delivery без payload, не новая очередь.
