## Проблема и механизм

Транспорт раньше терял признаки цитирования и часть названий; агент дописывал
все URL и технические providers к Reply.text. Новый search_sources — адаптер
представления в том же v2-пути, без сетевых вызовов или определения намерений.

OpenAITransport.search сохраняет полный набор safe_source URL из завершённых
tool actions и финальных url_citation. Exact-URL дедупликация объединяет origins,
альтернативные titles и проверенные диапазоны/буквальные spans; title цитирования
предпочтительнее первичного названия. Метаданные не усечены двумя источниками.
URL с разными путями/query не объединяются как один сайт.

Отбор обычного footer: цитирование API с валидным диапазоном → прочее цитирование
API → URL, упомянутый в ответе → open_page/find_in_page → прочие результаты.
При равенстве сохраняется порядок получения. Так поздний цитируемый URL может
оказаться раньше первых произвольных retrieval-результатов. Это эвристика
релевантности, **не** доказательство технической истинности/взаимозаменяемости.
Safe_link дополнительно проверяет clickable URL. Название — сохранённый title
до 64 символов либо hostname реального URL; технический provider не считается сайтом.

Официальная [документация Web search](https://developers.openai.com/api/docs/guides/tools-web-search)
различает sources tool call и url_citation в тексте ответа, включая URL/title и
диапазоны. Проверена 19.10.2026; использован существующий Responses SDK, не новая модель.

Ссылки в прозе преобразуются в их текстовые labels, распознанные отдельные
библиографии убираются, API citation-маркеры не показываются. Иные annotated spans
не удаляются: там может быть сам факт. Буквальные товарные строки/характеристики
защищены до очистки. Числовые и неоднозначные factual anchors сохраняются даже
при совпадении с title; приложение не угадывает смысл ради сокращения текста.
Неоднозначное имя может остаться обычным текстом, но без повторного hyperlink.
Неизвестные произвольные URL из прозы не становятся ссылками footer.

## Полный набор и просмотр без повторного поиска

Reply.sources сохраняется целиком в JSON существующей steel_v2_turn вместе с
origins/titles/citations. Reply.search_text хранит исходный полный поисковый ответ,
search_query — запрос, search_providers — техническое происхождение provider-only.
Эти private поля не выводятся пользователю/в технические логи и не отправляются
как список сайтов. Reply.text и presentation содержат согласованный компактный
видимый текст. Готовый HTML outbox строится до commit, deliver не меняется.

«Покажи все источники» и аналогичные просьбы понимает существующий координатор
GPT через readonly view=sources. Это **один обычный coordinator-вызов**, ноль
search-вызовов/повторных вызовов поисковой стадии, без regex-intent router.
Контракт запрещает операции и search_query в этом виде. Python не принимает
модельный список ссылок: Repository.source_search читает canonical историю.

Область: тот же пользователь, request_id и текущая revision. Без активной заявки
берутся только поиски без заявки. Последний поиск должен быть успешным, а его
inbox-задание (если существует) — delivered. Неудачный, denied, pending или unknown
последний поиск является барьером; старый результат не подставляется. Provider-only
без URL честно не имеет списка. После смены заявки/ревизии источники не выдаются
за подтверждение текущих данных; произвольный выбор старого запроса вне этой
области не реализован. При отсутствии списка сообщается об этом без нового поиска.
Legacy/core-записи без inbox по-прежнему читаются как исторические завершённые
turn; искусственно создавать delivery receipt для них не требуется.

Полный вид сохраняет source_event_id и полный sources, не меняет активную заявку,
версии или последнюю карту отображения. Количество ссылок не ограничено двумя;
прежний html_chunks безопасно делит длинный список. Старые Reply/SourceLink читаются
с пустыми optional-метаданными, сериализация прежних receipts не меняется.
Нет DDL, новой таблицы, миграции, перерасчёта или повторного форматирования outbox.
