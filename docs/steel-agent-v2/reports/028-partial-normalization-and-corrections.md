## Что теперь происходит

1. Один обычный вызов координации, при известном structural/validation-сбое — один
   ремонт с точным кодом/полем, приватными loc/type/msg и previous proposal. Никакого бесконечного цикла.
2. После второго структурного сбоя recovery.py независимо принимает лишь те Item,
   чьи ID, диапазоны и literal evidence проверяемы. Дубликаты имён не удаляются:
   повреждённая позиция целиком остаётся неразобранной. Перекрытия/неоднозначные
   ссылки исключаются из доверенной части, а не маскируются.
3. Новый цельный partial содержит исходные абсолютные ranges для принятых позиций
   и unresolved для всех остальных непробельных символов. Полная валидация coverage,
   references, quantities и partition выполняется снова на целом оригинале.
   Из разных ответов модели не собирается «мозаика». При повреждённой группировке
   используются отдельные нейтральные группы, без предположения о взаимозаменяемости.
4. Если активной нет, проверенный partial атомарно сохраняется как заявка с историей
   и outbox. Если надёжных позиций нет — Snapshot не создаётся, исходник остаётся
   pending в turn. Если уже есть старая активная, она не заменяется неудачным новым
   результатом: проверенная часть новой сохраняется в Reply.pending_snapshot и
   показывается как **ещё не активная**.
5. Явное продолжение использует точный pending_event_id и сохранённый source_text;
   в ходе ремонта менять источник нельзя. Неверная ссылка или два нечитаемых ответа
   на «продолжи» не заменяют длинный оригинал коротким сообщением. Успешный разбор
   помечает исходную pending-запись разрешённой; запись не удаляется.

Суммы partial обозначаются как известная часть; unresolved в них не включаются.
Этот признак передаётся и GPT через totals_are_partial. Запрос итога не меняет версию.

Нет новой БД или DDL: прежние active/version/turn/inflight и queue schema=1.
Pending-маркеры и необязательный pending_snapshot — в существующем Reply/turn.
При None поле не сериализуется: совместимость старого durable receipt проверена.
Доставка, permissions gate, FIFO, три execution worker и typing не изменены.

## Узкие дополнения контракта

- `AgentPlan.pending_event_id`: только явно выбранное продолжение сохранённого
  исходника в create_request. Это не автоматическое создание вместо edit/append.
- `Operation.resolve.resolution`: разбор существующего unresolved с records только
  внутри его прежнего диапазона. Новые Item/originals происходят из того же original_text;
  прежние ID/позиции не меняются. Новые display numbers добавляются в конец.
  Последующий set может применить явную поправку из текущего сообщения в той же
  атомарной версии. Unsafe resolution отклоняется целиком; undo возвращает unresolved.
- `set.characteristic.replace_from`: ровно один буквальный старый токен; новый
  value должен присутствовать в evidence текущего сообщения. Это не сортаментный
  парсер и не язык команд. Вложенные/неоднозначные совпадения отклоняются.
- Групповые set — явный список устойчивых ID, атомарность прежняя. Форматирование
  использует readonly custom; оно не разрешает техническую мутацию.

Повреждённый GPT-план по-прежнему **отклоняется**, проверяется заново построенный
результат. Исторические отрицательные тесты сохраняют прямой assert такого отказа,
а затем проверяют partial. Базовые инварианты RequestEngine не ослаблены.

## Пример реального локального пути с fake GPT

Синтетический исходник:

```text
Труба 159×6 мм — 240 м
Уголок 50×50×5 мм марка неизвестна — 2,125 т
Лист 8 мм С245 — 17,625 кг
```

В двух ответах искусственно продублирована характеристика уголка. Результат
Agent → независимая проверка → Repository, не вручную созданный Snapshot:

```text
Заявка требует уточнения.
1. Труба 159×6 мм — 240 м
2. Лист 8 мм; С245 — 17,625 кг
Неразобранный фрагмент 1. Не обработано:
Уголок 50×50×5 мм марка неизвестна — 2,125 т


Уточните: сведения по неразобранным фрагментам.
```

Сообщение пользователя: **В позиции 2 марка 09Г2С**. Модельный план адресует i3, потому что лист
сейчас имеет отображаемый номер 2. Результат после одного set:

```text
Заявка требует уточнения.
1. Труба 159×6 мм — 240 м
2. Лист 8 мм; 09Г2С — 17,625 кг
Неразобранный фрагмент 1. Не обработано:
Уголок 50×50×5 мм марка неизвестна — 2,125 т


Уточните: сведения по неразобранным фрагментам.
```

Revision 1 → 2 в БД; труба, исходник, группы и неразобранный фрагмент сохранены.
Для разбора фрагмента существует resolve; отдельный тест проверяет resolve+set,
все три исходные потребности, точные суммы и undo. Утверждение этого синтетического
примера владельцем как экспертного CASE не имитировалось; knowledge не подключена.

## Осталось и порядок review

- Семантическая полнота и выбор намерений живой GPT не доказаны. Покрытие символов
  не доказывает распознавание каждого товара, всей марки или всех связей размеров;
  модель обязана согласованно адресовать связанные признаки, Python не знает сортамента.
- Pending не является второй активной заявкой. При наличии старой активной для новой
  сначала нужен явно выбранный успешный разбор сохранённого исходника; затем доступны
  обычные адресные правки. При неоднозначности между ними требуется вопрос.
- После отказа/таймаута API автоматического повтора нет. Исходник сохраняется прежним
  путём; execution_unknown сначала требует административного разрешения. Pending-
  восстановление не является обходом unknown. Два структурных вызова не гарантируют разрешение всех неоднозначностей;
  последующее продолжение требует явного действия пользователя.
- Append, сортаментные правила, Reference/knowledge, новая инфраструктура и постоянные
  предпочтения форматирования не добавлялись. Отдельный подробный view сохраняется.
