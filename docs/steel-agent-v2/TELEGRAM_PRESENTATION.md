# Представление заявки и поиск

## Кандидат этапа 2 — отображаемая адресация

presentation.display_order(request) определяет последовательность товарных ID из
существующих group.item_ids без новой сортировки. render normalized/forward не
печатает номера и сохраняет одну логическую строку на товар. Метаданные Reply.display
с request_id/revision/item_ids фиксируются вместе с историей и прежним outbox.
Следующий ход получает display_numbers из последнего полного подтверждённого
нормализованного показа, а не из items/исходника. Прямой core-вызов возвращает
этот показ вызывающему; durable Telegram-путь дополнительно проверяет delivered.
Неподтверждённая доставка, другая заявка/версия или старая история без карты
не позволяют молча подставить исходные номера. Нужен повторный показ.

Custom/original/totals не переназначают порядок последнего normalized/forward.
Pending-часть ещё не активной заявки также не меняет его. Edit/undo возвращают
новый normalized и обновляют карту атомарно. Для семантических правок используется
тот же GPT; Python разрешает selection и не выходит за совпавшие ID.
Печатные номера ниже — историческое описание №27, отменённое BR-002/010.
BR-003–005 и HTML в этом кандидате не реализованы.

### BR-006: проверка возможности HTML, без реализации

Telegram [sendMessage](https://core.telegram.org/bots/api#sendmessage) принимает
parse_mode; [HTML style](https://core.telegram.org/bots/api#html-style) поддерживает
в том числе именованные ссылки. Документация требует экранировать специальные
символы вне разметки и ограничивает допустимые теги. Лимит текста после разбора
entities — 4096. В проекте HTML сейчас не передаётся.

Предлагаемая безопасная реализация следующего этапа:

- Строить разрешённые теги приложением; пользовательский текст, характеристики,
  названия источников и произвольный ответ GPT считать данными, экранировать.
  Не передавать сырой Markdown/HTML модели прямо с parse_mode=HTML. Удалять
  значимые символы исходника регулярным выражением также нельзя.
- URL сначала проверять прежним safe_source; затем экранировать HTML-атрибут,
  а короткое название сайта — как текст. Не превращать неподтверждённые URL в источники.
- DurableQueue.finish_hook сейчас сохраняет только chat_id/text после safe_chunks;
  deliver передаёт payload в TelegramAPI.call. Именно здесь должен сохраниться
  готовый безопасный формат частей и parse_mode, атомарно с прежним outbox.
  Просто включить parse_mode глобально в API.call недостаточно и небезопасно.
- safe_chunks режет по строкам/UTF-16 и не понимает HTML: может разрезать тег или
  entity. Сначала формировать целостные части из данных с учётом длины видимого
  текста, затем экранировать/оборачивать каждую часть, сохраняя валидность тегов.
  Проверить длинные строки, амперсанд/угловые скобки/кавычки, emoji и вредоносную
  ссылку, включая ошибочные ответы и доставку после восстановления.

Это проверенная возможность протокола и предложенные точки интеграции, а не
готовый патч или подтверждение живой HTML-доставки. Новая инфраструктура не нужна.

### BR-007: краткий и полный список

OpenAITransport.search сохраняет safe SourceLink и удаляет повтор точного URL.
SteelAgent.handle добавляет весь список «title — URL» к result.text, где ссылки
могут уже присутствовать; лимита 1–2, коротких HTML-названий и общего устранения
повторов нет. Reply.sources хранит полный список в истории, но Repository.history
передаёт только текст; отдельный пользовательский путь полного списка ещё нужен.
Следующая работа: краткое релевантное представление отдельно от полных доказательств,
чтение полного списка по запросу без нового web_search. Не считать вариант URL
дублем механически, если это может отбросить разные подтверждающие страницы.
При feeds без URL не выдумывать кликабельный сайт.

Актуализация №27, 18.10.2026. Ниже описан код кандидата, **ещё не установленного**
в production. Его работа в настоящем Telegram ждёт разрешённого выпуска и ручной
проверки. Целевой стиль —
[NORMALIZATION.md](NORMALIZATION.md); известные проблемы и живые подтверждения —
[PROJECT_STATE.md](PROJECT_STATE.md).

## Обычный ответ

`normalized` и `forward` показывают краткие строки: наименование, подтверждённые
характеристики — точное количество и исходная единица. Одна позиция — без номера,
несколько — с номерами. Версия, заголовки групп, промежуточные суммы и повторные
пояснения различий не входят в копируемый текст. UUID, ID групп/позиций/источников,
служебное подтверждение проверок и длинное обоснование GPT не выводятся.
Значения характеристик, уже присутствующие в подписи, не повторяются.
Общий город показывается отдельно только при одинаковом структурированном city
у всех позиций. Разные города остаются у соответствующих позиций. Из текста
произвольной заметки Python город не угадывает.

В обычном тексте каждая позиция группы показана отдельной полной строкой, включая
одинаковые позиции: консолидации ради краткости нет. Группы в данных не меняются.
Суммы доступны в totals, обоснования и предупреждения о взаимозаменяемости —
в explanation. Отсутствие предупреждения в каждой строке не утверждает эквивалентность. Номера позиций соответствуют `display_numbers` в контексте
координатора; перегруппировка не меняет соответствие номера исходной позиции.
`explanation` раскрывает причины/различия и дополнительный исходный текст,
заменяя служебные ссылки человеческими номерами. `original` возвращает оригинал.
Изменение/отмена показывают актуальные данные; новая версия сохраняется в БД,
а её номер виден в подробном представлении. Фраза «Не требуется уточнений» удалена:
partial=false не доказывает профессиональной полноты. Вопросы, явные неизвестные
параметры и unresolved-фрагменты остаются видимы. Formatter не определяет
обязательность отсутствующего в модели признака и не восстанавливает пропущенные GPT факты.

Числа форматируются из Decimal без округления, с десятичной запятой и без
добавленных нулей. Исходные единицы хранятся; при изменении единицы отдельно
показывается прежнее количество с единицей. Неизвестные значения, вопросы и
необработанные фрагменты остаются видимыми. Повторный показ partial не превращает
его в готовую заявку. Длинный ответ делится существующим Telegram-адаптером.

## Пересылка и произвольное оформление

GPT по намерению выбирает `show_request`/`answer_question` с `view=forward`.
Python формирует текст из текущей заявки без приветствия, UUID и номера версии.
Никакого повторного извлечения или второго GPT-вызова ради форматирования нет.
Один вызов координатора остаётся необходимым для понимания свободной команды.
Неполнота и существенные технические различия не скрываются даже при пересылке.

`view=custom` передаёт произвольное оформление в `answer` того же плана: таблица,
сокращение или выбранные пользователем поля. Это readonly-ответ по актуальному
контексту. Строгий контракт запрещает совмещать новые readonly-представления с
изменением заявки. Произвольный текст GPT не считается проверенным машинным
экспортом: его содержание требует живой оценки; Python не применяет его к данным.

## Web Search

Официальная [документация](https://developers.openai.com/api/docs/guides/tools-web-search)
описывает источники в `web_search_call.action.sources`, ссылки в annotations и
специализированные feeds. Парсер принимает безопасные URL из этих структур и
завершённых действий open_page/find_in_page. Ссылки из произвольного текста не
считаются подтверждёнными источниками.

Документированные `oai-weather`, `oai-finance`, `oai-sports` принимаются только
из структурного источника type=api завершённого вызова инструмента. Если URL нет,
пользователю показывается имя сервиса, без выдуманной ссылки. Неполный tool call,
неизвестный provider, отсутствие ответа/источников и ошибка API дают безопасный
отказ. Поиск никогда не меняет заявку.

Событие `steel_v2_search_verification` сохраняет только причину, факт завершения
инструмента, число tool calls/ссылок/feeds и request ID, если SDK предоставил его.
Ошибки API сохраняют безопасные HTTP status/code/param/request ID прежним
механизмом. Успешный SDK-объект не содержит числового HTTP status: такой код не
придумывается. Тела ответа, запрос, URL источников и переписка не журналируются.

Причина сохраняется в существующей Reply.diagnostics, без миграции БД.
`last_search` передаёт только техническое резюме. При вопросе о причине GPT
выбирает `view=search_status`; Python отвечает в пределах сохранённой диагностики.
Для старых отказов без подробностей причина остаётся неизвестной.

Интерфейс/парсер первоначально проверялись mock HTTP/SQLite в №11. Позже №21
зафиксировал живой API-вызов Web Search; его интервал не доказывает качество
источников, работоспособность любого запроса или качество UX. Причина раннего погодного отказа
не восстановлена: body намеренно не сохранялся.

## Уточнение runtime №13

Одноходовый `max_tool_calls=1` удалён из запроса: для многошагового поиска он
ограничивал выполнение последующих действий. Это не добавляет клиентских повторов:
один SDK-вызов поиска, max_retries=0 и прежний timeout=180 сохранены. Внутреннее
число инструментальных действий теперь определяет API, а не искусственный предел 1.

Принимается только завершённый Response с явно завершёнными tool calls,
завершённым assistant message после последнего инструмента, его текстом и
подтверждёнными источниками. Отсутствующий/неизвестный статус не считается успехом.
Смешанные failed/incomplete/in_progress/searching не превращаются в completed
из-за наличия ссылок. Для ослабления этой политики пока нет живых доказательств.

Диагностика различает response_status, статусы и типы отдельных действий,
наличие message/output_text, факт хотя бы одного completed-действия
(`search_performed`), завершение всех действий (`tools_completed`) и пригодность
ответа (`usable`). Метки allowlisted; список ограничен первыми 32 действиями с
флагом усечения. В старом событии search_performed=false означало провал общей
проверки всех статусов, а не доказанное отсутствие выполненного поиска.

Контекст previous_operation содержит только intent/status последнего хода.
Он отделён от last_search. Инструкция явно различает короткое объяснение
предыдущего поискового отказа, вопрос после другой операции и явный повтор
поиска. По слову «почему» Python не маршрутизирует; смысл выбирает GPT, объяснение
search_status формируется из подтверждённой причины. Естественное понимание
такого вопроса и качество ответа требуют отдельной предметной приёмки, даже
после установки изменений №13 и наблюдавшегося живого API-вызова поиска.

## Разбиение длинного текста — №27

Общий safe_chunks теперь предпочитает целые строки; если отдельная строка сама
длиннее лимита, делит её по символам с учётом UTF-16 (emoji занимает две единицы).
Лимит 3200 сохранён, конкатенация частей точно восстанавливает текст. Durable queue
пользуется прежним helper и сохраняет части прежним способом; её код не изменён.
Проверка на 120 позициях прошла через настоящие Repository/Executor и fake Telegram.
Качество извлечения GPT этими тестами не доказано. [Отчёт №27](reports/027-professional-presentation.md).

## Частичные заявки — кандидат №28

Компактные строки №27 сохранены. Явная неизвестная характеристика показывает также
её исходное неоднозначное обозначение; неразобранные фрагменты имеют отдельные номера,
не совпадающие с номерами уже принятых товаров. Вопросы остаются видимы.
После явной технической правки исторический токен в дублирующей подписи обновляется
только при однозначном буквальном совпадении; сохранённые оригиналы не меняются.

При наличии старой активной и неудачной новой текст явно различает их. Pending-часть
не является активной: для продолжения новой нужен явный выбор исходника; нельзя
применять её номера к прежней. Форматирование — custom без технической мутации.
UI-коды schema/UUID не выводятся. Длинный результат проходит прежние durable outbox
и safe_chunks, проверено на 200 синтетических позициях с одним неразобранным фрагментом.
