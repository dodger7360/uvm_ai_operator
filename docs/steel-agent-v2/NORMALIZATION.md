# Нормализация и инварианты

Актуализация №23, 18.10.2026: целевые требования владельца и редакция для review.
Текущее состояние и известные отказы — [PROJECT_STATE.md](PROJECT_STATE.md).
Ниже отдельно описаны желаемый результат и уже реализованные проверки Python.

## Два результата одной нормализации — целевое поведение

**A. Человекочитаемая заявка.** Краткая профессиональная строка: наименование,
существенные технические характеристики, количество и единица в конце. Текст
пригоден для копирования без удаления служебных вставок. UUID, номер версии,
внутренняя структура групп и заголовок «Заявка, версия 1» в основной текст не входят.
Город показывается, если подтверждён данными. Не повторять объяснения и сведения
без запроса; существенные отличия внутри группы не скрывать. Подробности — по
явному запросу, оригинал и внутренние версии всегда сохраняются отдельно в БД.

«Не требуется уточнений» недопустимо без доказанной полноты характеристик.
Отсутствие вопросов у GPT или `partial=false` само по себе её не доказывает.
Критерии достаточности по видам продукции ещё открыты: [DECISIONS.md](DECISIONS.md).
Текущий formatter пока выводит версию и указанную фразу; №23 его не меняет.

**B. Структурированная товарная позиция.** Данные для будущего сопоставления:

- Вид металлопродукции, наименование/обозначение.
- Размеры и геометрия; марка стали или материала.
- Стандарт/ГОСТ/ТУ, если указан; исполнение или тип, если установлен.
- Длина, раскрой и дополнительные параметры, если известны.
- Количество, единица, оригинальное обозначение и исходное написание единиц.
- Ссылки на доказательства в исходнике; неизвестные и требующие подтверждения признаки.

Это перечень возможных предметных характеристик, а не обязательная анкета каждого
товара. Нельзя заполнять отсутствующие размеры, тип трубы, ГОСТ или длину «по умолчанию».
Необходимость уточнения определяется значимостью для операции; отраслевые правила
обязательности требуют согласования. Отдельная фиксированная схема на каждый
сортамент этим документом не предписывается: нынешний Item имеет общий список
Characteristic и source evidence. Изменение контракта требует проектирования.

Оба результата используют одни подтверждённые факты. Красивое представление не
должно менять заявку, её original, количества или технические различия.
Нормализация помогает узнавать одну номенклатуру в разных написаниях, сохраняя границы:

| Результат | Что означает |
|---|---|
| Нормализация написания | Разное написание приведено к читаемому виду; это ещё не доказательство совпадения |
| Подтверждённое техническое совпадение | Существенные признаки проверены по источникам и согласованному критерию |
| Неполное совпадение | Недостающие сведения явно указаны; требуется проверка |
| Возможный аналог/замена | Отличия известны, допустимость замены отдельно подтверждается |

Критерии соответствия и замен пока открыты. Похожесть названий и коммерческая
группа не являются доказательством взаимозаменяемости. Примеры приёмки —
[NORMALIZATION_CASES.md](NORMALIZATION_CASES.md); будущие источники —
[PROCUREMENT_PIPELINE.md](PROCUREMENT_PIPELINE.md).

## Реализованные инварианты и их границы

GPT выделяет исходные позиции, нормализует характеристики и предлагает группы.
Python не решает эквивалентность стали или ГОСТов.

Оригинальный текст неизменен. SourceRecord задаёт диапазон Python Unicode
[start,end), kind product/header/note/unresolved. Все непустые символы покрываются
ровно один раз; диапазоны не пересекаются. Каждому product соответствует один
Item со стабильным ID и source_id. Повторяющиеся строки сохраняются раздельно.
Характеристики содержат raw и ссылки source_ids; literal evidence проверяется.
Количество — конечная неотрицательная Decimal из исходного numeric fragment;
unit/unit_text сохраняют исходное обозначение. Неизвестное не считается нулём.

Коммерческая группа ссылается на item_ids. Совокупность групп содержит каждую
позицию ровно один раз. Суммы не принимаются от GPT: Python суммирует Decimal и
приводит совместимые единицы, например кг к тоннам. Метры/штуки не превращаются
в тонны без источника массы. Неизвестные единицы выводятся отдельно.
Различия характеристик и единиц вычисляются буквальным сравнением, отображаются
вместе с замечаниями модели. Подпись группы не заменяет технические требования.
В ответе явно сказано, что закупочная группа не доказывает взаимозаменяемость.

Адресные изменения: set по target_id, regroup полного набора прежних ID, undo
последней правки. Ожидаемые id/revision защищают от устаревшего плана. Значение
правки требует evidence в текущем сообщении. Несовместимые операции отклоняются
целиком; новая версия сохраняется только после проверки всего результата.
Undo создаёт новую revision, восстанавливая прежний снимок и стек отмен.
Исходные значения остаются в originals и версиях; discussion/search их не меняют.

При существенной неоднозначности модель должна уточнить вопрос. Неизвестные
характеристики/количества, unresolved и вопросы видимы как partial. После одного
неудачного ремонта старое состояние сохраняется, оригинал сообщения остаётся
в истории либо inflight при сбое SQLite.

Границы проверки: покрытие символов не доказывает правильность классификации
product/note; наличие raw не доказывает семантическую верность value или полноту
извлечённых характеристик. Эти ошибки оцениваются по исходнику в живых испытаниях,
а не добавлением каталога частных правил. Undo действует внутри текущей заявки;
возврат к предыдущей архивной заявке пока не реализован.
