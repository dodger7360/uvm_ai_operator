# Правила разработки Steel Agent v2

Область: ядро v2, его тесты, документация и подключение Telegram.
Корневой AGENTS.md требует прочитать этот файл и при работе вне docs/.

Перед любым новым заданием прочитать [PRODUCT.md](PRODUCT.md),
[DECISIONS.md](DECISIONS.md), [PROJECT_STATE.md](PROJECT_STATE.md) и связанные
предметные спецификации. Для нормализации — [NORMALIZATION.md](NORMALIZATION.md)
и [NORMALIZATION_CASES.md](NORMALIZATION_CASES.md); для источников —
[PROCUREMENT_PIPELINE.md](PROCUREMENT_PIPELINE.md). GitHub — постоянный источник
утверждённых требований и состояния, а не только архив отчётов.

Если задание противоречит утверждённому решению владельца — остановиться и указать
конкретное противоречие. Предложения, ожидающие review, не выдавать за утверждённые.
Не устанавливать неутверждённые бизнес-правила самостоятельно. После утверждённых
изменений продукта обновлять основные документы, не оставлять решения только
в переписке/отчёте. Количество Python-тестов не является единственным доказательством
предметного качества ИИ; отделять mock, живые технические и предметные испытания.

- Единственный активный ИИ Telegram — v2, gpt-6-luna/high. Legacy/нет config дают
  отказ; старый ИИ не является fallback. Полезные старые парсеры переносить выборочно.
- Forward-only; нет возврата старого обработчика, внешнего guard, ProgramData,
  admin/IT или изменения Task Scheduler для текущего контура. Исторические
  инструкции №15–18 не восстанавливать. Разработка и выполнение сейчас Windows.
- Не переносить production-строки, payload, переписку и SQLite в GitHub;
  использовать синтетику либо явно разрешённые данные.
- GPT понимает заявку, номенклатуру и намерение; предлагает коммерческие группы.
- Python хранит данные, считает Decimal, проверяет инварианты и исполняет операции.
- Не добавлять частные Python-правила для марок стали, ГОСТов и типоразмеров.
- Не подгонять модель под буквальное совпадение с одним эталоном.
- Не восстанавливать старую многоступенчатую архитектуру; не переносить B1–B10 автоматически.
- Сохранять оригинал, все исходные позиции и технические отличия; исключать потерю и двойной учёт количеств.
- Коммерческая группировка не означает техническую взаимозаменяемость.
- Не скрывать ошибки, предположения и оставшиеся ограничения.
- Не соглашаться автоматически с пользователем или предыдущим ассистентом при противоречии тестам или технических рисках.
- При разногласии объяснять причину и альтернативу, не менять требования молча.
- Один пронумерованный промпт — один отчёт в reports/.
- Production и deployment требуют прямого разрешения пользователя.
- Реальные API-испытания требуют отдельного разрешения; mock-тесты не доказывают качество модели.
- Фактическая реализация: [ARCHITECTURE.md](ARCHITECTURE.md); приоритеты:
  [ROADMAP.md](ROADMAP.md). Документация №23 ожидает review владельца, не реализацию №24.
