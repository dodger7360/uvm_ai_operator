## Подтверждение единицы при create/partial — 22.10.2026, блок 4.4

Владелец разрешил одно явное типизированное предложение единицы вместе с create.
Предложение — гипотеза, не исходный факт: unit/unit_text целевой позиции остаются
неизвестными до отдельного согласия. GPT интерпретирует ответ; Python применяет
только связанную с event/request/revision/target/value операцию confirm_unit,
записывая цитату ответа и ссылку на вопрос отдельно от исходных данных. Другие
поля и вопросы не меняются. Binding переживает restart через Repository.finish;
после undo/смены scope старое согласие не действует. Общий механизм вопросов и
pending → append сюда не входят. [Контракт](UNIT_CONFIRMATION.md), кандидат и проверки —
[отчёт 4.4](reports/block-4-4-create-unit-confirmation.md); deployment не разрешён.

## P0: полезная нормализация и необязательный норматив — 19.10.2026

Утверждено владельцем после живого CASE-002: номер ГОСТ не универсально
обязателен и не должен блокировать извлечение товаров. Точный approved
owner_indicative профиль/размеры/марка/длина допускают предварительную массу
без необязательной ссылки GPT standard_name. Явные противоречащие нормативы,
исполнения и размеры по-прежнему запрещают неподтверждённую массу, сохраняя товар.
Не добавлять отсутствующие характеристики. Повторяющиеся вопросы и внутренние
имена полей не входят в обычный ответ. Основной create-план должен быть компактным;
Python сохраняет прежние проверки, исходники, версии и атомарность.
Реализация и границы — [P0 отчёт](reports/simple-create-and-approved-mass.md).

## Срочное решение после живой приёмки этапа 8 — 19.10.2026

Утверждено владельцем: самостоятельный новый товарный список создаёт новую
активную заявку без вопроса о замене. Старые заявки сохраняются в версиях и
истории; прежний pending не подменяет новый исходник. Если действительно был
задан вопрос о новом списке, его исходное событие сохраняется до подтверждения.
«Новая заявка» использует этот исходник, не требует повторной отправки.

«Закрой заявку», «Заверши заявку», «Сбрось текущую», `/close` закрывают active
без удаления original/items/versions/turns. После закрытия начинается обычный
GPT-чат без прежнего рабочего pending/clarification. `/close` выполняется без GPT.

«Добавь <новые товары>» при активной заявке дополняет её, сохраняя старые ID,
факты и количества. Новые исходники/provenance проверяются прежним RequestEngine;
новая версия и ответ фиксируются атомарно, undo сохраняется. Это отменяет
исторический запрет append; BR-001–011 и эталонные CASE не меняются. GPT различает
новые товары и увеличение количества имеющейся позиции, Python не вводит новый
парсер русского языка. Неоднозначность по-прежнему требует предметного вопроса.

Кандидат реализован в отдельном PR; новая версия ещё не установлена. Ручная
Telegram-приёмка необходима после отдельно согласованного выпуска.

## Актуализация этапа 7 — 19.10.2026

Утверждено владельцем при завершении PR №22: явное последовательное исправление
той же характеристики той же позиции обновляет актуальное обозначение целиком.
Пример: труба профильная 40×40×3 Ст3, 430 шт. по 6 м; уточнение «Стенка 5 мм»
означает актуальные 40×40×5 Ст3, 430 шт., 6 м. Исходные 40×40×3 остаются
в оригинале и истории. При однозначной связи не нужны номер позиции и лишний
вопрос; при неоднозначности нужен предметный вопрос. Это относится к одному
сообщению, последующему уточнению и правке сохранённой заявки. Связь и намерение
определяет существующий GPT-координатор; Python применяет проверенные операции.
Это не правило «последнее число заменяет предыдущее» и не изменение BR-001–011.

Уточнение товара и расчёт массы независимы: 3,36 кг/м для 40×40×3 нельзя применять
к 40×40×5. Без нового проверенного основания товар сохраняется без теоретического
тоннажа. Если одновременно действующие структурированные размеры противоречат
друг другу и явное исправление не установлено, Python блокирует только массу,
не выбирая победителя. CASE-002 с исходной стенкой 3 мм остаётся без изменений.

Утверждено владельцем: этап 6 закрыт и слит (`8805e39f`); подключить existing
approved знания к тому же GPT-6 Luna High. BR-001–011 rev1 глобальны в своей области;
CASE-001–006 (25 позиций) — частные эталоны, без автоматического обобщения исправлений.
Не брать первые исторические ответы за эталоны, не обращаться к GitHub на заявку,
не блокировать товар отсутствием записи, не менять очередь/архитектуру заявок.

Реализовано в кандидате этапа 7: локальный manifest/artifact, хеш-версия источников,
релевантный контекст, provenance в прежнем Reply, девять одобренных ориентиров
через существующий MassCatalog. Выбор по темам — инженерный индекс, не новое
бизнес-правило. Защита применимости и Decimal обязательны; новые интернет-факты
по-прежнему требуют прежнего подтверждения. Проверки с mock-планами не утверждают
экспертное качество живого GPT. Реализация ожидает независимого review; merge и
production не разрешены этим этапом. [Отчёт](reports/stage-7-approved-knowledge.md).

18.10.2026, основа №23, сверка №24. Редакция для review владельца. GitHub хранит
утверждённые требования и фактическое состояние; чат и Codex сверяются с ними.
Новые формулировки и критерии приёмки требуют review: публикация не равна утверждению.
Позднее явное решение владельца отменяет противоречащее историческое.

## Открытые вопросы

| Вопрос | На какое решение влияет |
|---|---|
| Существенные характеристики видов; когда нужны ГОСТ, длина, раскрой, исполнение | Уточнения и приёмка; универсальной обязательности не устанавливаем |
| Когда предлагать типовой вариант, когда только спрашивать | Разделение предположений и подтверждённых требований |
| Критерий готовности заявки | Право сообщать о полноте и передавать в закупку |
| Дубли и коммерческие группы | Суммирование с сохранением индивидуальных различий |
| Аналоги и допустимые замены | Статус соответствия и подтверждение сотрудником |
| Источники теоретической массы, пересчёты единиц | Получение тонн из метров/штук с доказательством метода |
| Несколько активных заявок пользователя | Выбор контекста, адресность правок, undo и append |
| Границы свободного диалога | Обсуждение, уточнение или операция без скрытой мутации |
| Ранжирование цен/поставщиков | Закупочные приоритеты, которые нельзя назначать самостоятельно |
| Подтверждение наличия и свежести цены | Срок доверия данным и учёт запрошенного количества |
| Филиалы, расстояние и радиус 400 км | Географический отбор, а не автоматический жёсткий фильтр |
| Форматы, права и ограничения Bitrix24 | Доступ к истории без полной локальной репликации |
| Интерфейсы/владение/актуальность существующих парсеров | Выборочный перенос, ограничения сайтов и обновление данных |

Ответы сейчас не запрашиваются. Неутверждённое бизнес-правило агент не устанавливает сам.

## №28 — полезный частичный результат вместо общего отказа

Владелец утвердил: показывать достоверно нормализованное, сохранять и явно показывать
неразобранное. Неизвестные характеристики допустимы; структурно повреждённый план
не становится нормализацией. После одного ремонта допустим локально построенный
**заново проверенный** частичный план с unresolved для непроверенных фрагментов.
Контроль полноты, точности, ссылок и однократного учёта не ослабляется.

Если нет надёжных позиций — исходник ожидает разбора в существующей истории,
не фиктивной заявке. При неудачной новой заявке прежняя активная сохраняется;
проверенная часть новой может храниться как pending_snapshot в ответе того же turn.
Возобновление сохранённого исходника требует явной просьбы, не фонового replay.
Unknown API/доставка остаются под прежним административным контролем очереди.

Разрешение сохранённого unresolved — узкая операция resolve, без новых исходных
строк. Это не append. Свободная правка адресуется по актуальным номерам/ID; массовая
операция атомарна. Неоднозначность требует одного вопроса. Форматирование не меняет
технические характеристики. Каталоги и новые глобальные сортаментные правила не вводятся.
