# Надёжная очередь — проект №15, реализация №16

Статус: **реализовано в отдельной ветке для review, не развёрнуто**. База
`aa11380dfe1ed646fec2355b22880fdb03b0d706`.
Предметная модель RequestEngine, Decimal и коммерческие правила не меняются.

## Основание согласованного изменения

До №16 `telegram_bot.run_bot` синхронно вызывал dispatch, затем сохранял offset
в legacy SQLite. V2 begin сохраняет единственный inflight на пользователя,
finish атомарно фиксирует заявку, версию и ответ. Это защита от повторной мутации,
но не очередь: нет принятых ожидающих заданий, стадий внешнего вызова, outbox
и подтверждений доставки. Репозиторий разрешает только четыре существующие таблицы.

Надёжная параллельность требует новых таблиц v2, изменения транзакционного finish,
политики восстановления и совместимости отката. Это существенное изменение
хранения и эксплуатационных гарантий. Проект был согласован заданием №16 после
остановки №15 для согласования. ThreadPoolExecutor
без этих изменений не является допустимой реализацией.

## Согласованная модель

Один существующий process lock и один poller getUpdates. Отдельный диспетчер
обслуживает не более трёх пользовательских операций одновременно; на одного
user_id допускается только одна операция, включая доставку. Выбор готовых
пользователей — round-robin, внутри пользователя — порядок приёма update_id.
Неопределённое задание блокирует последующие сообщения этого пользователя,
но не остальных. Существующие admin/callback/access операции также проходят
durable admission; нельзя оставить для них побочный недедуплицируемый путь.

Отдельная локальная конфигурация `telegram-queue.json` (не .env, не настройка
модели): workers=3, max_pending=100, max_pending_per_user=20,
max_pending_bytes=8 MiB. Это параметры приёма, не API-бюджеты. Все значения
валидируются до polling; эти пределы утверждены №16. При заполнении
не удалять задания, не подтверждать недопущенный update, прекращать чтение новых
пакетов до освобождения места. Обрабатывать Telegram limit с учётом вместимости;
для слишком большого отдельного сообщения нужен явный устойчивый отказ.

### Хранение и offset

Созданы добавочные таблицы version=1 **в отдельной существующей SQLite v2**:

- inbox: глобально уникальный update_id, user_id/chat_id, вид события, ограниченный
  payload, hash, порядок, стадия, поколения прав и билет обслуживания;
- attempts: job/attempt ID, стадия внешнего вызова, безопасный outcome;
- outbox: job, порядковый номер части, точный текст ответа, delivery state,
  полученный Telegram message_id при известном успехе;
- queue_meta: версия схемы, durable receive watermark и параметры восстановления.

Нельзя логировать payload, запросы модели и ответы; данные inbox/outbox защищаются
так же, как история заявок. Время хранения/очистка — отдельная явная политика,
без удаления необработанных и неопределённых заданий.

В одной транзакции v2 сохраняются принятые события и receive watermark. Только
после её commit разрешено записать соответствующий общий legacy offset и сделать
следующий getUpdates с повышенным offset. Это **write-before-ack**, не атомарная
транзакция двух SQLite. При сбое между commit inbox и записью legacy offset
повторно доставленные update_id дедуплицируются по полному hash/владельцу/типу.
Конфликт повторного ID останавливает приём с безопасной диагностикой.

Полученный пакет должен быть проверен на порядок; нельзя продвигаться за событие,
которое не удалось устойчиво принять. Не требовать арифметически непрерывных ID:
разрывы Telegram допустимы. Для нецелевых событий также фиксируется безопасное
terminal решение. Не сохранять весь update без минимизации персональных данных.

Legacy offset остаётся общим операционным cursor, но его продвижение теперь
означает durable admission, а не завершение бизнес-операции. Старый код не умеет
дочитывать inbox: это принципиальное ограничение отката, требующее проверки очереди.

### Выполнение и внешние эффекты

Стадии: queued → claimed → api_started → result_received → committed →
delivery_pending → delivery_started → delivered. Отдельные terminal состояния:
denied, rejected, execution_unknown, delivery_unknown. Переходы через compare-and-set
и стабильные ключи, без удержания write transaction во время сети.

Перед запросом GPT устойчиво записывается api_started; SDK retries остаются
выключенными. После неизвестного исхода запроса автоматического повтора нет.
Авария между marker и фактической отправкой тоже считается неопределённостью:
консервативно нельзя доказать, что платного вызова не было. Это не exactly-once.
Каждый дополнительный штатный ремонт плана — отдельная явно учитываемая попытка,
только после известного ответа, максимум существующего протокола.

Проверенный результат, новая версия, история, завершение claim и полный outbox
должны фиксироваться одной транзакцией v2. Для этого finish должен принимать
транзакционный контекст либо новый репозиторный метод; обёртка поверх существующего
finish не обеспечивает атомарность. Непроверенные предложения не становятся
активными позициями. Если результат после API не удалось устойчиво записать,
состояние execution_unknown, без нового GPT. Внутренние повторы коротких DB-записей
ограничены и не должны повторять внешние эффекты.

Перед sendMessage устойчиво фиксируется delivery_started. Успех с message_id
помечается delivered. Таймаут/сбой между отправкой и записью receipt —
delivery_unknown; автоматическая пересылка может дублировать сообщение и поэтому
запрещена без решения оператора. Заведомо не начатые части outbox можно доставить
после перезапуска без повторной мутации. Не обещать exactly-once Telegram delivery.

### Права, потоки и SQLite

Авторизация проверяется при приёме, перед исполнением, перед commit и перед каждой
частью отправки. Админ-отзыв доступа сериализуется репозиторием; нельзя блокировать
его за медленной пользовательской сетью. При отзыве после оплаченного ответа
заявка не изменяется, событие получает denied, служебное состояние сохраняется.
Отдельно тестировать гонку revoke/commit: существующий callback в другой БД сам
по себе не доказывает атомарную авторизацию между двумя SQLite.

Database уже открывает независимое соединение на каждый контекст. Предлагаются
короткие транзакции, явный busy timeout и ограниченные повторы до начала сети;
без глобальной shared connection. Изменение journal mode допускается только после
отдельной проверки backup/Windows, не является необходимым условием проекта.

У каждого execution worker свой OpenAITransport/SDK client; у poller отдельный
TelegramAPI. Общую безопасность SDK-клиента не предполагаем. TelegramAPI сейчас
строит отдельный urllib Request на вызов, но политика общего opener и ошибок
ещё требует проверки. Диагностический operation ContextVar создаётся внутри
задачи; метрики агрегируются под lock, без общего текущего пользователя/запроса.
TelegramAccess содержит репозиторий, а не пользовательский mutable context;
нужны тесты конкурентных callback/notification reservations.

### Остановка, авария и откат

Maintenance прекращает admission и планирование новых queued задач. Уже начатые
задачи завершаются кооперативно; ожидающие остаются на диске. Существующие stop
и supervisor не убивают worker: при превышении 180 секунд stop сообщает таймаут,
maintenance сохраняется, второй процесс не запускается. Worker не должен выйти,
пока работающие non-daemon задачи не завершились или не зафиксировали исход.

После аварии queued можно выполнять; claimed до api_started можно безопасно
возвращать в очередь только по доказанному состоянию транзакций. api_started без
устойчивого результата — execution_unknown. committed с не начатой доставкой —
только доставка. delivery_started без receipt — delivery_unknown.
Нельзя автоматически освобождать старый inflight и повторять запрос.

Перед включением: backup, версия схемы, dry-run на временной БД, один poller,
проверка всех записей старого inflight вручную без replay. Откат на нынешний код
разрешён только после опустошения inbox/outbox и разрешения unknown либо при
сохранении совместимого queue consumer. Возврат одного Git SHA при опережающем
offset может потерять обработку уже принятых заданий. SQLite/offset назад не откатывать.

## Обязательная проверка реализации после согласования

Event/barrier тесты: A/B реально перекрываются; A1/A2 FIFO; три пользователя
параллельно, четвёртый ждёт; fairness; bounded bytes/count; stop до/во время
admission/API/commit/delivery; SIG/crash injection на каждой границе транзакций;
повтор update и конфликт hash; locked SQLite; revoke/commit/delivery гонки;
частичная отправка ответа; reopen; legacy offset между двумя commit;
один process lock и supervisor; миграция и запрет несовместимого отката.

Для каждого сценария проверять версии, оригинал, суммы Decimal, историю,
количество API attempts и устойчивые terminal/unknown состояния. Текущие
диагностические тесты №15 этих новых гарантий **не подтверждают**.

## Отдельные локальные изменения после согласования

Source records: допустим кандидат на удаление только служебного note/header,
указывающего исключительно на whitespace, с корректными границами и без ссылок
из items/characteristics. Затем заново полная валидация покрытия и однократности.
Product/unresolved, неверные Unicode offsets, повтор IDs, пропущенные строки
нельзя механически удалять; один адресный GPT repair либо отказ без изменения
заявки. Сначала расширить отрицательную матрицу, не вводить сортаментных правил.

«Добавь»: текущий контракт содержит set/regroup/undo и не поддерживает append.
Минимальный путь — GPT выбирает clarify с понятным ограничением, без create_request
вместо добавления. Усилить инструкцию и разделение последнего отклонённого исходника
и активной заявки; историю считать данными, не разрешением на мутацию. Добавление
новой операции и правила объединения исходников — отдельное согласование.
Из пользовательского текста отказа убрать диагностические коды, оставив их в
служебной структурированной диагностике. Эти изменения реализованы в №16.

## Фактическая реализация №16: уточнения первоначального проекта

Нормативное описание реализации ниже уточняет первоначальные предложения выше.

- `queue.py`: steel_v2_inbox/attempt/outbox/queue_meta. Аддитивная транзакционная
  DDL-миграция version=1; неизвестная версия и чужая БД отклоняются. Core-таблицы
  не ALTER-ятся. `queue_runtime.py`: scheduler thread + ограниченный execution pool.
- Один getUpdates остаётся в исходном worker-процессе. Scheduler работает и во
  время long polling. FIFO — по user_id/update_id; билет последнего обслуживания
  задаёт round-robin, новые пользователи присоединяются в конец.
- Text сохраняется точно. Нецелевые/некорректные события с известным update_id
  получают durable rejected. Poll limit=1 ограничивает захват сверх вместимости.
  При рестарте сохранённый receive cursor можно зеркалировать в legacy до poll.
  Исходный legacy offset принимается как baseline лишь при первой установке.
  Последующее опережение legacy offset относительно durable inbox блокирует запуск;
  несогласованное восстановление двух SQLite нельзя замаскировать выбором max.
- `AccessRepository.commit_permission`: BEGIN IMMEDIATE в legacy, проверка approved
  и revision, затем короткий commit в v2, освобождение legacy. Порядок locks:
  legacy → v2. Все SQLite writers, включая другие экземпляры AccessRepository,
  сериализуются этим lock. Admission/API-start/commit/send-start используют gate.
  Во время GPT и обычной доставки write transaction не удерживается. Отзыв после
  API/send-start не отменяет уже разрешённый внешний вызов.
- Admission/execution связаны с revision права. Revoke/reapprove не оживляет старые
  queued/inflight задания. Текст, принятый до выдачи доступа, не становится платным
  заданием задним числом. Существующая история после повторного одобрения сохраняется.
- finish атомарно сохраняет snapshot, version, turn, завершение inflight и полный
  outbox. `committed` сменяется `delivery_pending`. Result_received без commit
  при аварии означает execution_unknown: черновик мог быть потерян, replay запрещён.
- Callback/admin также проходят inbox. Перед старым access.route фиксируется
  access-start; фактические send/answer/edit журналируются до вызова и после receipt.
  Одобрение зависит от реального успешного уведомления, не от постановки в очередь.
  Между legacy access commit и v2 completion нет общей транзакции: авария даёт
  execution_unknown и ручную сверку прав, без повторной transition. Роли не меняются.
- Одобрение сохраняет существующий legacy write lock во время уведомления.
  Socket timeout queue access proxy=3 (не строгий wall-clock deadline). При сбое
  возможен безопасный отказ, но не ложное одобрение. На ожидание GPT lock не держится.
- `/claim` сохранён: только его credential защищается Windows DPAPI до записи
  inbox, не копируется plaintext в history/logs. Hash до шифрования стабилен для
  дедупликации. Расшифровка требует того же Windows account; отказ не выполняет claim.
- Unknown блокирует следующие задания пользователя, но не других. Известная HTTP
  ошибка не повторяется и может завершиться failed turn. SearchUnavailable сохраняет
  outcome_known: сетевой таймаут поиска не маскируется как обычная ошибка проверки.
- Части outbox идут по порядку; send-start предшествует сети, message_id обязателен.
  Неизвестная доставка не повторяется. Можно продолжать лишь не начатые части.
  Pre-queue cached Reply без delivery receipt тоже уходит в delivery_unknown.
- Закрытые payload-копии очищаются, сохраняются 1000 terminal tombstones с hash.
  Более старые ID ниже durable cursor никогда не исполняются заново. Pending/unknown
  не удаляются по сроку. Canonical history сохраняет исходник/ответы/версии; denied
  и ручное закрытие сначала сохраняют обычный исходник в turn. Credentials туда не идут.
- CLI `scripts/v2_queue_status.py`: read-only counts/state/update IDs/opaque confirm,
  без user IDs и переписки. Mutating операции требуют maintenance, свободных обоих
  process locks, совпадения root/handler/database и явного confirm. Разрешение unknown
  — только закрытие без replay/send/отката уже сохранённых данных.
- Старый опубликованный v2 Repository отвергает queue-таблицы и не начнёт polling.
  Это проверено на коде aa11380. При полностью закрытой очереди CLI делает полный
  SQLite backup с integrity/hash manifest вне checkout, сверяет source/backup, затем
  атомарно убирает только четыре operational queue таблицы. Архив сохраняет аудит;
  core/history/offset не заменяются. Менять handler на legacy для обхода gate запрещено.
- Maintenance прекращает admission/scheduling; active операции кооперативно
  завершаются, queued остаются на диске. Два plan и search с timeout=180 могут
  превысить stop timeout=180. Таймаут stop требует ждать/разбирать, не убивать процесс.

Результаты — reports/016-concurrent-queue-implementation.md. Живые API не запускались.
Данное изменение не является разрешением на deployment.

`delivered` означает завершение доставки, а не успешность нормализации: исходный
Reply.status (ok/partial/failed/busy) остаётся отдельным результатом операции.
Ограничения admission могут приостановить общий getUpdates: если первое ещё не
принятое событие принадлежит переполненной пользовательской очереди, нельзя
подтвердить более поздние события без устойчивого решения по этому событию.
Справедливое планирование относится к уже принятым заданиям; защиты от бесконечного
входящего flood отдельного пользователя эта версия не обещает.
