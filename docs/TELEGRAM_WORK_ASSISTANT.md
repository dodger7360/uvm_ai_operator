# Telegram-оператор и рабочий AI-помощник — этап 105

## Границы интеграции

`TelegramService(..., reliable=True, assistant=...)` включает режим надёжного
оператора. Штатная точка запуска `telegram_bot.run_bot` собирает именно этот
вариант. По умолчанию `reliable=False` сохраняет строгий контракт старых
программных клиентов: исключения валидации остаются исключениями. Это режим
совместимости, а не отдельный нормализатор. Workbench не переключён на новый
Telegram-режим.

Нормализация и интерпретация правок остаются в `AIService` и используют
`client.beta.chat.completions.parse` с существующими схемами, настройками модели,
low и medium fallback. Промпты нормализатора, нормативный справочник и
коммерческие решения не изменены.

Новый `WorkAssistantService` получает `AIService.assistant_transport`: тот же
настроенный OpenAI-клиент, ключ и прокси. Он не читает `.env`, не хранит второй
ключ и не отключает TLS. Его копия клиента задаёт собственный тайм-аут и запрет
SDK-повторов, не меняя настройки нормализатора.

## Возврат заявки

1. Успешный существующий путь возвращает проверенную нормализацию.
2. При ошибке оператор независимо проверяет подходящие позиции уже полученного
   AI-черновика теми же `_build_active`, source coverage и validator. Если
   варианты черновиков противоречат друг другу, первый вариант не выбирается.
3. Остальные строки пробует общий локальный RecognitionService, без GPT,
   справочника или подключения к БД. Мост в RequestItem использует известные
   поля и снова проходит те же проверки. Поддерживаются только локальные
   категории RecognitionService; другие остаются исходными строками, если
   проверенного AI-черновика нет.
4. Возвращаются явно обозначенная частичная нормализация и **полный исходный
   текст**, включая заголовки, примечания и нераспознанные строки. При полном
   отказе возвращается исходный текст с пояснением.

Непроверенные значения не выдаются за нормализованные. Одно неудачное изделие
не препятствует восстановлению других. Восстановление не делает дополнительных
платных вызовов. Штатный повтор low → medium при истинной неполноте сохранён.

Успешно сохранённая новая заявка, включая исходный fallback, создаёт новый
request_id; прежняя остаётся в telegram_history. Добавлены только поля JSON
ActiveRequest: `fallback_status`, `unprocessed_source`, `recovery_specs`.
Последнее поле сохраняет NomenclatureSpec с Decimal и provenance. Геометрия
legacy RequestItem по-прежнему float; точные локальные величины доступны в
recovery_specs. Таблицы SQLite и существующие записи не мигрируются.

Уточнения показываются после результата; повторяющиеся вопросы объединяются,
неизвестные строки перечисляются кратко. Известные марки, ГОСТ и количества
не запрашиваются заново. Отсутствующая марка остаётся отсутствующей; обязательные
характеристики определяет прежний validator, не новая коммерческая эвристика.

Пример неполной позиции:

```
Труба профильная 80×40 Ст3 — 2 т

Вопросы по заявке:
Укажите толщину стенки ...
```

При сбое извлечения:

```
Частичная нормализация; требуется проверка:
Уголок 50×50×5 Ст3 ГОСТ 8509-93 — 2 т

Исходная заявка сохранена без изменений:
Уголок 50х50х5 Ст3 ГОСТ 8509-93 — 2 т
Изделие ZZZ 91х13 — 7 шт

Вопросы по заявке:
Уточните наименование и характеристики нераспознанных строк: «Изделие ZZZ 91х13 — 7 шт».
```

Если БД недоступна, текст возвращается без утверждения о сохранении. Отозванное
право доступа не обходится. Физическая доставка при недоступном Telegram или
сети не гарантируется: исходный текст хранится при доступной SQLite, но отдельной
очереди доставки в этом этапе нет.

## Маршрутизация и контекст

Локальный маршрутизатор отделяет явные рабочие вопросы от новых перечней,
команд исправления и показа. Отдельного платного AI-классификатора не добавлено.
Неоднозначное сообщение в активном контексте вызывает один короткий вопрос.
Невозможно доказать правильное намерение для любого произвольного естественного
текста; неподдержанные формулировки следует проверять отдельно.

Рабочий вопрос получает снимок текущей заявки, исходный текст и текущие
технические поля после исправлений. Он не сохраняет новую версию, не сбрасывает
уточнения, не изменяет исходные характеристики и не создаёт глобальных правил.
Исходный текст передаётся как JSON-данные, а не системная инструкция. Доступен
только web_search, без отправки писем/сообщений или выполнения внешних действий.
Технические замены автоматически не принимаются.

## Responses API и Web Search

Проверено по официальной документации 15.10.2026:

- [GPT-6 Luna](https://developers.openai.com/api/docs/models/gpt-6-luna):
  API ID `gpt-6-luna`, Responses API, `reasoning.effort=low`, Web Search.
- [Web Search](https://developers.openai.com/api/docs/guides/tools-web-search):
  инструмент `web_search`, обязательный поиск через tool_choice, URL-citations.

Доступ конкретного OpenAI-аккаунта и корпоративной сети не проверялся реальным
запросом. Установленный SDK 3.19.2 имеет Responses.create и необходимые
параметры; новые зависимости не нужны. Нет автоматической подмены модели.

Ответы на известные понятия не включают поиск. Явный запрос поиска,
актуальные/действующие документы, производители, поставщики и текущие цены
включают `tools=[{'type':'web_search','search_context_size':'low'}]`,
`tool_choice='required'`, `max_tool_calls=1`. Поиск не вызывается при обычной
нормализации заявки. Правила выбора поиска локальные и не исчерпывающие.

Пользователь видит URL из реальных url_citation-аннотаций ответа. Нет выбора
первого справочного кандидата или признания коммерческого аналога технической
заменой. Если поиск недоступен/не выполнен/не вернул безопасные цитаты,
актуальный ответ не выдаётся: пользователь получает пояснение, что актуальность
не проверена. Второго вызова без поиска и смены модели нет. Отказ/пустой/
незавершённый ответ также не выдаётся за завершённый результат.

## Лимиты и диагностика

- Один Responses-вызов на рабочий вопрос, SDK max_retries=0.
- Тайм-аут 60 секунд, max_output_tokens=2500, store=false.
- Вопрос до 8 000 символов. Исходный контекст и технические поля ограничены
  12 000 символов каждый; при превышении контекст исключается целиком, и это
  явно сообщается пользователю. Скрытого обрезания характеристик нет.
- Скользящий час: 100 вопросов на процесс, 20 на пользователя, 30 вопросов с
  поиском на процесс. Неуспешная попытка тоже расходует локальный лимит.
- Лимиты защищены от конкурентного резервирования. Они непостоянные и
  сбрасываются при перезапуске; это не денежный лимит OpenAI-аккаунта.
- Диагностика фиксирует модель, reasoning, длительность, безопасную категорию
  ошибки, число web_search_call, input/output/total tokens. Не пишет тексты,
  URL с ключами, исключения с телами ответа, user_id или содержимое заявки.
- Денежная стоимость и внутренние сетевые подоперации hosted web search
  контролируются тарифами и лимитами OpenAI; здесь не выдумываются цены.

Тайм-ауты/SDK-повторы прежней нормализации не изменены. Она может занимать
существенное время до перехода в fallback. Индикатор typing сохраняется.

## Telegram-форматирование

Вопросы помечаются отдельным типом ClarificationMessage. Только этот тип
включает HTML: все данные экранируются, доверенный заголовок выделяется жирным.
При HTTP 400 HTML повторяется обычным текстом; при сетевом результате с
неизвестной доставкой автоматического повторного sendMessage нет.
Длинные исходные строки делятся с учётом UTF-16, без потери символов. Обычная
заявка и AI-ответ не получают интерпретируемую HTML-разметку.
