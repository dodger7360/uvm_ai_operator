# PROMPTING — AI Development Rules

Этот документ определяет правила подготовки задач для ChatGPT, Codex и Cursor в проекте «ТГ Бот: Оператор снабжения».

Документ относится к **процессу разработки**, а не к runtime-логике Telegram-бота.

---

## 1. Цель

Каждая задача для AI-агента должна быть:

- конкретной;
- ограниченной по области;
- проверяемой;
- совместимой с текущей архитектурой;
- понятной без необходимости угадывать намерения пользователя.

Главный принцип:

> Сначала понять состояние проекта и границы задачи, затем изменять код.

---

## 2. Контекст проекта

Основной стек:

- Python
- Telegram Bot API
- OpenAI API
- SQLite
- Git / GitHub

Архитектурные решения:

- SQLite используется сейчас.
- PostgreSQL рассматривается как следующий этап.
- AI-вызовы централизуются через `AIService`.
- Telegram handlers не должны содержать основную бизнес-логику.
- AI не является источником истины.
- Бизнес-правила реализуются в Python и базе данных.
- Источники данных подключаются через отдельные адаптеры.
- Секреты хранятся в `.env` и никогда не попадают в Git.

Первый эталонный товар для разработки и тестирования:

**Арматура Ø12 А500.**

---

## 3. Формат задач для Codex / Cursor

Для сложных задач использовать структуру:

```text
Goal
Context
Scope
Constraints
Approval Boundaries
Done
Verification
```

### Goal

Что именно нужно получить.

### Context

Только необходимый контекст проекта и уже принятые решения.

### Scope

Какие файлы, модули или директории можно изучать и изменять.

### Constraints

Что обязательно соблюдать и что запрещено менять.

### Approval Boundaries

Что требует остановки и подтверждения пользователя.

### Done

Проверяемый критерий завершения.

### Verification

Какие тесты, команды или реальные примеры должны подтвердить результат.

---

## 4. Границы работы AI-агента

AI-агент может самостоятельно:

- изучать код;
- искать зависимости между файлами;
- исправлять локальные ошибки;
- добавлять тесты;
- выполнять безопасные проверки;
- изменять файлы внутри согласованного scope.

AI-агент должен остановиться и спросить пользователя перед:

- удалением файлов;
- удалением существующего функционала;
- изменением схемы БД;
- миграцией SQLite → PostgreSQL;
- добавлением новых внешних сервисов;
- добавлением существенных зависимостей;
- изменением архитектуры;
- изменением публичных интерфейсов;
- изменением поведения за пределами поставленной задачи.

---

## 5. Работа с архитектурой

AI-агент не должен самостоятельно менять архитектурные решения проекта.

Если задача требует изменения архитектуры, необходимо сообщить:

```text
ARCHITECTURAL DECISION REQUIRED
```

и описать:

1. какое решение предлагается изменить;
2. почему текущая архитектура не позволяет выполнить задачу;
3. какое изменение предлагается;
4. какие последствия оно имеет.

Без подтверждения пользователя архитектурное решение не менять.

---

## 6. AI и данные

AI может:

- распознавать пользовательские заявки;
- нормализовать названия товаров;
- структурировать данные;
- анализировать предоставленный контекст;
- формировать итоговый текст ответа.

AI не должен самостоятельно считаться источником фактических данных.

Нельзя принимать от AI как факт:

- цену;
- остаток;
- наличие;
- характеристики товара;
- данные поставщика;
- данные склада;
- новости;
- результаты парсинга.

Если фактические данные отсутствуют или не подтверждены источником, система должна явно обозначить это.

Предпочтительный поток:

```text
User Input
    ↓
AIService
    ↓
Structured Data
    ↓
Python validation
    ↓
Business Logic
    ↓
Database / Sources
```

## 7. Режимы работы

### LEARNING

Использовать, когда пользователь хочет изучить программирование.

AI должен:

- объяснить необходимую концепцию;
- дать небольшую практическую задачу;
- позволить пользователю написать код самостоятельно;
- проверить код;
- объяснить ошибки;
- не выполнять всю задачу вместо пользователя без необходимости.

Особенно применять для:

- базового Python;
- функций;
- классов;
- словарей и списков;
- JSON;
- exceptions;
- `.env`;
- SQLite;
- SQL;
- тестов;
- pandas.

### WORK

Использовать для инженерной работы, которую эффективнее выполнить AI-агенту:

- рефакторинг;
- работа с несколькими файлами;
- интеграции;
- парсеры;
- сложная бизнес-логика;
- тестирование;
- повторяющиеся изменения;
- архитектурно определённые задачи.

Если пользователь не указал режим, выбрать подходящий и кратко объяснить выбор.

---

## 8. Правило минимального scope

Не давать агенту задачу:

> «Переделай весь проект».

Предпочтительно:

> «Изучи X, измени Y, не трогай Z».

AI-агент должен изменять только то, что необходимо для поставленной задачи.

Не добавлять:

- ненужные абстракции;
- ненужные зависимости;
- дополнительные функции;
- новые сервисы;
- незапрошенные рефакторинги.

---

## 9. Безопасность

Никогда не включать в промпты:

- API keys;
- Telegram tokens;
- пароли;
- cookies;
- connection strings;
- значения `.env`.

Использовать только имена переменных:

```text
OPENAI_API_KEY
TELEGRAM_BOT_TOKEN
```

Секреты не должны попадать в Git.

---

## 10. Проверка результата

Каждая задача должна иметь критерии завершения.

Минимальный стандарт:

```text
Done when:
- requested functionality works;
- relevant tests pass;
- existing functionality is not broken;
- no secrets were added;
- changed files are listed;
- verification results are reported.
```

Для критических задач использовать реальный пример.

Первый основной пример проекта:

```text
Арматура Ø12 А500
```

---

## 11. Контекст предыдущей работы

Если задача продолжает предыдущую работу, в промпт передаются только решения, которые влияют на текущую задачу.

Не нужно копировать всю историю проекта.

Минимальный контекст:

```text
## Project Context

- Python Telegram bot
- SQLite now, PostgreSQL later
- AI calls through AIService
- AI is not source of truth
- Business logic outside Telegram handlers
- First reference product: rebar Ø12 A500
- Do not change architecture without approval
```

---

## 12. Главный принцип

AI-агент является инструментом разработки, а не владельцем архитектуры проекта.

Приоритет решений:

1. Явное решение пользователя.
2. `PLAN.md`
3. `DECISIONS.md`
4. `ARCHITECTURE.md`
5. `TASKS.md`
6. Текущая реализация.
7. Предположение AI.

Если новая задача противоречит существующему решению, конфликт должен быть обозначен до изменения архитектуры.

---

## 13. Критерий хорошего промпта

Хороший промпт:

- однозначно определяет задачу;
- содержит необходимый контекст;
- ограничивает scope;
- определяет запрещённые действия;
- определяет момент остановки;
- содержит проверяемый результат;
- не содержит лишней теории.

Главная цель:

> Получить правильный результат с первого запуска без серии перепромптов.
