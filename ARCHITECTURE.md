# Architecture

Историческая архитектура прежнего контура. Активная архитектура Telegram —
[Steel Agent v2](docs/steel-agent-v2/ARCHITECTURE.md), продукт —
[PRODUCT.md](docs/steel-agent-v2/PRODUCT.md), состояние —
[PROJECT_STATE.md](docs/steel-agent-v2/PROJECT_STATE.md).
Схемы AIService/InventoryService/MarketService ниже не являются действующим
маршрутом v2 и не подтверждают подключение источников.

## 1. Общая схема

Целевая архитектура проекта:

```text
                         Telegram
                            │
                            ▼
                    Application Layer
                            │
                            ▼
                    Business Logic
                            │
          ┌─────────────────┼─────────────────┐
          │                 │                 │
          ▼                 ▼                 ▼
      AIService      InventoryService    MarketService
          │                 │                 │
          │                 │          ┌──────┼──────┐
          │                 │          │      │      │
          │                 │          ▼      ▼      ▼
          │                 │       MSK    EKB   Склады
          │                 │
          └─────────────────┼─────────────────┘
                            │
                            ▼
                       Repositories
                            │
                            ▼
                          SQLite
```

---

## 2. Основные слои

### Telegram Layer

Отвечает только за взаимодействие с пользователем.

Задачи:

- получение сообщений;
- получение файлов;
- отправка ответов;
- обработка команд;
- передача данных в application layer.

Telegram handlers не должны содержать бизнес-логику.

---

### Application Layer

Оркестрирует выполнение пользовательского сценария.

Например:

```text
Пользователь:
"Нужна арматура 12 А500 20 тонн в Москве"
```

Application layer:

1. принимает запрос;
2. передаёт текст в AIService;
3. получает Structured Request;
4. валидирует результат;
5. запускает поиск собственного остатка;
6. рассчитывает дефицит;
7. при необходимости запускает MarketService;
8. собирает факты;
9. передаёт факты в AI для формирования ответа;
10. возвращает результат в Telegram.

---

## 3. Business Logic

Бизнес-логика не должна зависеть от Telegram.

Основные направления:

- обработка заявок;
- расчёт дефицита;
- проверка остатков;
- поиск по складам;
- поиск рыночных предложений;
- сравнение вариантов;
- подготовка данных для закупочного решения.

---

## 4. AIService

`AIService` — единая точка взаимодействия с AI.

Основные задачи:

- отправка запросов модели;
- parsing свободного текста;
- получение Structured Request;
- нормализация данных;
- формирование итогового ответа;
- обработка ошибок API;
- контроль модели и параметров;
- логирование необходимых технических данных.

AIService не хранит бизнес-логику.

AI не является источником истины.

---

## 5. InventoryService

Отвечает за собственные остатки компании.

Основные задачи:

- импорт данных из Excel;
- нормализация номенклатуры;
- поиск товара;
- определение доступного количества;
- расчёт дефицита;
- работа со складами.

Источник данных на текущем этапе:

```text
Excel
  ↓
Python import
  ↓
Validation / normalization
  ↓
SQLite
```

---

## 6. MarketService

Единый интерфейс для работы с внешним рынком.

Пример:

```text
MarketService
      │
      ├── MetalserviceMoscow
      │
      ├── MetalserviceEkb
      │
      └── MoscowWarehouses
```

Каждый источник реализуется отдельным адаптером.

Основная бизнес-логика не должна зависеть от конкретного сайта.

---

## 7. ContextService

Отвечает за дополнительный рыночный контекст.

Источники:

- пользовательские наблюдения;
- новости;
- информация о рынке;
- события;
- комментарии поставщиков;
- другие проверенные источники.

Контекст должен храниться с указанием:

- даты;
- источника;
- типа информации;
- текста;
- при необходимости уровня достоверности.

Важно различать:

```text
Факт
↓
Наблюдение
↓
Гипотеза
```

AI не должен превращать гипотезу в факт.

---

## 8. Repository Layer

Repository отвечает за работу с хранилищем.

Пример:

```text
ProductRepository
RequestRepository
InventoryRepository
WarehouseRepository
MarketPriceRepository
ContextRepository
```

Business Logic не должна напрямую зависеть от SQL-запросов.

---

## 9. Database

На текущем этапе:


Целевые основные сущности:


## 11. Правило источника истины

При конфликте между AI и фактическими данными:


а не предположение.

## 13. Принципы разработки

### Single Responsibility

Каждый модуль отвечает за одну область.

### Separation of Concerns

Telegram, AI, бизнес-логика, БД и источники данных разделены.

### Replaceability

Внешние источники можно заменять без переписывания всей системы.

### Testability

Критическая бизнес-логика должна тестироваться без Telegram и без реального AI API.

### Explicit Data

Между слоями используются понятные структурированные модели.

### Minimal Complexity

Не добавлять инфраструктуру, которая не нужна текущему этапу.

## 14. Что не должно находиться в Telegram handlers

Запрещено помещать туда:

- SQL-запросы;
- расчёт дефицита;
- бизнес-правила закупки;
- парсинг сайтов;
- обработку Excel;
- прямую работу с AI API;
- сложную нормализацию товаров.

Handlers должны оставаться тонкими.

## Работающий Telegram-нормализатор — 13.10.2026

`main.py → telegram_bot.handle_update → TelegramService → AIService →
PurchaseRequest → normalize_request → validate_request → sort_items →
ordered_consolidation → format_normalized_request → sendMessage`.
Существующий консольный Workbench и supplier formatter сохранены.

Telegram принимает личные текстовые сообщения без /normalize. /start и /help
показывают инструкцию. Вызовы AI сосредоточены в AIService: parse_request для
нового перечня, interpret_message для классификации сообщения и правок.
Обработчики не выполняют SQL и не содержат предметных правил.

TelegramRepository использует существующий Database и добавляет три таблицы:
telegram_active (ключ user_id, JSON активной заявки), telegram_history
(неизменяемые снимки новых заявок и правок), telegram_state (offset polling).
Существующие таблицы и данные не удаляются. ActiveRequest содержит request_id,
полный source_text и упорядоченный список ActiveItem. Каждая позиция хранит
стабильный item_id, исходную строку, текущие поля и original — первоначальный
структурированный снимок после безопасной нормализации и проверки.
Изоляция контекста идёт по Telegram user_id. Decimal сохраняется JSON-строкой.

Единственный локальный процесс защищён Windows файловой блокировкой.
Существующий webhook не удаляется: запуск прерывается для проверки.
Telegram 409 о конфликтующем polling также завершает процесс.
Offset сохраняется после отправки всех частей ответа. Если процесс упадёт
между отправкой и сохранением offset, повторный ответ возможен: exactly-once
доставка в MVP не гарантируется. Polling последовательный; длинный AI-запрос
может задержать обработку других пользователей.

### Запуск и восстановление для обслуживающего специалиста

Секреты: локальный .env, исключённый из Git. Нужны OPENAI_API_KEY и
TELEGRAM_TOKEN (также принимается TELEGRAM_BOT_TOKEN). OPENAI_MODEL по умолчанию
gpt-5.6-luna. OPENAI_PROXY при необходимости направляет только OpenAI через
существующий SOCKS-прокси; глобальная сеть не перенастраивается. OPERATOR_DB
по умолчанию operator.sqlite3 в папке проекта. Зависимости — requirements.txt.

Запуск: start-telegram.ps1 открывает фоновый pythonw main.py без окна терминала.
Повторный запуск безопасно отклоняется файловой блокировкой. Журнал telegram.log
пишет только состояния, типы ошибок, user_id и количество частей ответа,
без текстов заявок, URL с токеном, ключей и полных исключений API.
Для восстановления после остановки повторно запустить start-telegram.ps1.
SQLite сохраняет заявку, историю и polling offset. Не удалять базу и не менять
offset для восстановления. При 401 проверить локальный токен; при 409 найти
другой экземпляр; при отказе OpenAI проверить настроенный локальный прокси.
Запуск не является установкой Windows-службы: выключение компьютера, завершение
сеанса или остановка прокси прерывает доступность, автоматического перезапуска
после перезагрузки пока нет.

### Проверки и реальные материалы

tests/test_telegram.py проверяет стали и категории, точность, дубли, стабильные
идентификаторы, правки и восстановление, новую заявку, двух пользователей,
атомарность, пропущенные строки, split ответов и обработчик Telegram.
tests/test_real_request_fixtures.py проверяет структурированную сохранность
двух имеющихся материалов: 10 балок и 27 листов. Provenance сохранён в JSON.
Это существующие подготовленные артефакты проекта, а не оригиналы ненормализованных
заявок: потерянные до этого категории по ним восстановить нельзя.
Исходные наборы 21 смешанная позиция, 38 уголков/швеллеров и 26 прочих позиций
не найдены; необходимы реальные тексты для покрытия этих трёх групп.
Live AI-проверка отдельно проверяет четыре позиции, замену марки, количество,
восстановление и затем извлечение имеющихся реальных наборов.


Проверка 13.10.2026: 145 автоматических тестов прошли; реальные AI-прогоны
имеющихся наборов 10 / 27 позиций прошли с контролем количества и стандартов.
Успешный getMe установил @UVM_SteelBot; фоновый polling получил личное сообщение
и отправил ответ. Это подтверждает Telegram транспорт; проверка нормализованного
перечня в реальной переписке остаётся пользовательским приёмочным сценарием.
Прямой доступ OpenAI получил unsupported_country_region_territory; настроенный
ранее локальный SOCKS-прокси обеспечивает успешный запрос. Прокси не заменён.
Схема Decimal для Structured Outputs публикуется как строка без неподдерживаемого
lookaround; BeforeValidator принимает десятичные точку и запятую.
API-схема сверена с официальной документацией:
https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=chat


По отдельной команде оформления тоннажа («тоннаж приведи к виду 0,100т,
три знака после запятой») активная заявка сохраняет tonnage_decimals=3
(также поддерживается 2). Отображение округляется ROUND_HALF_UP, нули
сохраняются, перед т пробела нет. Пример: 0,0015 → 0,002т.
Исходное и текущее количество Decimal не изменяются. Другие единицы
не затрагиваются. Настройка сохраняется при правках этой заявки;
новая заявка начинает с точного формата без округления. При формулировке
«три знака, либо два» выбирается первый указанный вариант — три.


Общая шапка листов: блок «лист ГК ГОСТ 19903 Ст.09г2с раскрой 1,5*6м:»
с последующими строками «толщина — количество единица» разворачивается перед
AI-разбором, только если вся область применения однозначна. Явный раскрой в
метрах переводится в миллиметры (1500×6000), тип, марка и ГОСТ переносятся в
каждую позицию. Смешанные строки и раскрой без единиц этим правилом не
интерпретируются. Полный исходный текст хранится в ActiveRequest.source_text;
в ActiveItem.source_text остаётся исходная строка, source_context хранит шапку.
Отдельные марки стали не заменяются: Ст.09г2с оформляется как Ст09Г2С.


## Управление доступом Telegram — 13.10.2026

Авторизация внедрена перед нормализатором:
`handle_update → TelegramAccess.route → AccessRepository → TelegramService`.
Команды доступа и callback-запросы обрабатываются без AI. Нормализатор,
его правила, Metalservice, Bitrix24 и inventory этим изменением не затронуты.
Идентификатор доступа — только фактический числовой `message.from.id` или
`callback_query.from.id`. Имя и username используются только для отображения.
Разрешена работа только со статусом approved; первоначальный admin также approved.
При отсутствии администратора доступ закрыт. /start не назначает владельца.
Обычные сотрудники не могут выполнять административные команды или callbacks.
Callback допускается только в личном чате фактического отправителя.

### Первоначальная привязка администратора

Есть два подтверждённых способа. Для заранее подтверждённого ID обслуживающий
специалист задаёт ADMIN_TELEGRAM_ID в локальном .env. Конфликтующий ID не
перезаписывает существующего администратора: запуск прекращается с ошибкой.
Для владельца, подтвердившего одноразовую привязку, обслуживающий специалист
создаёт случайный код `secrets.token_urlsafe(24)` и передаёт его владельцу через
доверенный канал. `AccessRepository.issue_binding` сохраняет только SHA-256 и
срок действия 30 минут. Владелец отправляет `/claim <код>` самому боту. Сервер
привязывает фактический from.id, а не номер из текста. Код одноразовый и не
принимается после назначения администратора. SQLite-транзакция и уникальный
индекс защищают от двух параллельных привязок. Для одного Telegram ID допускается
пять попыток ввода за 30 минут. Код не записывается в журнал или Git.
Переиздать истёкший код может только обслуживающий специалист после подтверждения
владельца; публичной команды генерации кода нет. В этом развёртывании выбран /claim.

### Работа сотрудника и администратора

Новый сотрудник нажимает /start → «Запросить доступ». Бот сохраняет pending,
уведомляет администратора (имя, username, ID) и показывает кнопки «Одобрить» /
«Отклонить». Повторное нажатие не создаёт запись или повторное уведомление.
Если уведомление администратора не доставлено, pending сохраняется; повторная
попытка уведомления возможна не чаще раза в минуту при повторном нажатии.
В отсутствие администратора запрос сохраняется и становится виден после привязки.

Команды администратора:
- /users — имена, username, статусы, кнопки одобрения или отзыва.
- /pending — ожидающие запросы с двумя кнопками решения.
- /revoke — сотрудники с доступом и кнопка «Отозвать доступ».
- /approve — неодобренные сотрудники, включая rejected и revoked.

После approved сотрудник получает уведомление и может прислать новую заявку.
Если уведомление о предоставлении доступа не доставлено, транзакция одобрения
откатывается: доступ не выдаётся. Администратор повторяет действие, когда сотрудник
снова открыл бота. При rejected/revoked повторное нажатие запроса не уведомляет
администратора; повторное предоставление происходит только через /approve или
/users. Отзыв вступает в силу независимо от доставки уведомления сотруднику.
Единственный admin не отображается в списках сотрудников и не может быть отозван.

Все кнопки содержат текущую revision записи. Решение выполняется по CAS в
BEGIN IMMEDIATE с повторной проверкой роли actual actor внутри транзакции.
Повторное решение, устаревшая кнопка или поддельный callback не выдаёт доступ.
Административные команды показывают только данные доступа, не чужие заявки.

### SQLite и сохранение контекста

Миграция добавочная и идемпотентная, через существующий Database.connection:
- telegram_access_user: user_id, role, status, display_name, username,
  requested_at, approved_at, changed_at, acted_by, revision, context_floor,
  admin_notified_at и время последней попытки уведомления.
- telegram_access_event: история решений, actor и время.
- telegram_access_bootstrap: единственный хеш привязки и срок действия.
- telegram_access_claim_attempt: ограничение попыток привязки по ID и времени.

Существующие таблицы, заявки и снимки не удаляются. AuthorizedRequestRepository
использует прежний TelegramRepository и дополнительно запрещает чтение/запись
неодобренным. При одобрении сотрудника context_floor фиксирует последний снимок;
старая активная заявка скрыта, пока сотрудник не отправил новую. Это действует
и после повторного одобрения revoked. Старые данные остаются в истории. Явное
восстановление чужой заявки администратором в MVP не реализовано. При первой
привязке admin его собственная активная заявка сохраняется доступной.
После обработки дополнительно проверяется статус перед отправкой ответа.

### Перезапуск и ограничения

start-telegram.ps1 запускает тот же единственный фоновый polling-процесс.
Разрешения, admin, очередь pending, revision и граница активного контекста
сохраняются в operator.sqlite3. Перезапуск не требует повторной привязки.
При восстановлении сохранять базу, не редактировать права SQL вручную и не
назначать первого /start-пользователя. Код выдаётся только если admin отсутствует.
Polling теперь получает message и callback_query. В журнале новых обработок
нет Telegram ID, имён, содержимого заявок, callback_data или кода привязки.

Для небольшого отдела команды показывают до 25 записей за вызов; пагинация
не реализована. Проверенные решения убирают записи из /pending, открывая
следующие при превышении лимита. Уведомление при одобрении выполняется внутри
короткой SQLite-транзакции: при медленной сети возможна задержка управления.
Exactly-once доставка уведомлений не гарантирована при падении процесса между
ответом Telegram и фиксацией транзакции. Windows-автозапуск и смена владельца
не добавлены; действуют ранее описанные ограничения фонового запуска.

tests/test_access.py проверяет закрытый доступ, отсутствие AI-вызовов и чтения
контекста, /start, запросы, отсутствие дублей, одобрение, отклонение, отзыв,
поддельные и старые callbacks, команды, уведомления, параллельные решения,
сохранение после рестарта, изоляцию заявок, повторное одобрение, сохранение
контекста владельца, одноразовую привязку, истечение и ограничение попыток.

Проверка развёртывания: 184 автоматических теста проходят. Владелец выполнил
/claim в Telegram; назначение администратора и собственный прежний контекст
подтверждены. Повторное создание AccessRepository сохраняет права. Проверка
постороннего через действующий контроллер с mock Telegram не вызвала
нормализатор. getMe подтвердил @UVM_SteelBot. Полный сценарий второго
сотрудника (запрос / одобрение / отзыв) проверен автоматически; его реальная
проверка выполняется с отдельного Telegram-аккаунта.


## GPT-6 Luna и стабилизация обработки — 13.10.2026

Действующая конфигурация после этой миграции:
OPENAI_MODEL=gpt-6-luna, OPENAI_REASONING_EFFORT=low,
OPENAI_FALLBACK_REASONING_EFFORT=medium. Оба сценария AIService используют
один _invoke и тот же model. API остаётся Chat Completions; строгие исходные
PurchaseRequestExtraction и MessagePlan сохранены. Temperature, top_p и
дополнительный искусственный лимит токенов не добавлены. Существующие timeout
120 секунд, SDK openai 3.19.2 и сетевые retries=2 сохранены. Прокси не заменён.
Поддержка reasoning и Structured Outputs сверена с официальной страницей:
https://developers.openai.com/api/docs/models/gpt-6-luna
Вызовы без function tools совместимы с Low. Работа API подтверждена реальной
заявкой из пяти труб; повтор после исправления форматирования прошёл на Low
за один логический AI-вызов. Два живых прогона за всю задачу: первоначальный
обнаружил разделительный дефис в ГОСТе, второй проверил точный ожидаемый текст.

### Граница Low → Medium

TelegramService делает не более двух попыток на этап: базовую Low и одну
резервную с OPENAI_FALLBACK_REASONING_EFFORT. Повтор допускается только для
SemanticExtractionError с явными причинами: source_fragment_mismatch,
missing_positions, merged_positions, unsupported_attributes, header_mapping,
header_positions_missing или edit_target_mismatch. Перед повтором извлечения
проверяется наличие исходных количеств в распознаваемых товарных строках.
При отсутствии количества повтор не выполняется. Эта проверка консервативна:
необычные табличные формы без явной единицы могут не получить Medium.

Ошибки транспорта, 401/403/404/400 API, Pydantic/JSON-схемы, отказ модели,
обрыв по длине, ошибки Python и прав доступа не запускают Medium.
SDK может отдельно повторять сетевые запросы; calls считает логические
вызовы приложения. HTTP hook отдельно считает http_attempts и sdk_retries
по x-stainless-retry-count, без записи URL, заголовков и содержимого. Кандидат полностью проверяется
на копии до save, поэтому неудачная Low-попытка не меняет активную заявку и
корректировки не применяются дважды. Medium покрыт автоматическими тестами;
отдельный платный Medium-прогон не выполнялся, поскольку рабочая заявка прошла Low.

### Новая заявка и уточнения

Самостоятельная товарная строка с количеством или поддержанная общая шапка
имеют приоритет над предыдущей заявкой и её pending_clarification. Новая
полноценная заявка обычно требует один AI-вызов извлечения, без классификатора.
Явные команды изменений направляются в interpret_message. Нестандартный
неполный текст может по-прежнему использовать классификатор перед извлечением.

ActiveRequest дополнен initial_extraction — неизменяемым первоначальным
структурированным результатом выбранной успешной попытки. Полный исходный
пользовательский текст и исходные снимки каждой позиции остаются сохранёнными.
pending_clarification содержит request_id, item_id, field, kind, question,
candidate и options. Это часть прежнего JSON активной заявки в SQLite;
отдельной БД или новой таблицы не требуется. kind: number, unit, confirmation,
choice. Поддерживаются количество и единица измерения. Число отвечает только
на ожидаемый вопрос; номер выбирает вариант только при kind=choice. «Да»
подтверждает только сохранённое предложение, «нет» отклоняет его и запрашивает
правильное значение. Ответ «70х70х5 в штуках» на вопрос о единице меняет только
единицу, затем «28» закрывает вопрос о количестве. Завершённое уточнение не
возобновляется от отдельного «1» без ожидающего вопроса. Ответы сохраняются в
clarification_answers, первоначальные поля original не перезаписываются.
Новое сообщение и явная команда изменения могут прервать ожидающее уточнение.
Неоднозначные вопросы для нескольких позиций без явного номера не привязываются
автоматически. Уточнения произвольных геометрических полей и марок отдельными
короткими ответами пока не поддерживаются: используются явные команды/новая заявка.

### Причина пяти труб и диагностика

Ошибка воспроизведена локально: exact_source_attributes отклонял любые две
марки, включая явную альтернативу «ст3 (или ст.20)». Теперь такие альтернативы
сохраняются целиком в одном grade. Сортировка и количества не изменяются.
Точный живой тест дополнительно обнаружил захват разделительного дефиса после
ГОСТ 10704-91- перед количеством; этот дефис теперь не входит в стандарт.
Для круглой трубы с явно указанным ГОСТ 10704 название оформляется «Труба э/с»
согласно утверждённому ожидаемому результату данной задачи.

diagnostics.py пишет JSON-события ai_call, medium_retry, processing_error и
operation_complete: случайный operation_id, этап, класс исключения и безопасный
код причины, source_count/extracted_count, модель, reasoning, Medium, длительность,
calls и stage_calls. Возвращённые usage включают входные/выходные/кэшированные/
reasoning-токены. При ошибке до доступного ответа usage может отсутствовать.
Данные log не содержат пользовательских текстов, полного ответа модели, Telegram
ID, токенов или ключей. Число исходных позиций — оценка по распознаваемым строкам,
а не гарантированное количество произвольной таблицы. Для оценки стоимости можно
задать OPENAI_INPUT_USD_PER_MILLION, OPENAI_CACHED_INPUT_USD_PER_MILLION и
OPENAI_OUTPUT_USD_PER_MILLION; без заданного тарифа стоимость не вычисляется.
Это приблизительная оценка, не счёт провайдера. В текущем .env тарифы не заданы.
Bot handler показывает конкретное безопасное уточнение из PipelineError;
программные и API-ошибки фиксируются кодом и не скрываются Medium-повтором.

## Индикатор обработки Telegram

После проверки доступа бот запускает отдельный поток sendChatAction
с action=typing одновременно с обработкой текста. Пока выполняется TelegramService (включая Low/Medium), отдельный
поток обновляет действие примерно раз в 4 секунды. После обработки или исключения
новые обновления прекращаются; ожидание потока ограничено 50 мс. Уже начатый
HTTP-запрос индикатора может завершиться после отправки ответа. Telegram отображает стандартное
«печатает…», без дополнительных сообщений в тексте заявки. Действие имеет
HTTP timeout 3 секунды; его ошибка записывается безопасным кодом и не отменяет
нормализацию. Для /start, административных команд и закрытого доступа поток
не запускается. Тесты проверяют повторение, остановку, ошибки и проверку доступа.


## Стабилизация и измерения на Mac — 13.10.2026

Подтверждённые воспроизведения на fb112b1:
- AIService разрешал различия пунктуации в исходном фрагменте, но проверка
  полноты TelegramService сравнивала `*` и `×` буквально. Корректные пять труб
  отклонялись как missing_positions, после чего следовал бесполезный Medium.
- Подготовка листов принимала одну шапку только в начале сообщения, а проверка
  полноты принимала шапку за товарную строку. Смешанная заявка из 21 позиции
  с двумя шапками не сохранялась. Теперь разворачивается каждый отдельный блок,
  шапки исключаются из товаров, соответствие исходной строки сохраняется.
- Ответ «новую» не имел собственного состояния и мог попасть в извлечение.
  ActiveRequest.dialog_state теперь active / choose_request / awaiting_new,
  с default=active для старого JSON. Выбор сохраняется в прежнем JSON SQLite,
  без новых таблиц; старая заявка остаётся до успешного сохранения новой.

Полная новая заявка имеет приоритет над pending_clarification, без AI-классификации.
После «новую» даже неполный новый перечень товаров обрабатывается как новая
заявка, не как ответ на прежнее уточнение. Приветствия не отправляются в AI;
обычный непредметный текст не меняет items. Короткие ответы продолжают работать
по сохранённому typed pending_clarification. Состояния разделены по user_id,
проверка авторизации и повторная проверка доступа перед отправкой сохранены.

Python разбирает только полные однозначные команды: «В позиции 1 измени марку
на Ст20», «В позиции 1 измени количество на 0,0015 т», «Верни исходную марку
позиции 1», «Везде С255 замени на Ст3». Сложные команды остаются interpret_message.
Номера относятся к текущему отсортированному списку, правка выполняется на копии.
В AI-контексте правок передаются только position/item_id, товар/типоразмер,
текущие grade/quantity/unit и исходные значения этих трёх полей. История и
полные source_text/initial_extraction не нужны для выбора поля и исключены:
5 позиций — 9223 → 1433 символа, 21 позиция — 35255 → 5692 символа.
Доменные инструкции и strict JSON Schema не сокращены.

Один operation охватывает handler от авторизации до отправки. stage_ms измеряет
monotonic clock: authorization, routing, classification/extraction, validation,
normalization, sorting, formatting, sqlite_load/sqlite_save и sending. AI-вызов
включает сеть и SDK; отдельно измерить чистое серверное время или прокси из этого
ответа нельзя. Ошибка, перехваченная handler для отправки безопасного сообщения,
остаётся processing_error и ошибочным result операции. Логи не включают ключи,
Telegram ID, текст заявки или ответ модели. Настройки прокси, таймаутов и SDK
retries не изменены; теперь повторы доступны в метриках.

Локальное сравнение с mock AI и временной SQLite, 40 сообщений на сценарий,
медианы полного process до/после:

Это локальные mock-замеры, не скорость модели. Основная экономия — исключение

## Этап 1: проверяемая нормализация больших заявок

Проверка исходных строк предшествует производной консолидации. Дополнительный
