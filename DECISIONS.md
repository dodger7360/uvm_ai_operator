# Architectural Decisions

Здесь фиксируются важные архитектурные и технические решения проекта.

---

## ADR-001 — SQLite как первая БД

**Статус:** принято

Для первой версии проекта используется SQLite.

### Причины

- простота;
- не требует отдельного сервера;
- достаточно для MVP;
- удобно для локальной разработки;
- хорошо подходит для текущего Python-проекта.

### Ограничение

Архитектура должна позволять перейти на PostgreSQL без переписывания бизнес-логики.

На текущем этапе PostgreSQL не подключается.

## ADR-002 — AI не является источником истины

**Статус:** принято

AI используется для:

- понимания свободного текста;
- извлечения структурированных данных;
- нормализации пользовательских запросов;
- анализа переданного контекста;
- формирования итогового ответа.

AI не должен самостоятельно определять:

- наличие товара;
- остатки;
- цены;
- характеристики товара;
- данные поставщиков;
- результаты парсеров;
- рыночные факты;
- результаты расчётов.

Источником истины являются БД, файлы, парсеры, внешние источники и бизнес-логика приложения.

## ADR-003 — AI-вызовы централизуются в AIService

**Статус:** принято

Все обращения к AI должны проходить через единый слой `AIService`.

Telegram handlers и бизнес-логика не должны напрямую управлять API-вызовами модели.

Причины:

- единая конфигурация;
- единая обработка ошибок;
- контроль промптов;
- возможность смены модели;
- удобное тестирование;
- контроль расходов API.

## ADR-004 — Telegram не содержит бизнес-логику

**Статус:** принято

Telegram используется как интерфейс пользователя.

Handlers должны:

1. принять сообщение;
2. передать его в application/service layer;
3. получить результат;
4. отправить ответ пользователю.

Расчёты, работа с БД, AI, остатками и рынком находятся за пределами Telegram handlers.

## ADR-005 — Market Sources реализуются через отдельные адаптеры

**Статус:** принято

Каждый внешний источник рынка реализуется как отдельный адаптер.

Целевые источники:

- Metalservice Москва;
- Metalservice Екатеринбург;
- московские склады.

Это позволяет менять или добавлять источники без переписывания основной бизнес-логики.

## ADR-006 — Первая эталонная номенклатура

**Статус:** принято

Первым эталонным товаром для разработки и тестирования является:

**Арматура Ø12 А500**

На этом товаре последовательно проверяется весь основной pipeline:

```text
Telegram
→ AI parsing
→ Structured Request
→ Validation
→ Product
→ Inventory
→ Market
→ Context
→ Final answer
```

После прохождения полного сценария архитектура расширяется на остальные виды металлопроката.

## ADR-007 — Структурированные данные между слоями

**Статус:** принято

Между AI и бизнес-логикой должны использоваться структурированные данные.

Предпочтительный формат:

```json
{
  "items": [
    {
      "product": "арматура",
      "diameter": 12,
      "steel": "А500",
      "quantity_tons": 20,
      "city": "Москва"
    }
  ]
}
```

После получения результата Python должен выполнить валидацию.

Непроверенный свободный текст AI не должен напрямую использоваться бизнес-логикой.

## ADR-008 — Metal Reference как внутренняя база знаний сортамента

**Статус:** принято

- Metal Reference — машиночитаемая внутренняя база знаний сортамента для AI-оператора, не пользовательский каталог.
- Источники: 23MET, данные складских остатков компании и в будущем другие источники. Граница поддерживаемого ассортимента определяется потребностями УВМ-Сталь и прежде всего фактическим ассортиментом компании; отсутствие остатка не означает отсутствие товара в сортаменте.
- Текущий согласованный scope — 32 категории, перечисленные в `docs/METAL_REFERENCE.md`; категории сайта сверх этого списка автоматически не включаются.
- 23MET `/price` является полноценным источником товарных и справочных данных, а не только коммерческим источником.
- Reference Data и будущие Market Data разделяются по назначению данных, а не по URL. Одна страница `/price` может содержать оба вида данных.
