# PLAN — ТГ Бот: Оператор снабжения

## 1. Назначение проекта

Создать внутреннего Telegram AI-ассистента для сотрудников снабжения.

Основная задача системы — принимать обычные человеческие заявки на металлопрокат, понимать их содержание, структурировать данные, проверять наличие собственного металла, определять дефицит, при необходимости искать металл на внешнем рынке и формировать полезный для снабженца ответ.

На первом этапе система предназначена для внутреннего использования.

Коммерциализация, продажа сервиса внешним клиентам и создание SaaS-продукта сейчас не являются целями проекта.

---

# 2. Конечный пользовательский сценарий

Пользователь пишет в Telegram заявку в свободной форме.

Например:

> Нужна арматура 12 А500 20 тонн в Москве

Система должна:

1. понять заявку;
2. выделить товары;
3. нормализовать характеристики;
4. определить количество;
5. определить регион / город, если он указан;
6. проверить собственные остатки;
7. при необходимости проверить остатки по складам и филиалам;
8. определить дефицит;
9. при наличии дефицита проверить внешний рынок;
10. использовать доступные рыночные источники;
11. при необходимости учитывать дополнительный контекст рынка;
12. сформировать краткий и понятный ответ снабженцу.

Целевая цепочка:

```text
Telegram
    ↓
User Request
    ↓
AI Request Parser
    ↓
Structured Request
    ↓
Validation
    ↓
Product Normalization
    ↓
Own Inventory
    ↓
Warehouse / Branch Inventory
    ↓
Deficit Calculation
    ↓
External Market
    ↓
Market Context
    ↓
Response Generator
    ↓
Telegram
```

# 3. Главный принцип проекта

AI не является источником истины.

AI используется для:

- понимания естественного языка;
- извлечения структуры из заявки;
- нормализации;
- анализа предоставленного контекста;
- формирования ответа.

Фактические данные должны поступать из проверяемых источников:

- базы данных;
- файлов компании;
- результатов парсеров;
- складских остатков;
- внешних источников;
- явно предоставленного пользователем контекста.

AI не должен самостоятельно придумывать:

- цены;
- остатки;
- наличие;
- характеристики;
- поставщиков;
- новости;
- результаты парсинга.

Если данных недостаточно, система должна явно сообщать об этом.

Первый товар, на котором строится и проверяется логика проекта:

**Арматура Ø12 А500.**

Этот товар используется как эталон для:

- AI-парсинга;
- нормализации;
- Product Model;
- хранения в SQLite;
- проверки цен;
- работы с остатками;
- проверки источников;
- формирования ответа;
- последующего масштабирования.

Нельзя считать задачу завершённой только потому, что код работает на искусственном примере.

Telegram является интерфейсом.

Основная бизнес-логика не должна находиться внутри Telegram handlers.

6. AIService

Все обращения к OpenAI API должны проходить через централизованный AIService.

AIService отвечает за:

создание AI-запросов;

отправку запросов;

получение структурированного ответа;

обработку ошибок;

контроль конфигурации;

единый интерфейс работы с AI.

Нельзя без необходимости размещать отдельные OpenAI API-вызовы непосредственно в:

Telegram handlers;

парсерах;

database modules;

бизнес-логике.

AI должен возвращать структурированные данные там, где результат используется программой.

Python обязан валидировать результат AI перед передачей дальше.

7. Структурированные данные

Предпочтительный поток:

User Text
    ↓
AI
    ↓
Structured JSON
    ↓
Python Validation
    ↓
Business Logic

Например:

{
  "items": [
    {
      "product": "арматура",
      "diameter": 12,
      "steel": "А500",
      "quantity_tons": 20,
      "city": "Москва"
    }
  ]
}

Фактическая схема будет уточняться при реализации.

8. База данных

На текущем этапе используется:

SQLite.

PostgreSQL сейчас НЕ подключается.

Архитектура должна позволять в будущем перейти на PostgreSQL без переписывания бизнес-логики.

Нельзя размещать SQL-логику непосредственно внутри Telegram handlers.

Работа с БД должна проходить через отдельный database layer / repositories.

9. Основные сущности

Целевая модель данных включает:

Product

Товар и его нормализованные характеристики.

Request

Пользовательская заявка.

RequestItem

Отдельная позиция внутри заявки.

Warehouse

Склад или филиал.

Inventory

Остаток товара на конкретном складе.

MarketPrice

Результат получения рыночной цены.

MarketSource

Источник рыночных данных.

ContextEvent

Дополнительный рыночный или бизнес-контекст.

Состав полей будет уточняться по мере реализации.

10. Собственные остатки

Исходные данные по остаткам могут поступать из Excel и других корпоративных файлов.

Файлы являются исходным источником данных.

AI не должен самостоятельно интерпретировать Excel вместо программной обработки.

Предпочтительный поток:

Excel / Source File
    ↓
Python Parser
    ↓
Validation / Normalization
    ↓
SQLite
    ↓
InventoryService

При изменении исходного файла должна быть возможность повторно загрузить данные.

11. Склады и филиалы

Система должна учитывать наличие товара не только в одном месте.

Для заявки необходимо иметь возможность определить:

общий собственный остаток;

остаток по складам;

город;

филиал;

доступный объём;

дефицит.

Пример:

Запрос:
Арматура Ø12 А500 — 20 т

Москва:
Склад 1 — 7 т
Склад 2 — 4 т

Общий остаток — 11 т
Дефицит — 9 т

Расчёт должен выполняться Python / бизнес-логикой, а не самим AI.

12. Рыночные источники

Первоначальные источники:

Металлсервис Москва.

Металлсервис Екатеринбург.

Склады Москвы.

Каждый источник должен быть реализован как отдельный адаптер.

Целевая структура:

MarketSource
    ├── MetalserviceMoscow
    ├── MetalserviceEkb
    └── MoscowWarehouses

Добавление нового источника не должно требовать переписывания основной бизнес-логики.

13. История рыночных данных

Результаты парсеров должны сохраняться в SQLite.

Минимальный набор:

источник;

город;

товар;

характеристики;

цена;

наличие;

timestamp.

История сохраняется прежде всего как источник данных для дальнейшего анализа.

Проект не должен превращаться в простой dashboard исторических цен.

Необходимо сохранять данные сейчас, чтобы в будущем иметь возможность анализировать:

значимые изменения;

аномалии;

резкие движения;

различия между регионами;

связь с рыночным контекстом.

14. Ценообразование и рыночный контекст

Арматура Ø12 А500 является базовой точкой для первоначальной логики ценообразования и сравнения.

Система не должна строить бессмысленный универсальный прогноз цены только на основании исторического ряда.

В будущем AI может использовать:

актуальную цену;

историю;

динамику;

другие товары;

регион;

новости;

информацию от пользователя;

подтверждённые рыночные события.

AI должен разделять:

Факт

Подтверждённые данные источника.

Наблюдение

Вывод непосредственно из имеющихся данных.

Гипотеза

Предположение, которое требует подтверждения.

Нельзя выдавать гипотезу за факт.

15. Пользовательский контекст

Пользователь должен иметь возможность передавать системе важную информацию о рынке.

Например:

ожидаемое изменение цен;

информация от поставщика;

ожидаемое повышение / снижение;

изменение условий поставки;

важное событие на рынке;

внутренний комментарий снабжения.

Такая информация должна сохраняться как отдельный контекст, а не смешиваться с фактическими данными источников.

16. Парсеры

Парсеры являются источниками данных, а не самостоятельной бизнес-логикой.

Парсер должен:

получить данные;

извлечь необходимые поля;

нормализовать технический формат;

вернуть структурированный результат;

передать данные в соответствующий сервис / repository.

Парсер не должен самостоятельно принимать решения о закупке.

17. Telegram

Telegram является интерфейсным слоем.

Telegram handlers должны:

принимать сообщения;

передавать их application/service layer;

возвращать пользователю результат.

Telegram handlers не должны содержать:

сложную бизнес-логику;

SQL-запросы;

прямые OpenAI API-вызовы;

расчёт дефицита;

логику ценообразования.

27. Архитектурные принципы

Простота

Не усложнять систему раньше необходимости.

Разделение ответственности

Telegram, AI, бизнес-логика, база и источники должны иметь разные зоны ответственности.

Проверяемость

Каждый важный результат должен иметь возможность быть проверенным.

Расширяемость

Добавление нового товара или источника не должно требовать переписывания всей системы.

Данные важнее предположений

Фактические данные имеют приоритет над предположениями AI.

Человек контролирует архитектуру

AI предлагает и реализует, но архитектурные решения принимает пользователь.

28. Definition of Done

код запускается;

изменённые файлы понятны;

документация обновлена, если изменение влияет на архитектуру или правила проекта.
